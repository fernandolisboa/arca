# ADR-0029: Correction requests, answered by a scheduled corrector run

- Status: Accepted
- Date: 2026-11-12
- Issue: [#413](https://github.com/fernandolisboa/arca/issues/413)
- Amends: [ADR-0006](0006-auth.md) and [ADR-0015](0015-identity-enrollment-step-up-and-recovery.md) (a step-up purpose, `corrector_key`); [ADR-0008](0008-database-security-and-environments.md) (roles for the request tables and the corrector key); [ADR-0010](0010-stack-revised.md) and [ADR-0021](0021-stay-on-vercel-and-neon.md) (a second kind of object in the Blob store); [ADR-0014](0014-knowledge-base-as-reviewed-data.md) (how a fix starts; a second unwatched authoring run)

## Context

An admin who reads a version and finds an item wrong can only reject it. A rejection is final and only falls back: to the previous active version, or to no version, so evaluations show "Indisponível". It records no reason and starts no fix. Versions are immutable files in the repository; a fix is a new version with `corrects`, written by an authoring session that follows the [rule audit runbook](../runbooks/rule-audit.md). Such a session starts when the owner asks for one, or on the monthly run's schedule, which picks routes by the age of their last audit, not by what anyone found wrong. The members' rule report (spec 0007, R8) counts flags per requirement, carries no sources and starts no session on its own.

The owner asked on 2026-11-12 for a way to point at what is wrong, item by item, attach sources (a link, pasted text or a file), and have the AI write the correcting version, which he then only activates.

## Decision

### Requests

- **Correction request** (UI "Pedido de correção"). On the version screen, an admin on the owner list opens "Apontar erro" on one item, on the version's settings, or on the whole version; the item kinds are the ones the version view and the check items already name, never a fixed list in the client. The admin writes what is wrong (up to 4,000 characters) and adds up to five sources: an `https` link, pasted text (up to 20,000 characters) or a file (PDF, HTML or plain text, up to 16 MB). Only owner-list admins file, so a request is the owner's own word and may start work (CLAUDE.md, "Only the owner's words set the work"); it sets which route, version and item to audit, never the rule's content. Each filed request emails the owner-list admins a generic notice with one link. The database functions take the admin basis the API computed: they accept only `owner_list` for filing, and check a `grant` basis against the grant history, as ADR-0027 does. Admins holding a grant see requests and their answers but do not file them.
- **Knowledge data, written by the owner.** A request names a route, a version and an item, never a case or a person. The form says, above the note, the pasted text and the file picker, that a request is read by an AI session and must hold no personal data. The owner chose on 2026-11-12 to send requests to the corrector run; that is the one way rows written in production reach a session outside it, and it covers requests only.
- **States**, computed by a pure function in `packages/domain` from the request's rows and the catalog's version identities and decision states: `open` → `taken` → `answered` (a proposed version, or an explanation of why nothing changed) → `closed`. Deciding the version an answer proposed closes the request; so does activating any correction of the request's version, as it closes rule reports. An admin can close a request at any time. Since a request on a version whose correction is already active would close at once, filing one is refused (`409 already_corrected`); a request closed by a correction's activation opens again if that correction is later rejected, since the fix it waited for no longer stands.

### Storage and roles

- Tables in the `knowledge` schema: requests, their sources, their events (taken, answered, closed) and corrector keys. Rows are only inserted; the retention step clears contents, and account erasure deletes the author's requests with their sources and events, through the registry as for rule reports; the export only reads. `app_api` serves admins only through reviewed `SECURITY DEFINER` functions, owned by the `knowledge_definer` role, after its own check, as with rule reports; it holds no table privileges, and the author's export reads their own rows through one of those functions too. Each function re-checks what it serves. The owner list lives in code (`owner-list.ts`), so filing a request and creating a key check it in the API and in the `app_auth` code that writes the key, and the functions refuse an account without the admin role (for the owner list, which lives in code, the database can check only that the transaction names an account; for a grant, that the grant to that account exists and no removal ended it, coarser than the API's replay of the history); reading and closing need the admin role as ADR-0027 computes it from the owner list and the grant history; key routes need a live key's hash. Corrector keys are inserted by `app_auth` behind a step-up. The retention step and erasure run as `app_jobs` under the author's identity, through the registry. The access-matrix suite covers every function for each role, including a granted admin refused when filing.
- **Files** go to the existing private Blob store, under a `corrections/` pathname prefix with random names, as plaintext copies of what are meant to be official texts. The upload grant fixes the size and the media type; completion re-checks size, SHA-256 and type by content. A file is downloaded only through a 5-minute URL minted per file after an admin or key check, served as an attachment with `nosniff`, never shown inline on the app's origin.
- **Retention.** A request's note, pasted text, links and files are erased 30 days after an admin closes it, or 180 days after it was filed otherwise; the source rows go and the request row keeps only identifiers, states and dates. A request closed because a correction of its version is active, or because an answer's version was decided, counts as unclosed here: that state is computed from the catalog, can open again when the correction is rejected, and leaves no date the job reads, so its leads stay until the 180 days. The daily cleanup job does it as `app_jobs` under the author, files first, and deletes an upload no request names a day after it started. The author's account erasure erases them at once, files first, and the author's export carries the note, links and text, and each file's type, size and date.
- **Files, as built (#415).** The admin starts an upload through a definer function that records the declared type, size and SHA-256 under a random `corrections/` pathname; the presign route signs a put of that type and at most that size, for 5 minutes, within an hour of the start. Filing names each upload, at most 2 hours old and named by no other request, checks the stored object (size, SHA-256, and type by its first bytes: a PDF's signature, an HTML opening tag, no binary byte in text) and deletes one that differs. The #414 functions stay as they are, since only their owner can replace them and a migration never changes role: files are added in the filing transaction by a function of their own, which takes only a request of the same author filed since that transaction started, and their type and size are read by another. Admins, by the owner list or a grant, download a file through a 5-minute URL with `download=1`, which the store serves as an attachment with `nosniff`; minting one and a refused file are audited with identifiers only. The type check reads only the first bytes, so an HTML or PDF file may carry script: it reaches admins only as a saved file named by its server-side type, never rendered on the app's origin, and the corrector run reads it as data. That residue is accepted with R-12, since only an owner-list session uploads.

- **Key and answers, as built (#416).** A `corrector_key` table holds `created` rows, inserted by `app_auth` under a policy that needs the actor's own spent `corrector_key` step-up, and `revoked` rows, inserted by a definer function; the live key is the newest created row unless revoked or a year old, and the API also requires its creator on the owner list with a confirmed account. Rows are retained with account IDs and digests only, as the history the answers name; the author's export carries their kind and date. `app_api` reads the live key's ID, digest, creator and date through `live_corrector_key()` and compares the presented key's SHA-256 in constant time; the definer functions the key opens (`corrector_request_list`, which lists a file with the cited page it copies and replaces the unused `corrector_requests`, `corrector_file`, `answer_correction_request`) take the key's ID and digest and refuse any but the live one. That re-check guards against a stale or revoked key, not against code running as `app_api`, which can read the digest; such code could already read every request through `correction_requests`, so the key adds no reach to it. Events gain the key that wrote them, a proposed version or an explanation (up to 2,000 characters), one event of each kind per request; admins read them through `correction_events`. An answer's explanation is the run's own plain-text summary of what it looked for and found; it must not quote the request's note, pasted text or files (the corrector run's prompt says so, #417), and it stays with the states until the author's account erasure deletes the request with its events. The corrector listing returns open and taken requests by computed state; a request already answered or closed answers 404. The listing is a `GET`; the file URL and answer routes are `POST` routes like any other, so the run sends the production origin as `Origin` on them. Making or revoking a key sends the owner-list admins the `corrector_key_changed` notice; audit codes are `corrector_key_created`, `corrector_key_revoked`, `corrector_key_refused`, `corrector_requests_listed`, `corrector_file_downloaded`, `correction_answered` and `corrector_use_refused` (a refused file or answer, with the request's ID and the reason); limits are in `correctorLimits` and `correctorKeyLimits` (`apps/api/src/auth/limits.ts`); the secret scan has a rule for the `arca_ck_` format. A file URL is minted only for a request the listing returns. Admins by grant see the live key's dates in settings, never the key, and cannot make or revoke one.

### Page copies (amendment 2026-11-12)

The owner agreed on 2026-11-12 that a copy he attaches may stand in for an official page the independent check cannot read (a site that refuses automated reading, redirects it away, serves too much, or serves a scan), as a fallback.

- **Naming the page.** A file source may name the page it is a copy of: one of the pages the version cites, picked from its sources on the form, never a free address. Filing refuses another (`404 not_found`). The page is stored on the source row (`page_url`) and listed with the file. Files are attached through `attach_correction_file_with_page`; the #415 function stays, unused, since only its owner could replace it.
- **Reading it.** The check reads a page, or its machine-readable address, as before. Only when that fails, and not because the page is off the version's pinned official hosts (`refused_url`), does it ask `knowledge.correction_page_copies`, which `app_jobs` runs with no account and which answers, for the cited URL, the newest stored copy's pathname, type, size and SHA-256, never a request's note, text or author. It reads the object from the store, refuses one whose size or SHA-256 differs from its upload, and turns it into text as the fetcher does for that media type (an HTML copy is read as UTF-8, by choice). Any failure leaves the page's own failure in the report.
- **In the report.** The fetch log marks the page `fromCopy`, keeps the page's own final status and names no address. The panel says, under each quote from it and in the page list, that the site did not open and the copy was read. A page read from a copy counts as read, so such a report lasts the usual 30 days, not one; attaching a copy later, or its erasure, does not make the current report stale, and an admin starts a new check to use it. `fromCopy` is stored only when true and read with a default of false, so code from before reads every report that read no copy; after a rollback of the API it shows no report for one that did, as ADR-0027 says of addresses.
- **Any stored copy.** The newest copy of the URL is read whatever its request's route, version or state, a closed one included, until retention erases it: a request is closed when its fix is done, not because its copy was wrong. To withdraw a wrong copy, the owner attaches a right one, which is newer.
- **Residue.** A copy is official text only by the owner's word, and the corrector run may read the same file, so a version written from a copy and checked against it can come out clean and join the checked batch: the page list and every quote from it say a copy was read, and the admin's activation stays the decision (accepted with R-12). The database takes any `https` page on a file; only the API checks that the version cites it, so a copy matches every route citing that URL. The report names no copy's date. `page_url` is an official address, not personal data, and the export function cannot be replaced, so the export leaves it out. The form asks for a page saved while signed out, since its text reaches the check model. A copy is still official text only by the owner's word: the check verifies quotes against the copy, and the admin's activation stays the decision. The prompt is unchanged, so no evaluation case changes.
- **Not in the catalog check.** It runs from bundled data with no database, so it reads no copy.

### Requests for a new route (amendment 2026-11-12)

The owner asked on 2026-11-12 for routes no session could author because their official sites refuse automated reads (Lithuania #99, Israel #109), [#418](https://github.com/fernandolisboa/arca/issues/418).

- **The request.** On the activation screen, an owner-list admin opens "Pedir regra nova", a guide in four steps: the country (any in the countries dataset) and a note saying which route; the official pages, each saved as PDF while signed out and attached with its address, or given as a link; the passages that carry the requirements, amounts, deadlines and dependent rules, each pasted with the page it came from; a review. It is a correction request whose item kind is `newRoute`, naming a country and no route or version, with up to twenty sources; a pasted text may name the page it came from, on any request. Filing, files, the notice, closing, retention and erasure are those of any request; `file_route_request`, `route_requests`, `corrector_request_queue` (which replaces `corrector_request_list` for the API and adds the country), `answer_route_request` and `own_correction_request_rows` (the export, now with the country) are new definer functions, since the earlier ones cannot be replaced. Admins by grant see these requests and their answers.
- **The copy stands for the page.** A file on such a request names any `https` page, not one a version cites, since no version exists yet. When the site refuses, the copy the owner attached stands, as his word, for the page he names: the version cites the page's own address and quotes the copy, and the independent check reads the same copy (page copies above), so the report says a copy was read. A passage with no copy behind it stays a lead. This settles the open question this ADR left (owner agreement in principle, 2026-11-12).
- **A country's first list.** The owner chose on 2026-11-12 that the corrector run writes a country's first official-domain list when it has none, in a pull request of its own that it may merge, holding only hosts of the request's pages that belong to a government or public body, each with an official source. It never changes an existing list.
- **The answer.** `version_proposed` names the new route, which must start with the request's country code; the event stores it (`proposed_route_id`). Deciding that version closes the request; an admin may close it before. `no_change` says what was missing.
- **Residue.** Since the page is any `https` address, a copy of it also feeds the check of any other route citing that address, as for any copy (R-12); only owner-list admins file. A first list rests on the official sources the run found, and the copy may be one of them: the admin's activation of the route stays the decision.

### The corrector run

- A scheduled task fires once a day into the project thread "Corrigir as regras apontadas", in a cloud environment of its own that holds only `ARCA_CORRECTOR_KEY` and reaches GitHub through the Claude GitHub App: no Vercel token, no other credential. With no open request, the run ends.
- It is a monthly-run-style session: everything the runbook's ["The monthly run"](../runbooks/rule-audit.md#the-monthly-run) requires of an unwatched run holds, from the fresh clone and the check against a reviewed prompt to merging on its own only when every changed path is a route version, its cases, a country set, `hashes.json` or a route note. It never writes a country guide, an official-domain list (but a country's first, for a request for a new route, amendment above), a reading recipe or OPEN-QUESTIONS; it notes the need in its answer for an on-demand session. It reads no issue. It takes at most three requests a run. The runbook gains a "corrector run" section with its prompt ([#417](https://github.com/fernandolisboa/arca/issues/417)).
- Per request it marks the request `taken`, runs the audit of the route with the request as a lead, including the check loop, merges, and answers once production serves the new version: `version_proposed` with its number, or `no_change` with a plain-text explanation in pt-BR of up to 2,000 characters, shown with links marked like any model output.
- **Leads, not sources.** A request is a lead: only an official source with an address changes a rule. Pasted text and files help find that source; when none is found, the answer is `no_change`, saying what was looked for.
- **Nothing from a request reaches the repository.** Route notes and pull requests name the request by its ID and cite the official sources found; they never quote or paraphrase its note, pasted text or files, and never cite a link of it that is not official.

### The corrector key

- 32 bytes from the server's CSPRNG, base64url with a fixed `arca_ck_` prefix that the secret scan knows, created by an owner-list admin with a step-up of its own purpose (`corrector_key`, spent in the same `app_auth` transaction that inserts the key), shown once with `Cache-Control: no-store` and kept out of client state, stored as its SHA-256; one key is live and a new one replaces it; it expires after a year. Creating one writes an audit event and emails the owner-list admins. A key stops working when its creator leaves the owner list or is erased, and an owner-list admin can revoke it without a step-up; a revocation is an inserted key event, written through a definer function, audited and emailed like a creation.
- It travels in an `Authorization` header, compared by hash in constant time, on three routes only: list open and taken requests with their sources (at most ten, oldest first); a download URL for one file of a listed request; and an answer that moves a request `open` → `taken` or `taken` → `answered`, checked against its computed state. A key can never close a request. The API refuses a proposed version that production does not serve, is on another route, neither corrects nor follows the request's version, or is already active or rejected (proposing it would close the request). Each use writes an audit event naming the key by its row ID, never its value or hash; all three routes are rate limited per key in Postgres; refused keys are rate limited per address before any audit write, and audited with identifiers only, never the presented value. The run never prints the key and sends it only to the production origin, through a reviewed script that pins the host (#417).

## Alternatives

| Option | Why not |
| --- | --- |
| Let the admin edit a version in the app | Versions are immutable (rule 6); old evaluations must stay reproducible |
| Draft the version inside the app with the Claude API | The draft still has to become a reviewed file in the repository, which needs a write path to GitHub from production and skips the reviewers and the check loop |
| The app opens GitHub issues | The repository is public, so notes and files would be published; it also needs a GitHub token in production |
| The session reads the production database | Services never connect with an owner role, and a database credential would reach case data (ADR-0008) |
| Any admin files requests | A grantee's words would start unwatched work, which CLAUDE.md gives only to the owner |
| The run uses the shared agent environment | It holds the Vercel token, and a run that reads leads every day would carry it (residual R-12) |
| A request on every rejection | A rejection is still right for a version that must not be used at all; asking for a fix is a separate act |

## Consequences

- A wrong item gets fixed without the owner starting a session: he points, and later activates the version the request links to.
- The owner does one setup step: create the key in the app and paste it into the corrector's environment. A new key replaces a lost or leaked one.
- A leaked key lets someone read open requests, mark them taken, or answer with a misleading explanation; it cannot close them, change a rule or reach case data, and the admin still decides every activation. Its uses are audited.
- Filing needs a signed-in owner-list session, not a step-up: someone holding a stolen owner session could file requests that the run reads every day. Each filed request emails the owner-list admins, so he can close one he did not file; closing it does not withdraw a page copy it carries, so he also attaches a right copy and starts a new check (page copies), and the run's path gate lets it merge only route data, never code (residual R-12).
- A steered run could still merge a wrong route version; it stays proposed, and the check and the admin's reading stand between it and use, as for the monthly run.
- The Blob store is no longer ciphertext only: it holds plaintext copies of official texts for at most 180 days.
- A daily run spends Claude Code usage only on days with open requests.
- An uploaded copy of a cited page feeds the independent check when the page cannot be read, marked as a copy in the report (amendment above).
- A route whose site refuses automated reads can still be added: the owner attaches its pages through "Pedir regra nova", and only activates the version the run writes (amendment above).
