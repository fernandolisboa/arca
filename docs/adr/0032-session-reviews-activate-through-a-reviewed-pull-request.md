# ADR-0032: Session reviews store and activate rule versions through a reviewed pull request

- Status: Accepted, amended 2026-11-20 (the offline check reads the echo rule on the address the app requests) and 2026-11-25 (a review may add a new route of a country whose stored routes already pin an official-domain list, [below](#amendment-2026-11-25-new-routes))
- Date: 2026-11-19
- Amends: [ADR-0031](0031-rule-updates-on-request.md) (a second way to add a route version, and an activation with no passkey); [ADR-0019](0019-reviewers-in-the-authoring-session.md) (one CI job reads official pages); [ADR-0027](0027-admins-and-the-checked-batch-activation.md) (a fourth decision proof); [ADR-0014](0014-knowledge-base-as-reviewed-data.md) (who approves a version); [ADR-0008](0008-database-security-and-environments.md) (what `app_migrator` may insert); CLAUDE.md rule 5; since 2026-11-25, [spec 0002, R8](../specs/0002-rules-engine-and-knowledge-base.md) (coverage of a version with no requirement)

## Context

Since ADR-0031 a rule changes only through an update request in the app, which spends the Anthropic API credit (used up until 2026-12-01), and every version needs an admin's passkey. The catalog holds 19 routes of 18 countries whose imported versions were never checked to the owner's satisfaction, and the loop that should have done it cost more than it fixed.

On 2026-11-19 the owner asked, in the project thread, to keep the in-app flow for later and to fix this first version of the catalog in Claude Code sessions on his subscription: one thread per country, each route read against the official sources, adversarial reviewers, at most three rounds, and then publish: "assim como PRs, quando estiver tudo verde, vc mesmo aprova e publica a regra" (as with pull requests, when everything is green you approve and publish the rule yourself). Told that activation needs his passkey, he chose to drop that step for these sessions (in pt-BR): "quando vier daqui, estou tranquilo em ter aprovação direta. Já vai ter passado pelos reviewers" (when it comes from here, I am fine with direct approval; it will already have passed the reviewers), and "pode até ser que no futuro habilite isso de novo, mas pra essa primeira versão são muitos países e tipos de entrada" (I may turn this on again in the future, but for this first version there are many countries and entry types).

## Decision

A **session review** is a Claude Code session the owner asks for that reviews the stored routes of one country and stores corrected versions, already active, through a reviewed pull request. It follows [the runbook](../runbooks/session-rule-review.md).

- **What it may write.** Only the next version of a route the database already holds, on the official-domain lists that route already pins: the app's own proposal check, `checkProposal` with an `update` target, refuses anything else. Since 2026-11-25 also the first version of a new route, [below](#amendment-2026-11-25-new-routes). An official-domain list, a country set and a route of a country with no stored route still go through the app, with a passkey.
- **Files.** `packages/knowledge/reviews/<review>/<route>.<number>.json` holds the version, `.cases.json` its cases with inline snapshots, and `.evidence.json` one to five official passages for every item the quote check reads (`checkItems`), each on a page the item cites. `packages/knowledge/data` stays as the import read it.
- **Checks in code.** `packages/knowledge/scripts/session-review.ts` checks each version as an update request's proposal is checked (schema, version order, pinned files, cases and coverage) against the imported rows and every earlier review. The evidence goes through the app's own quote check (`verifyAnswers`): every item matches on one to five quotes, each from a page the item cites, and its quotes state every value the item gives. CI runs that check twice. The `check` job runs it against the quotes themselves, each page under the address the app would request for it (its machine-readable address when the version names one, since that is the address the echo rule reads; amended 2026-11-20), and compares the committed migration with one generated again, so it fails on a version that does not pass or a migration edited by hand. The `review-quotes` job, for a pull request that changes a review, reads the cited pages with the app's guarded fetcher and reader and fails when a quote is not on its page; it is the one CI job that needs a network beyond the package registry. The ruleset on `main` does not name that job, so the required `check` job waits for it and fails with it: a pull request cannot merge while a changed review's quotes are unread or missing from their pages. A session runs the same test through its sandbox's proxy while it works (`ARCA_REVIEW_QUOTES_PROXY=1`, refused in CI); only the job counts. A further test scans the text of every later migration and fails on one that names the `knowledge` schema or the `session_review` proof, or holds a DO block, and is neither a listed review's nor named in that test after its own review. The scan is a tripwire, not a parser; the database tests hold what it cannot see, since they fail when the stored activations are not exactly the listed reviews' or the migrator's rights on decisions changed.
- **Rounds.** After the session's own reading, adversarial reviewer subagents try to prove each version wrong against the official text. At most three rounds of review and correction a route; what is still disputed is listed for the owner with its reason, never counted as matching.
- **Storage and activation.** The review's generated migration inserts each version, failing when the database already holds one under that ID and number, and one `session_review` decision a version: `activate`, of a route, with no author and no assertion, bound to the content hash and the cases hash.
- **The database.** `decision.proof` gains `session_review`; a check admits it only to activate a route version with a cases hash and none of the admin or step-up fields, and the author is null on these rows only; the personal-data registry records why such a row has no owner, which its guard otherwise refuses. `app_migrator`, which owns the table, gets an insert policy for this proof alone and gives up `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES` and `TRIGGER` on decisions. No runtime role can store one. As the table's owner the migrator could take those rights back in a later migration, so they hold only while migrations are reviewed: the access test in the required `db` job fails when the migrator's rights on decisions are not exactly these after every migration, and the reviewers read each migration. These decisions leave no audit event: the audit log records what accounts do, and here the record is the decision row, the review's files and the pull request.
- **The API.** A `session_review` activation counts as stored. As for an `admin_step_up` row, a version that now reads under another content or cases hash is refused, as rejected. An admin's rejection, with a passkey, still takes any such version out of use for good.
- **Who approves.** The owner's instruction above, and the merge of the pull request once CI and the repository's must-pass reviewers pass, stand in for the passkey on these versions. The session merges it itself, as the owner has it do with every pull request; he is not asked. Eligibility stays deterministic: a model writes and checks rule data, and the engine alone decides who qualifies.
- **This decision's own pull request.** It changes rule 5 of CLAUDE.md and what four reviewers accept, on words of the owner that only the session saw. A session's pull requests, comments and merges on GitHub all carry the owner's account, so nothing there can show that he, and not the session, agreed ([ADR-0014](0014-knowledge-base-as-reviewed-data.md) says as much). The project thread is the one place his words reach the session as his. So this pull request is merged only after he confirms it there once more, having been shown it and the reviewers' objection. Later session reviews need nothing from him.
- **Turning it off.** The owner said he may want the passkey back. Dropping the `decision_insert_session_review` policy in one migration ends new activations; stored ones keep counting.

## Consequences

- A merged pull request can now put a rule into use. Before, a merge could only propose, and the passkey stood between an agent (tricked by a researched page, or misusing the owner's token) and an active rule. The owner accepts this for a family's personal app. What remains in the way: a review cannot widen an official-domain list, and adds a route only on lists its country's stored routes already pin; every item needs quotes that state its values and that the `review-quotes` job finds on an official page the item cites, with the required `check` job failing when it does; the proposal check, the migration comparison and the scan of later migrations run in CI; the reviewers read `packages/knowledge/reviews/` and the migrations; and an admin can reject any version in the app.
- Rule content of reviewed versions lives in the repository again, as review files and a generated migration. The database rows stay the only thing the API reads.
- A review needs a deploy, since its migration runs in the build ([ADR-0012](0012-automation-first-setup.md)); a failed check fails the build and leaves production as it was.
- A source's `verifiedAt` is the São Paulo date the session read its page, set by the session. [ADR-0014](0014-knowledge-base-as-reviewed-data.md) has the pipeline set it from its own clock at fetch time and lets no model set a date; here nothing in code ties the date to a fetch, and the `review-quotes` job only shows the page held the quotes when the pull request ran.
- A review is checked against the repository's rows, not production's. If an update request stored the same number in the app meanwhile, the migration fails and so does every production build until the review's pull request is reverted.
- The mechanism has no end date and no limit to a first pass: the owner said he may want the passkey back and will say when.
- The update request, its passkey decisions and the hand edit are unchanged.

## Alternatives considered

- **One passkey activation a country**, the session storing proposed versions for the owner to activate together. The owner declined it on 2026-11-19: "não, já pode propor zero toque agora" (no, you can propose zero touch now).
- **The owner merges each review's pull request.** He asked for the opposite: the session approves and publishes, as it merges every other pull request on green checks.
- **Keeping [ADR-0022](0022-single-approver-activation.md)'s and [ADR-0014](0014-knowledge-base-as-reviewed-data.md)'s line.** ADR-0022 rejected "no activation at all; merged versions count" because it breaks rule 5, and ADR-0014 holds that a merged pull request is no proof a person approved anything, since an agent can produce one. Both stay true. This ADR accepts that risk for session reviews only, on the owner's word, and narrows it with the checks above.
- **A limit in code**: only one review a route, or an expiry date. Not taken: a later correction of a reviewed version would then need the app and its API credit again, which is what the owner set aside for now.
- **Committing each page's text** so every CI run could check the quotes offline. Not taken: megabytes a country, and a committed text proves only that the files agree with each other.

## Amendment 2026-11-25: new routes

### Context

A new route entered the catalog only through the app's new-route request, which spends Anthropic API credit (a small top-up until 2026-12-01) and needs an admin's passkey. On 2026-11-25 the owner was shown, in the project thread, an app review that proposed "liberar rota nova também por thread, com o mesmo PR revisado, para usar sua assinatura" (allow new routes by thread too, with the same reviewed pull request, to use his subscription), and picked, on a decision card, the option to add new routes "por thread com PR revisado" (by thread with a reviewed pull request), starting with the United States (EB-2 NIW, L-1A, EB-1C), then Spain and Portugal.

### Decision

- **What it may write.** Also the first version of a new route, when the review's listing names the route as new (`newRoute: true`). The script checks it as the app checks a new-route request's proposal (`checkProposal` with a `new` target): an ID no stored route has, starting with the country's code; number 1; and only official-domain lists that the country's stored route versions already pin and that are approved, as the app reads them (`countryPins`). A country with no stored route, and so no list, stays out of reach: its first list is a trust root the app decides apart, with a passkey ([ADR-0031](0031-rule-updates-on-request.md)). An ID the listing does not name as new is refused, so a mistyped ID never becomes a route.
- **Everything else holds.** Files, quotes for every item, the quote check in CI and in the `review-quotes` job, at most three adversarial rounds a route, the generated migration and its `session_review` activation, the scan of later migrations, the database tests and an admin's rejection all apply as they do to an update.
- **A route that rests wholly on judgment.** Some routes have no condition the case can decide: U.S. EB-2 NIW, L-1A and EB-1C turn on degrees, experience, a job's duties and a company's ties, which the case does not record. Such a version has assessments and no requirement, so it reads `needs_assessment` for everyone and lists what an officer weighs, with its dependents, costs and durations. The coverage rule of [spec 0002, R8](../specs/0002-rules-engine-and-knowledge-base.md) asked every open version for `not_eligible` and `missing_information` cases, which only a requirement can produce; it now asks a version with no requirement and at least one assessment only for `needs_assessment`, the one status it can reach; a version with neither still fails, so no route can read `eligible` for everyone. A requirement is still never bent to pass: one that cannot be false is not written.
- **This amendment's own pull request** changes rule 5's paragraph in CLAUDE.md and what the security and AI safety reviewers' prompts accept (the data-access and auth and cryptography prompts never limited a review to updates), on the owner's choice on that card in the project thread. As with this decision's own pull request, nothing on GitHub can show that he agreed, so it is merged only after he confirms it in the project thread, having been shown it and the reviewers' objections. Later session reviews need nothing from him.

### Consequences

- A merged pull request can now put a new route into use with no passkey, on lists the country already trusts. A wrong route shows to the family as `needs_assessment` or worse until an admin rejects it in the app.
- New routes for Spain, Portugal and any other country whose stored routes pin an official-domain list can follow the same runbook; a country with no stored route still needs its first list through the app.
