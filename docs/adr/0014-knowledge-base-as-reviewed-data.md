# ADR-0014: The knowledge base as reviewed data in the repository, activated by a person's passkey

- Status: Accepted
- Date: 2026-11-02
- Amends: [ADR-0002](0002-rules-as-versioned-data.md) (where route versions live, the shape of their sources, the country dataset, how approval is recorded); [ADR-0006](0006-auth.md) (knowledge-base decisions join the step-up actions, verified against keys pinned in the repository rather than the passkey table, as the slice 3 ADR will specify); [ADR-0010](0010-stack-revised.md) (fast-check for property tests); [ARCHITECTURE.md](../ARCHITECTURE.md) (code layout, rules flow, entities); CLAUDE.md domain rule 5 (what "sees the change" means)

## Context

[ADR-0002](0002-rules-as-versioned-data.md) makes rules versioned data evaluated by a pure function, with human approval before the engine sees a change. It does not say where the versions live, how they are tested, or how approval is recorded. Facts that shape the answer:

- The knowledge base holds public rules only: routes, requirements, fees, durations, country sets and their sources. It never holds case data ([SECURITY.md](../SECURITY.md), cross-case leakage). The repository is public, which is fine for public rules.
- CLAUDE.md requires table-driven tests for every rule version. Tests live in the repository, next to code.
- Agents act with the owner's GitHub token ([ADR-0012](0012-automation-first-setup.md)). A merged pull request, an approving review or a label from the owner's account is therefore no proof that a person approved anything: an agent can produce each of them.
- A passkey assertion needs a person's gesture on an authenticator, which an agent holding a GitHub token cannot produce.
- Nothing reaches a user from the knowledge base until slice 3 of the consultancy core (case model and intake), which comes after authentication and step-up ([spec 0002](../specs/0002-rules-engine-and-knowledge-base.md#the-epic-consultancy-core)).
- A poisoned or wrong rule harms every family that relies on it ([SECURITY.md](../SECURITY.md), assets).

## Decision

### Where the base lives

- Route versions, country sets (for example, the E-2 treaty countries), the official-domain lists and the country lists are JSON files in `packages/knowledge/data`, one file per version, validated by the rule schema in `packages/domain` ([spec 0002](../specs/0002-rules-engine-and-knowledge-base.md)).
- Each route version ships with its table-driven cases in a sibling cases file. CI rejects a version whose cases do not exercise every requirement every way.
- Sources are a list per version, each with an ID, URL, title, kind (`official` or `secondary`) and `verifiedAt`; an `official` source's host must be on an official-domain list the version pins (spec 0002, R4 and R6). This replaces ADR-0002's single source URL.
- Country codes come from a pinned Unicode CLDR release, plus a reviewed list of former states with ISO 3166-3 codes (spec 0002, R7). This is ADR-0002's ISO 3166 dataset.
- The API bundles the validated catalog at build time. The database gets knowledge tables only when decisions (slice 3) or retrieval (slice 6) need them.
- Whether documents, steps, fees and action points (`knowledge_item`, `action_point`) also become files is decided by slice 5.

### Immutability

- A file under `packages/knowledge/data` or `packages/knowledge/vendor` never changes once it is on `main`. A required check fails a pull request that modifies, renames or deletes one. The check runs from `main` and reads the pull request's files as data, so a pull request cannot weaken the check that judges it (spec 0002, R6). Cases files and `hashes.json` are append-only instead: they may gain entries, never change or lose them.
- A rule change is a new version with an effective date later than every earlier version's. A correction of a data error is a new version with a `corrects` field naming an earlier version; once the correction is in effect, the version it fixes is no longer selected (spec 0002, R5). Re-verifying a source is a new version too, so every date a user sees has been through the same approval.
- Each version is identified by its route ID and number, and by a content hash over the version and every file it pins, transitively (spec 0002, R6). Evaluations record both, plus the engine's commit, so an old evaluation can be reproduced exactly.

### Approval in two steps

1. **Proposal.** A change reaches `main` through a pull request like any other, reviewed by the gate. Merged versions are *proposed*: they exist in the catalog, but the engine does not evaluate them for any case.
2. **Decision.** An approver either *activates* or *rejects* a version in the app, with a passkey step-up bound to its content hash.
   - Only an active version is evaluated.
   - A rejected version is never selected; the route reads whatever selection picks without it, by the rule in spec 0002 R5, which also covers a later correction of a rejected one. It can never be activated again; a fix is a new version. Rejection works on a proposed version, which is how a bad proposal stops blocking a route, and on an active one, which takes a rule out of use. A rejection wins over an activation of the same version.

This is what CLAUDE.md rule 5 means by the engine seeing a change. The engine contract that enforces it, including the identity fields selection may read and the `pending_activation` status, is spec 0002 R5; this ADR does not repeat it.

Until decisions exist (slice 3), no version is active. That is safe, because nothing reaches a user before then.

### Decisions: required properties

The decision ceremony, the approver list and its lifecycle, notices and storage are designed in the slice 3 spec and a later ADR, after the foundations' step-up ADR is accepted. That ADR must justify using WebAuthn as a signing ceremony (SECURITY.md principle 6) and pass the auth and cryptography, data access and security reviewers. The properties below are a floor that its reviewers check it against, not the design.

- **A person decides.** A decision is a fresh passkey step-up by a listed approver from their own session, on the production deployment only. Being in a case grants nothing.
  - The binding lives inside the signed bytes. The challenge is SHA-256 over the RFC 8785 canonical JSON (the canonicalizer of spec 0002 R6) of one object with named fields: a fixed, versioned domain-separator string, the decision kind (activation, rejection, veto, approver-list activation), the target's identity and content hash, the credential ID, the hash of the previous decision, the nonce's issue time and a single-use server nonce that expires within minutes, so neither the chain links nor the times can be rewritten without an approver's key. The nonce is at least 16 bytes from a CSPRNG. The previous-decision hash is SHA-256 over the same canonical encoding of that decision's record, under its own domain separator. The verifier recomputes the expected challenge from the decision's own stored fields, never from a stored challenge, and passes it to the WebAuthn library as the expected challenge, so no client data is parsed in-house; a nonce is accepted once. The slice 3 ADR shows the exact derivation with test vectors.
  - WebAuthn shows the person nothing about what they sign, so the app screen is what tells them. The client computes the content hash itself, with the shared RFC 8785 canonicalizer and WebCrypto SHA-256, over the exact files it renders, never taking a hash from the server; it recomputes the challenge from that hash and the decision's fields and refuses to sign a mismatch.
  - User verification is required on the request and its flag checked. The relying-party ID is the production one and the accepted origins are the production web origin and the registered native app origins (ADR-0006), so an assertion made anywhere else never verifies. The backup flags are recorded with each pinned credential.
- **Database access alone decides nothing.** Approvers and their public keys come from a reviewed, immutable list in the repository, never from the database, and every stored decision is re-verified against those keys before it counts. Decisions are insert-only, enforced by grants as for the audit log, and chained through the signed previous-decision hash. The chain is linear: each decision carries a sequence number, and a second decision on the same previous hash is refused. The chain head is also written, with every decision, to an anchor the database owner role cannot rewrite (for example a write-once object in the separate backup account); state computation compares the two and, on any gap or mismatch, treats every version as not active and raises an alert. An access-matrix case deletes the newest decision and asserts exactly that. The slice 3 ADR defines recovery when a crash leaves a decision in the database but not yet in the anchor, or the reverse; recovery never counts a decision missing from either without a fresh decision.
- **Git access alone changes no approver key.** A change to the approver list takes effect only through a decision by an offline credential already in effect, and a new credential proves possession of its key before it counts. The first list is established by a ceremony a GitHub token holder cannot reproduce: each listed credential signs it from a session of the owner's account on production, and the owner confirms its hash and key fingerprints through the independent notice channel. That bootstrap, and a delayed, notified recovery path when every credential is lost that never rests on Git or email alone, are designed with the rest.
- **A stop is always possible.** Every decision reaches every approver through a channel independent of the account that syncs the approver's passkeys. Activations, rejections and approver-list changes count only after a delay during which any pinned credential of any approver can veto them from the app, including a credential that a list change removes, and the recovery path can also cancel a pending list change; a rejection is delayed too, because it can bring an older version back. A veto is final, and nothing can veto a veto; a vetoed activation or rejection can be submitted again as a new decision. A list change vetoed by a credential of an approver whose credentials it adds, removes or replaces suspends every decision by that approver (fail closed) until the recovery path resolves it; a veto by another approver only cancels the change and suspends no one. So a thief holding one credential cannot win by vetoing or by being vetoed, and cannot suspend another approver.
- **Taking a rule out of use is immediate.** While a rejection of a version is pending, that version is reported to the engine as `proposed`, so the route reads `pending_activation` at once, never the older version.
- **Credentials are tiered, so one stolen credential never gains sole control.** Each approver pins an everyday credential (the phone's passkey) and an offline, device-bound one (a hardware security key, registered with an attestation verified against the FIDO Metadata Service and an allowlist of hardware-key AAGUIDs; its backup-eligible flag must also be false at registration and on every assertion, an extra check only, since the authenticator sets that flag itself). The everyday credential may activate, reject and veto route versions and may veto any approver-list change, its own revocation included. Only the offline credential, or the recovery path, may propose an approver-list change, and a revocation is such a change: a new list version in the repository plus an activation by the offline credential, with a longer window than any rule decision. From the moment a revocation of a credential is proposed, that credential's new and pending activations and rejections stop counting and it keeps only its veto, so a thief cannot keep resubmitting a decision while the longer list window runs; when the revocation takes effect, it cancels the credential's pending decisions. A stolen offline credential is contained only by the recovery path: its list changes can be vetoed, which suspends the approver until recovery. Rotation is a tested path.
- **Code deploys are the open path.** A GitHub token holder who merges and deploys a change to any code, configuration or dependency on the path from the catalog to an evaluation result or a decision (the engine, the API that builds `states`, the decision verifier, the auth and relying-party configuration, dependencies and the build) bypasses every property above, because the passkey checks run in that code. The slice 3 ADR must close that path, with whatever enforces it outside anything a GitHub token holder can change or deploy, or accept it explicitly in its residual risks.
- **The guarantees assume an approver can act within a window.** The windows are sized for that, the approver-list window longest, and the slice 3 ADR states the sizes.
- **No home-made cryptography.** Assertions are verified by a maintained WebAuthn library; there is no parsing or signature code of our own.
- **The engine sees states, not decisions.** The decision states (active, rejected or proposed) are computed by a pure, table-tested function in `packages/domain`, in a module separate from the rules engine, from decisions the API has verified. The engine receives only the resulting state per version.
- **Outside production**, fixture decisions for fixture routes come from a test file that the production build does not bundle. They carry other origins, so the production verifier rejects them.
- **What the owner sees.** The activation screen shows the rule as data, rendered deterministically: its expression tree, its pinned country sets with their members, the diff against the version it replaces, each source's full URL, shown as text rather than a raw link, with new hosts flagged, and whether each source's page hash matches the previous verification, and its rule cases. No model is in the path.

With a single approver, the veto window protects against the owner's own mistakes, and, provided the owner acts within the window, a stolen credential leads at worst to a lockout resolved by the recovery path, never to a rule the owner did not approve; it is not a second opinion. Adding a destination lawyer as an approver is an open question for the owner.

### Research agents: required properties

The research agent and its tools are specified with slice 2. That design must give these properties:

- **Narrow tools.** No shell, no generic GitHub tools, no tool or port that reads case data. A research task carries only public terms and identifiers (country, route ID, requirement key), never snapshot facts, intake text or person IDs.
- **Fetching.** One fetch tool: GET over `https` only, no credentials or cookies, size and count limits per task. It resolves each host before connecting and refuses loopback, private, link-local, unique-local and cloud metadata addresses and names that are not public DNS names; it connects to the address it checked, so a DNS change cannot redirect it, and follows a small number of redirects, each checked the same way. Responses come back only inside a delimited data block, with links and remote images stripped. Every fetch is logged with the proposal: URL, status, time and a hash of the page text.
- **Proposing.** One proposal tool behind a port, `KnowledgeProposalSink`, with a GitHub adapter and a fake for tests. It validates the proposal with the build's schema and reference checks and refuses an invalid one. It accepts a source only if that exact URL was fetched successfully in the same task, and it sets the source's `verifiedAt` from its own clock at fetch time; the model never sets a date. It writes only new route-version and country-set files and their cases files, for the IDs the task names, and appends their `hashes.json` entries, computed by the build's own canonicalizer. It composes the pull request's title and body from identifiers and hashes only (route ID, version numbers, file paths, source hosts, content hashes and the fetch log), never from a free-text field. Free text in the proposal is held to the fetched page's own title for a source title, and refused when it matches instruction-like patterns. It cannot merge and cannot touch official-domain lists, the approver list, workflows or code.
- **Its own credential.** The adapter authenticates as a dedicated GitHub App installation, never a personal token, so its pull requests carry a bot identity distinct from the owner's. Installation tokens are short-lived and minted per task, the App's permissions are contents and pull requests on this repository only, with no workflows permission, its private key is a Production-only secret, and the tool pushes only to branches under a fixed prefix, rate-limited per task. Slice 2 says where the agent runs and adds the GitHub row of the data-flow register for what the runtime sends.
- **Never deciding.** Agents never decide on a version; that needs an approver's passkey.
- **Adversarial cases** in the evaluation suite, each expected to produce only a correctly structured proposal or a refusal: a page with injected instructions, where no free-text field of the proposal may carry text from the page other than its title; a lookalike official host; an attempt to touch the approver list, an official-domain list or a path outside knowledge data; a page targeting a different route; a page asking the agent to fetch a URL that carries task content; a page pointing the agent at an internal or private address; a page that supplies its own verification date; a proposal citing an official-host URL the agent never fetched.

### Trust roots in their own pull requests

Official-domain lists decide what counts as official. The `knowledge-immutable` check fails a pull request that changes them together with any other knowledge data, except an append to `hashes.json` (spec 0002, R6). A host added to a list cites proof on a host already in a merged list version, or on a registry such as a country's domain authority; the first list for an issuer gets its own reviewed pull request. The approver list gets the same rule when slice 3 adds it.

## Alternatives

| Option | Why not |
| --- | --- |
| Route versions as database rows with an in-app editor | An admin editor, review queue and migrations before the first rule exists; no diff review, no tests beside the data |
| Approval by the owner merging the pull request, or by an approving review | Agents act with the owner's token, so neither proves a person approved |
| A code-owner review rule on `packages/knowledge` | Same reason; ADR-0012 also dropped code-owner reviews |
| Signed commits from the owner's own key | Strong, but needs a computer with the key for every rule; the owner works mostly from a phone |
| Verifying decisions against Better Auth's credential table | Anyone with database access could insert a credential; keys pinned in a reviewed file need a reviewed change |
| A source re-verification log outside the content hash | Cheaper to keep fresh, but a merged log entry would change the date users see with no approval |
| Proposed versions expiring after a number of days instead of rejection | Silent, and a bad proposal would still block the route until then |
| Activating country sets separately from routes | Two approvals for one change in meaning; pinning sets inside the route version's hash covers both with one |
| Designing the full decision ceremony now | Nothing uses it before slice 3, and it builds on the foundations' step-up design, which is still being written; the properties above bind it instead |
| Let the AI reviewers approve | Breaks domain rule 5 in CLAUDE.md: a person approves |

## Consequences

- Every rule has a reviewable history in Git, tests beside it, and a reproducible identity.
- The owner activates or rejects each rule once, in the app. The activation screen must make that quick and must show the real rule and its cases, not a model's description of it.
- Keeping sources fresh costs one activation per re-verified version; the diff shows only the changed dates, so the check is quick. Until it is activated, the route reads `pending_activation`, which is the conservative answer. Slice 3 may add a lighter path for an unchanged source if it keeps every date a user sees approved by a person.
- Adding a route stays a data change: a new JSON file and its cases, no code. A route that the schema cannot express extends the schema generically, which is a code change in `packages/domain` with its own review.
- Slice 1 can be built and tested with fixture states and no decisions at all.
- **Residual risk**, in line with ADR-0012: an agent holding the owner's GitHub token can merge a bad proposal or change code, including the future decision code. Merged versions stay proposed, so a bad data proposal still needs a person's passkey before it reaches anyone; a merged and deployed change to code on the decision or evaluation path does not, until the slice 3 ADR closes or accepts that path (above). Someone with the database owner credentials can delete decision rows; the anchored chain head required above is what turns that into a detected outage rather than a wrong rule, and until slice 3 proves it, it is an open risk of that design, not a guarantee.
