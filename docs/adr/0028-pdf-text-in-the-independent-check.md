# ADR-0028: The independent check reads a PDF's text layer with pdf.js

- Status: Accepted, amended 2026-11-12 (a PDF's own byte cap, under Caps)
- Date: 2026-11-11
- Issue: [#363](https://github.com/fernandolisboa/arca/issues/363) (spec [#351](https://github.com/fernandolisboa/arca/issues/351))
- Amends: [ADR-0027](0027-admins-and-the-checked-batch-activation.md) (what the check reads); [ADR-0010](0010-stack-revised.md) (one dependency outside the stack)

## Context

Many official texts exist only as PDFs: Portugal's Diário da República, Poland's Journal of Laws through the Sejm's ELI API, Iceland's gazette, Irish statutory instruments before their HTML form, policy documents. The independent check refused every `application/pdf` answer, so the items resting on them could not be checked. On 2026-11-11 the knowledge data named 33 distinct PDF addresses (18 of them in route versions), and the Portuguese routes had 1 of 46 items matching after their audit, every other one could not be checked.

## Decision

- The check reads an `application/pdf` answer as the text of its pages, in order, through **pdf.js** (`pdfjs-dist`, Mozilla), its Node build, in `apps/api/src/knowledge/check/pdf-text.ts`. Each text item is appended as it comes and a line ends where pdf.js says one does; pages are a blank line apart. From there the text is a page's text: the same caps, the same passages for a long one, the same quote and value checks. No prompt changes.
- **Bytes in, text out.** pdf.js gets the bytes the fetcher already received under its byte and decompression caps, never a URL. It fetches no fonts, character maps or WebAssembly, uses no system fonts or canvas, and reads no forms (XFA), annotations, links, attachments or scripts: only `getTextContent` is called. pdf.js 6 has no code path that compiles code from a file (the `isEvalSupported` switch behind CVE-2024-4367 is gone). Text inside optional content that a page's content stream marks is left out when the file switches any layer off, since pdf.js does not say which layer a mark belongs to; pdf.js does not apply a drawn form's own layer to its text, so that text stays, like the other hidden text below. The thread gets no environment variables, so a flaw in pdf.js reaches none of the process's secrets.
- **A thread of its own.** pdf.js parses as one unbroken chain of promise work, so no timer in the same thread can interrupt it: the reviewers measured a 2 KB file of nested drawings that held the event loop for 84 seconds and a 389 KB stream that inflated to 400 MB. Each file is therefore read in a `worker_threads` thread, which pdf.js runs its own worker inside, handed over as a module. The thread gets a copy of the bytes and the addresses of the library and its worker; its module is `extractPdfText` as compiled, so it is the reviewed function, with the two helpers a bundler or the test runner may insert defined as what they stand for. The caller terminates the thread when the fetch's time limit passes (`timeout`), when its heap passes 256 MB, or when the process's resident memory grows by more than 512 MB while it reads (`too_large`): an inflated stream lives outside the heap, so the process's memory is watched every 25 ms, and growth from other work counts too, which fails safe. Starting a thread and loading pdf.js costs about 0.3 seconds a file. pdf.js's console output stays in the thread.
- **Caps.** A PDF has a byte cap of its own, 16 MB received and after decompression, in place of a page's 3 MB and 6 MB (amended 2026-11-12; a page's are 8 MB and 10 MB since 2026-11-14): a gazette embeds its fonts, so the 136-page Portuguese foreigners law, republished by Lei n.º 18/2022, is 12 MB for 445,000 characters of text, which pdf.js reads in under two seconds and about 120 MB. The thread's heap and memory watch bound what the file inflates to, whatever its size. At most 400 pages; a longer file is `too_large`, as a body past the byte cap is. Reading stops at the first page that takes the text past the text cap, and the text is cut there and marked cut, as a long page's is.
- **Vertical text** (amended 2026-11-12). pdf.js ends a line after each glyph of a vertical column, as Japanese notices are set, so a run of lines that each hold one Han, kana or Hangul character (or a full-width mark) is joined back into one line after reading; other text is unchanged. Before, the Nikkei notice reached the model one character per line and no quote could be copied from it.
- **Reasons.** A file pdf.js cannot open is `pdf_unreadable`; one whose pages carry no text, such as a scan, is `pdf_no_text`. Both are fetch failures like any other: the step completes and the items citing the file could not be checked, with the reason shown.
- **The dependency.** `pdfjs-dist` 6.5.438: maintained by Mozilla, published with npm provenance from the project's own repository, no dependencies, no install scripts, Apache-2.0. Its one optional dependency, `@napi-rs/canvas`, is native code for rendering; `ignoredOptionalDependencies` keeps it out of the install, and a test fails if it ever becomes resolvable from pdf.js, which tries to load it on import. The package also ships WebAssembly decoders, fonts and character maps; none is loaded with these options, and Nitro ships the package beside the bundle (`traceDeps`), since the thread imports it by path, which adds about 38 MB to the server output; only the library and its worker are ever loaded.
- **Evaluation:** three cases join the suite: a correct version whose act is read through the gazette's PDF, an adversarial one whose PDF carries a visible line telling automated reviewers to report a match, and one whose PDF draws that instruction and a wrong amount in invisible text. That makes 36 cases (10 correct, 6 wrong, 20 adversarial); the bar is 9 of the 10 correct ones checked, and the cap rises to 90 calls. The workflow-step tests read synthetic PDFs through the real fetcher: one with text, a scan, a malformed file and files over the page and byte caps; `pdf-text.test.ts` reads a file of nested drawings that must stop at the time limit and a stream that inflates past the memory bound.
- A sourced value the check now reads from a PDF needs no new version: the cited addresses do not change. A rule audit may now name a PDF as a source's `machineReadableUrl`.

## Alternatives

| Option | Why not |
| --- | --- |
| Send the PDF to the model as a document | ADR-0027 refuses it: the quotes are checked in code against the text the server read, and a model that reads the file itself gives text the code cannot see |
| `unpdf` | A repackaged pdf.js from a third party; its provenance attests that build, not Mozilla's, and its fixes arrive after pdf.js's |
| `pdf-parse` | Wraps pdf.js too, with its own release cadence and fewer maintainers |
| `pdftotext` (Poppler) | Native code and a binary to ship to the function |
| A parser of our own | No home-made parsing of a format this large; the text layer depends on font encodings and content streams |
| Reading PDFs on the request's own thread | First proposed; the review showed a small hostile file stalls it with no timer able to fire, and with Fluid compute that stalls every step sharing the instance |
| Another process | A thread gives the same stop with less to ship and start; a process would also bound inflated streams exactly, which the memory watch does approximately |
| Accepting `application/octet-stream` as a PDF | Some gazettes serve downloads that way; it stays refused, so a file is read as a PDF only when its server says it is one |

## Consequences

- The Portuguese, Polish and Icelandic gazette texts, and other PDFs on official hosts, can confirm items.
- A text layer reads in the order the file draws it: multi-column pages and tables can come out interleaved, so some items still come back read and not confirmed. A file whose text uses fonts without a Unicode map (some East Asian PDFs, which need character maps the check does not load) gives text that does not match, and its items could not be checked.
- pdf.js prints a warning on load that it found no canvas; it is harmless, since nothing is rendered, and stays in the thread.
- Unlike a page's markup, a PDF can hide text from a reader in ways its text layer keeps: invisible rendering (which a scan's OCR layer uses, so it cannot be dropped), white on white, text clipped away or covered, and wording struck through by a drawn line or an annotation. That text reaches the model and a quote on it passes the quote check, as text a style sheet hides on a page does (ADR-0027); the model's judgment and the admin's tap stand against it, and an evaluation case plants such an instruction. A rule audit names a PDF as a machine-readable address only when it is an original or consolidated text with no struck wording.
- **Residual risks, accepted:** the memory watch looks every 25 ms, so a stream that inflates faster could pass the bound by what it inflates in that time before the thread is stopped; pdf.js inflates in JavaScript, at a few hundred megabytes a second. Each read watches the whole process from its own start, so two reads that overlap on one instance could together pass the bound, and a legitimate file read while other work grows the process is too large; the checks of one version fetch one page at a time. pdf.js is a large parser of hostile input; its updates follow Dependabot and the minimum release age like any dependency's, so a security fix waits up to a week unless the owner exempts that version.
