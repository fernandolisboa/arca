# ADR-0006: Authentication with Better Auth and passkeys

- Status: Accepted; enrollment, step-up mechanics, recovery details, the timing of native sessions and the production relying-party ID amended by [ADR-0015](0015-identity-enrollment-step-up-and-recovery.md); step-up extended to knowledge-base decisions by [ADR-0014](0014-knowledge-base-as-reviewed-data.md), which verifies them against keys pinned in the repository (designed with consultancy core slice 3)
- Date: 2026-11-01 (revised after review: native passkeys, recovery, storage)

## Context

- Users are families, including older relatives; passwords are a weak point and a support burden.
- The same identity must work on the web, in Capacitor apps on Android and iOS, and possibly on desktop ([ADR-0005](0005-platform-strategy.md)).
- Identity data should live in our own database, in Brazil.
- Rolling our own authentication is not acceptable.

## Decision

- **Better Auth**, self-hosted inside the API, storing users, sessions and passkeys in our Postgres under the `app_auth` role ([ADR-0008](0008-database-security-and-environments.md)).
- **Passkeys as the only first-class login**, through the `@better-auth/passkey` plugin (SimpleWebAuthn). The relying-party ID is the production host from day one.
- **Native apps use native passkey APIs**, not WebAuthn inside the WebView: the Capacitor WebView runs on a `localhost` origin that cannot match the relying-party ID. A native plugin behind the `platform` port calls Android Credential Manager and Apple's passkey APIs. The app is linked to the domain through Digital Asset Links and Associated Domains, and the server accepts the Android app origin (`android:apk-key-hash:<hash>`) alongside the web origin.
- **Sessions:** cookies on the web; on native apps, the bearer plugin returns a session token kept in the Keychain or Android Keystore. Capacitor origins are trusted origins, and CORS exposes the token header.
- **Step-up:** opening the vault, financial actions and changes to security settings require a fresh passkey verification.
- **Recovery never rests on email alone**, because that would make the inbox the master key. Recovering access requires the email link plus one of: a recovery code issued at enrollment (shown once, kept offline), another passkey the person already registered, or approval from another adult in the case the person designated in advance. A new passkey from recovery activates only after a delay, with alerts to every registered device and the email address. Vault key recovery follows [ADR-0018](0018-vault-encryption.md).
- **Rate limiting** uses shared storage (the database), never in-memory state, because serverless instances do not share memory.
- No social login in the MVP. If added later, check each store's login requirements first.

## Consequences

- No passwords to leak, phish or reset.
- Auth is a library we configure; its configuration is security-critical code with a must-pass security review.
- Better Auth is younger than managed providers: versions are pinned, advisories are tracked (Dependabot alerts and osv-scanner), and auth stays behind our API so it can be replaced.
