# ADR-0015: Identity: invite-only enrollment, purpose-bound step-up and recovery

- Status: Accepted
- Date: 2026-11-02
- Amends: [ADR-0006](0006-auth.md) (enrollment, step-up mechanics, recovery details, session transport timing), [ADR-0005](0005-platform-strategy.md) and [ADR-0010](0010-stack-revised.md) (native bearer tokens move to Phase 4)
- Spec: [0003 identity and access](../specs/0003-identity-and-access.md)

## Context

ADR-0006 chose Better Auth with passkeys only, step-up for sensitive actions and recovery that never rests on email alone. Building it raises questions ADR-0006 left open:

- **Who may create an account.** Until Phase 3, Arca serves one family. Open sign-up would let anyone on the internet create accounts, store data and spend AI budget.
- **The first account.** Someone has to become the first user of an empty production database without an operator touching it, and before any invite exists.
- **Step-up bound to what it approves.** A step-up that proves only "someone verified recently" can be spent on another action by whoever shares the session. Some approvals must also be provable later: knowledge-base decisions (ADR-0014, proposed in pull request #39) will need a person's passkey step-up bound to a content hash, re-verifiable against keys pinned outside the database. Their purposes, tables and ceremony come in their own spec and ADR after this one; this ADR only provides the purpose-bound step-up they will consume. Better Auth's passkey plugin issues its own challenges for sign-in only.
- **The relying-party ID.** Passkeys are bound to it. Production uses the production domain, which is not registered yet. `vercel.app` is on the [Public Suffix List](https://publicsuffix.org/list/public_suffix_list.dat) (checked 2026-11-01 for ADR-0010), so previews cannot share one relying-party ID.
- **Identity name.** The request identity in the database is `app.person_id` (spec 0001, R7). A case holds people who never sign in (children, a grandparent described by a relative), so the signed-in identity is an account, not a case person.
- **Native sessions.** ADR-0006 asks for bearer tokens on native apps. No native app exists until Phase 4.

Facts checked on 2026-11-02:

- `better-auth` and `@better-auth/passkey` 1.7.15 are the latest; the passkey plugin supports passkey-first registration (`registration.requireSession: false` with a `resolveUser` callback that receives an opaque context), and server-defined WebAuthn extensions at registration and authentication ([Better Auth passkey plugin](https://better-auth.com/docs/plugins/passkey)).
- The passkey plugin 1.7.15 depends on `@simplewebauthn/server` `^13.3.2` and `@simplewebauthn/browser` `^13.3.0`; 14.x is the latest major (npm registry). Our step-up uses the same 13.x copy the plugin resolves, so one WebAuthn verifier runs, until the plugin moves to 14.
- PRF is supported by Google Password Manager passkeys, iCloud Keychain (Safari 18 and later, iOS 18.4 and later without the earlier data-loss bugs) and Windows Hello on recent Windows 11; support is still incomplete, so PRF is an enhancement with a recovery path ([Corbado](https://www.corbado.com/blog/passkeys-prf-webauthn)).
- Resend sends from São Paulo (`sa-east-1`) when the domain is added with that region; account data, logs and email metadata are stored in the United States whatever the region ([Resend: choosing a region](https://resend.com/docs/dashboard/domains/regions)).

## Decision

### Accounts and request identity

- An **account** is a Better Auth user: an email address, one or more passkeys, sessions. Its ID is a UUID generated by the database driver configuration, never by Better Auth's default string IDs.
- The request identity setting is renamed from `app.person_id` to `app.account_id`. Case persons (slice 3 of the consultancy core) carry an optional `account_id`; access policies read the account, then the case membership.
- Better Auth tables live in their own schema, `auth`, owned by `app_migrator`, read and written by `app_auth` through its own pool. They are on the guard allow-list for tables without row-level security, as ADR-0008 planned. One other grant exists: `app_backup` reads the tables worth restoring ([ADR-0017](0017-data-lifecycle-and-backups.md)); workflow steps that touch `auth` (retention, deletion) run their transaction on the `app_auth` pool, so `app_jobs` has no privilege there. One repository module in `apps/api` is the only code that reads the plugin's credential rows, so a plugin schema change touches one file.
- Better Auth's telemetry is disabled in configuration, asserted by a test, so a changed default cannot add an unregistered processor.

### Enrollment is invite-only

- Sign-up is closed. An account is created only by accepting an invite, or by the owner enrollment below.
- **Invites** are created by an existing account (every account is an adult; children are case persons without accounts), bound to one email address, single-use, valid for 48 hours, stored as a SHA-256 hash of a 256-bit random token. The invite link is sent by email only, so accepting it proves the address that recovery relies on. Accepting it starts passkey-first registration with the token as the passkey plugin's registration context. The new account is linked to its inviter (the `account.link` that lets two accounts find each other's vault recipient) only after the inviter confirms it in the app, seeing its email and recipient fingerprint, with a `sensitive_settings` step-up; the confirm screen asks the inviter to compare the fingerprint with the invited person directly, since the email alone would look the same to an impostor. Resend keeps message content; turning that off needs its $50-a-month add-on and a sending history Arca will not have (checked 2026-11-02), so the residual is accepted: someone reading Resend's copy within 48 hours could create an account for that address, which the inviter is notified of. Until the inviter confirms it, an invited account is restricted: it cannot invite, create a case, upload or share documents, or trigger model calls (it may create its vault identity, so the inviter can compare the fingerprint); if the inviter declines it, or 30 days pass without confirmation, it is erased through the registry and its address is free again.
- **Owner enrollment.** The first account of an empty database is created with a one-time enrollment code. The owner runs one repository script locally (`pnpm enrollment-code`), which prints a 128-bit CSPRNG code and its SHA-256 hash; the owner keeps the code and gives only the hash to an agent, which commits it to a repository file. The code never enters a model, an issue, a pull request, a commit or a log. The passkey registration that completes enrollment sends the code again, and `resolveUser` checks its hash, so the verification email alone (which Resend keeps) cannot complete enrollment. The endpoint accepts the code only while the database holds no account **and** the code has never been used: a successful enrollment records the code's hash in `auth.setup` (its primary key, inserted first in the enrolling transaction, so two concurrent enrollments cannot both succeed), a table that erasure and retention never touch and that backups include. An empty user table therefore does not revive an old code (after the only account is erased, or in a restored branch); enrolling again needs a new code, whose hash lands by a reviewed change.
- No social login, no passwords, no magic-link sign-in.

### Sessions

- Web sessions are Better Auth cookie sessions: `__Host-` prefix, `Secure`, `HttpOnly`, `SameSite=Lax`, an idle timeout of 3 days and an absolute lifetime of 30 days, after which the person signs in again. The trade-off: family members return every few days, a passkey sign-in costs one touch, and everything that changes the account or reaches documents needs a fresh step-up, so a session alone reads case data but cannot change credentials or open the vault. Shorter idle timeouts are revisited if sign-in telemetry shows the cost is low.
- Each session records the credential that signed it in. Revoking a passkey revokes every session it created, in the same action.
- Better Auth's origin check stays on; the trusted origins are the environment's own origin only.
- Sign-in requires user verification; the server rejects assertions without the UV flag.
- **Adding a passkey** to an account that already has one needs a step-up, and the new passkey can neither sign in nor satisfy a step-up for 24 hours, during which an older active passkey can cancel it with a step-up, every session shows a banner, and notices go out. A stolen session therefore cannot plant a passkey that defeats step-up.
- Changing the email address is not offered; when it is, it needs a step-up, confirmation at both addresses and a notice to the old one.
- A session records a coarse device description derived on the server as two closed enums (browser family, operating system family), rendered through i18n, never the raw user agent, and no IP address. The device list shows passkeys with the sessions each signed in; each can be revoked.
- **Bearer tokens for native apps are deferred to Phase 4.** Nothing in this design blocks them: Better Auth's bearer plugin is configuration, and the API contract carries no cookie assumption.

### Step-up is a purpose-bound ceremony of our own

The step-by-step procedure, encodings and tests are normative in [spec 0003](../specs/0003-identity-and-access.md) R5; this section records the decision and the guarantees it must keep.

- Step-up uses `@simplewebauthn/server` directly (a direct catalog dependency of `apps/api`, pinned to the version the passkey plugin resolves, with a lockfile check that only one copy exists), against the passkeys Better Auth stores, so the challenge can be bound to the action:
  - `POST /v1/auth/step-up/options` takes a purpose from a closed enum and the action's target; the server computes the 32-byte subject hash itself. For the account purposes it is SHA-256 over the canonical action: the route, the target IDs (the passkey or session being revoked, the deletion request), a hash of the security-relevant body fields where there are any (new bank details, an amount) and an action nonce the client generates and later sends with the action itself. `vault_unlock` carries no subject (an empty field).
  - The server draws a 32-byte nonce and sets the challenge to SHA-256 over four fields, each prefixed with its length as 4 bytes big-endian: the ASCII tag `arca-step-up/v1`, the purpose in UTF-8, the raw subject hash and the raw nonce. A test vector is committed with the implementation. The challenge row lives in `auth.step_up_challenge` (written by `app_auth`), expires after 2 minutes, and is consumed with `DELETE … RETURNING` before verification; issuing and submitting are rate-limited in Postgres.
  - The challenge row stores the session and account that requested it. `POST /v1/auth/step-up/verify` accepts it only from that session and only with an active credential of that account, and checks the assertion against the stored challenge, the relying-party ID, the origin, user presence and user verification, rejects revoked credentials, and updates the signature counter.
  - The verified assertion (session ID, credential ID, authenticator data, client data JSON, signature, purpose, subject hash, nonce, time) is stored, so a consumer can verify it again later; a consumer may copy the assertion into its own record. Re-verification takes the public key from the caller, so a consumer that must not trust the database (such as future knowledge-base decisions, with keys pinned in the repository) cannot be fooled by a credential inserted by someone holding the owner connection. The signature counter is checked once, at verification, never on re-verification.
- Purposes start as: `sensitive_settings`, `account_deletion`, `data_export`, `financial_action`, `vault_unlock` and `vault_write` (replacing or deleting a batch of documents; its subject is the account-purpose canonical action, with the ordered document IDs as targets and the new objects' SHA-256 values as the security-relevant body, so an open `vault_unlock` window cannot be spent on writes). Knowledge-base decisions will add their own purposes in their own spec. A new purpose is a reviewed code change.
- **Every step-up is single use:** the route recomputes the subject from the request it is serving and consumes, atomically, the one step-up of that purpose and subject verified by the same session within 5 minutes. A step-up approved for one action cannot be spent on another. Revoking three passkeys means three verifications. The one exception is `vault_unlock`, below.
- Re-verification never reads purpose or subject from the stored row: the consumer passes the purpose and subject it expects, with the public key.
- A `vault_unlock` step-up is fresh for 15 minutes and gates the vault's envelopes and download URLs; the PRF ceremony that then opens the identity runs on the device ([ADR-0018](0018-vault-encryption.md)). Login passkeys are registered with the PRF extension enabled so they can serve both.

### Relying party per environment

- Production uses the production domain as relying-party ID, set in a repository configuration file. Until that file names a domain, production refuses every registration and enrollment, so no passkey is ever bound to a temporary host.
- A preview uses its branch URL host as relying-party ID and rejects ceremonies from any other origin. Preview passkeys are throwaway, like preview data.

### Recovery

- A passkey registered through recovery, or added while another is pending, yields no session: any session the registration ceremony creates is revoked in the same transaction, and sign-in with a pending credential is refused on the server.
- Recovery needs the email link **and** the recovery code. The code is 128 bits of randomness shown once at enrollment as a printable kit, stored as SHA-256 over a per-account salt and the code, and **consumed the moment it is accepted** (recovery cannot start again while a recovery passkey is pending), in exchange for a single-use registration context valid for the rest of the link's 30 minutes, so a failed passkey ceremony can be retried, and a new account recovery code, shown at that moment, before the ceremony, so a lost tab never leaves the account without one (the vault part follows the order in spec 0003 R6 at the first unlock).
- Registering the recovery passkey puts every existing session of the account into a restricted state for the 24 hours, with a notice (the `recovery completed` event and notice mark this moment): a restricted session shows the pending-recovery banner and can cancel it with a step-up, and nothing else, so the rightful person sees the warning on their own devices without a thief's session reading data. When the passkey activates, every restricted session is revoked (the `passkey activated` event). A device someone else holds can cancel, as any active passkey already could; that is the price of a visible warning.
- A passkey registered through recovery is inactive for 24 hours. During that time another active passkey of the account can cancel it with a `sensitive_settings` step-up; every session shows a banner while it is pending, and a security notice goes to the email address and every device. A cancelled recovery also invalidates the code it issued and closes recovery for the account until the person generates a new kit, which every session shows.
- **Accepted residual: one active passkey controls the account.** Someone holding an unlocked device and able to pass its user verification can, with step-ups, revoke the other passkeys, regenerate the kit and cancel a recovery, leaving the rightful person no way back. Each of those sends a security notice to the email and every device, and the device list tells a person who lost a device to revoke it before anything else. The planned mitigation is the designated adult as a second factor for these actions, reviewed before the real-data gate (OPEN-QUESTIONS).
- "Another passkey the person already registered" (ADR-0006) needs no recovery: that passkey signs in. "Approval from another adult in the case the person designated in advance" waits for the case model and is specified with it.
- Recovering the vault follows [ADR-0018](0018-vault-encryption.md). The recovery kit has two parts: the account part (the recovery code) shown at enrollment, and the vault part (the vault recovery secret) shown when the vault is created, only after the recovery envelope is sealed and opened once as a check, so no one ever types a printed secret back in to seal it.

### Security notices and audit

- Security events (sign-in, new passkey, passkey or session revoked, recovery started or completed, step-up, invite created, accepted, confirmed or declined, deletion requested (with its reason) or cancelled, export) go to an append-only audit log written by `app_audit` and readable by the account it concerns. Each record carries identifiers and an event code, never names, emails or free text.
- A new passkey, a sign-in from a browser or system family not seen before for that passkey, a revoked passkey, a cancelled pending passkey, a regenerated recovery kit, a recovery and a deletion request also send a security notice by email and, once notifications exist ([spec 0005](../specs/0005-vault-devices-and-notifications.md)), to every device. Notices say what happened and when, without location or device details beyond the device description.

### Email

- Resend sends from the production domain with the sending region set to São Paulo. Messages carry a link and generic text. Link tokens (invite, enrollment, recovery) travel only in the URL fragment: the web app reads the fragment and sends the token in a POST body, and the API accepts these tokens in no path or query parameter, so they never reach request logs, history or a `Referer`; the data-flow register records that Resend stores recipient addresses and metadata in the United States.
- Non-production environments never send email. Their sender writes to an outbox table that a preview-only page shows, behind Vercel Deployment Protection. The table exists in every environment, so schemas never diverge; production refuses to select the outbox adapter.
- Resend is called through its REST API with `fetch`, with no SDK package.

### Rate limiting

- Better Auth's rate limiter with database storage on every auth endpoint, plus our own limits on the step-up, invite and enrollment endpoints, stored in Postgres.
- An edge rate-limit rule on `/v1/auth/*` in Vercel Firewall.

## Alternatives

| Option | Why not |
| --- | --- |
| Open sign-up with email verification | Anyone could create accounts and spend AI budget; not needed until Phase 3 |
| First account claimed by whoever signs up first on an empty production | A public URL makes it a race |
| Owner enrollment through a Sensitive Vercel variable | The owner would have to create it by hand, or an agent would have to write and then disclose a secret it cannot read back |
| Step-up through Better Auth's sign-in endpoint | Its challenge is random and cannot carry app data, and it creates a session rather than proving an action |
| Recovery by email link alone | ADR-0006: the inbox would become the master key |
| Bearer plugin enabled now | No native client exists; an unused token path is attack surface |

## Consequences

- Production cannot have users until the domain is registered and set; previews can.
- Owner enrollment depends on the owner running `pnpm enrollment-code` once and keeping the code.
- Step-up and its stored assertions are security-critical code with must-pass security and auth-and-cryptography reviews.
- The `app.person_id` rename touches the identity helper, the pool's connection check and their tests.
- Losing both the passkeys and the recovery kit locks the person out; the designated-adult factor reduces that once the case model exists.
