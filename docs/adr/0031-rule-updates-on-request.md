# ADR-0031: Rule updates on request, in two rounds, with rules in the database

- Status: Accepted
- Date: 2026-11-16
- Spec: [#455](https://github.com/fernandolisboa/arca/issues/455)
- Supersedes: [ADR-0029](0029-correction-requests-and-the-corrector-session.md) (the corrector run, its key and its trigger; the correction request becomes the update request)
- Amends: [ADR-0002](0002-rules-as-versioned-data.md) and [ADR-0014](0014-knowledge-base-as-reviewed-data.md) (where the base lives; how a version is proposed; how a first official-domain list is trusted); [ADR-0027](0027-admins-and-the-checked-batch-activation.md) (the independent check, its starts, country guides, the checked batch, the audit loop and the catalog check; activation takes a step-up again); [ADR-0025](0025-rule-summary-for-the-approver.md) (summaries read versions from the database); [ADR-0004](0004-ai-providers-behind-ports.md) (two ports; the key and the model come from settings; rule data and page text may be cached); [ADR-0006](0006-auth.md) and [ADR-0015](0015-identity-enrollment-step-up-and-recovery.md) (the `ai_key` step-up purpose; `knowledge_decision` offered again); [ADR-0008](0008-database-security-and-environments.md) (rule, request and settings tables, their roles, a secret in the database); [ADR-0009](0009-background-jobs-guarantees.md) (an update request's ID as a workflow argument); [ADR-0021](0021-stay-on-vercel-and-neon.md) (rule history lives in the database; members' files in the Blob store); [ADR-0028](0028-pdf-text-in-the-independent-check.md) (its PDF reading serves the quote check); [ARCHITECTURE.md](../ARCHITECTURE.md); CLAUDE.md (where rules live, how a rule changes)

## Context

Route versions live as JSON files in the repository, so every fix is a Claude Code session, a pull request, six to ten reviewers and a deploy. On top of that, the independent check re-read every proposed version whenever its prompt changed (eight prompt versions, `rule-check-1` to `rule-check-8`, from 2026-11-07 to 2026-11-15), an hourly cron re-checked them, and a daily corrector routine on claude.ai turned each "Difere" or "Confira" into another version. The check was unstable (the owner saw 5 of 8 production "differs" match in CI on the same rule), and "Tudo bate" required every item matched while about 40% of items sit on pages the checker cannot read, so the loop had no fixed point. By 2026-11-15 it had spent, by the owner's account, more than US$230 of API credit plus subscription usage; the credit ran out and took the owner's other apps down with it; some versions were corrected about ten times with the same problems returning.

The owner asked on 2026-11-16 for something simple: gather a country's requirements per visa, have a second agent validate them, fix once, validate again, approve, use; at most two rounds; no external routine and no AI cron; everything run and configured from inside the app. He approved the plan the same day in the project thread, including moving rules out of the repository (in his words, in pt-BR, "nunca fez sentido no repositório"), and rejected spend caps ("sou só eu"): the fixed number of rounds is the bound. The first step, removing every automatic check start, shipped in [#454](https://github.com/fernandolisboa/arca/pull/454).

## Decision

### Rules live in the database

- Route versions, country sets and official-domain lists become insert-only rows in the `knowledge` schema, keyed by ID and number, each with its content, its content hash (computed in code with the existing canonical hashing, spec 0002 R6) and, for a route version, its rule cases. No runtime role holds update or delete on them. Decisions (activate, reject) stay in `knowledge.decision`, bound to the content hash.
- **Reading re-checks the hash.** The API recomputes each row's content hash when it reads it and refuses a row whose hash differs from the stored one or from the hash its decision names, so a row changed outside the insert-only grants (for example with the owner connection, which bypasses them) is never evaluated.
- The repository keeps the engine, the rule schema, the country dataset (CLDR and former states) and fixture routes for tests. It stops receiving route versions once the import lands.
- **Import.** A one-time, idempotent data migration, run by the build's migration step like any migration ([ADR-0012](0012-automation-first-setup.md)), loads every bundled version, country set and official-domain list with its existing hash; a hash mismatch aborts the whole import. It writes no decision and no state: states stay computed from `knowledge.decision` as before (ADR-0022 rows re-verified, ADR-0027 rows counted by their basis), so the move keeps every active, proposed and rejected state and cannot launder a decision row. Old evaluations keep naming the route, number and hash they used, so they stay reproducible.
- **Selection** keeps its pure functions in `packages/domain`; the API feeds them versions read from the database instead of the bundled catalog, and the API bundle stops shipping route data.
- **As built ([#457](https://github.com/fernandolisboa/arca/issues/457)).** Official-domain lists had no hash before; each got its first one at import, over its content with no pins. A refused row withholds every version of its route, so selection never falls back to a version the refused one superseded or corrected; the refusal is logged by error name only. The API re-reads the rows only when their counts change, so a row changed in place keeps serving the content already verified until the next cold start, which refuses it. A route version's rule cases sit beside its content, outside its hash: today only the migrator writes them, but before [#459](https://github.com/fernandolisboa/arca/issues/459) lets another role insert rows, the cases must be bound to a hash the read re-checks, since the admin reads them before approving.

### Roles

Following [ADR-0008](0008-database-security-and-environments.md): `app_jobs` inserts a pipeline's stage results and proposals under no account; `app_api` inserts requests and an admin's edited version through reviewed `SECURITY DEFINER` functions owned by `knowledge_definer`, each re-checking the admin basis as ADR-0027 computes it; `app_auth` inserts decisions and settings changes after a spent step-up. A member's request is personal data: row-level security lets its author read their own requests and admins read all, and it joins the personal-data registry for erasure and export. The access-matrix suite covers every table and function for each role.

### An update request, never an automatic run

- **Update request** (UI "Pedido de atualização") replaces the correction request. An admin asks for one route ("Pedir atualização"), or for a new route of one country by naming the visa or entry type. A member may ask for the route they are looking at, with an optional note, links and a file; their request waits until an admin releases it, and only a released request starts anything. A member sees received, released, finished or declined.
- **What reaches a model.** No free text from any request reaches a model: not a member's or an admin's note, nor a file. A request's links feed research only when they sit on the route's approved official-domain list, and only as addresses. Everything else is for the admin to read; an admin who finds an official page in a member's note re-enters it in their own request. So a member's words never leave Arca, and a planted instruction in a note cannot steer research.
- **Files.** A member's or admin's file goes to the private Blob store under the existing `corrections/` prefix, with the upload checks, the attachment-only download and the retention ADR-0029 set for request files (erased 30 days after the request ends, or 180 days after it was filed), now covering members' uploads; erasure and export follow the author's account. The form asks for copies of official pages only, never personal documents, and only owner-list admins can download a member's file; a member who attaches a personal document anyway leaves a plaintext copy for up to 180 days, a residual the owner accepts, recorded in the threat model's vendor-compromise row.
- **One live request per route**, and for a new route one per country, so two clicks never pay twice. A new request for a route or country with one already running is refused.
- **Nothing runs by itself.** No request starts on a prompt or model change, on a timer, or when a screen opens. There is no claude.ai routine, no corrector key and no AI cron.

### The pipeline, bounded at two rounds

One Vercel Workflow per request, whose argument is the request's ID and whose step inputs and outputs are identifiers only ([ADR-0009](0009-background-jobs-guarantees.md)): each stage writes its result to the database and returns its ID. A pure controller in `packages/domain` picks the next stage from the stored stage results and enforces the bound: **research → validation → at most one correction → final validation → done**. Any failure (provider down, timeout, an answer that does not parse) ends the request with a fixed code and no proposal, and nothing retries it on its own.

- **Research.** The research model, through a `RuleResearcher` port, with Anthropic's web search and web fetch server tools limited to the route's approved official-domain list, answers in the rule schema through structured output: every item with its source URL and the quoted passage, plus rule cases. Its input is the route's ID, its current version, its official-domain list and the request's qualifying links: public data and identifiers only. Whether the tools' domain limit also admits subdomains is checked against Anthropic's documentation when the adapter is built ([#459](https://github.com/fernandolisboa/arca/issues/459)); either way, Arca's own host matching decides what counts as official.
- **Checks in code, between stages.** Schema validation; every official source's host on an approved official-domain list, by Arca's own matching; the existing SSRF-safe fetcher (with the PDF text layer of [ADR-0028](0028-pdf-text-in-the-independent-check.md)) reads each cited page and verifies that each quote is a verbatim substring and carries the item's value, with the existing quote and value checks; `verifiedAt` set from the code's clock when the page was read, never by a model; the engine runs the proposal's rule cases, and the coverage rule of spec 0002 R8 (every requirement exercised every way) holds. An item whose quote is not on its page is marked by code, never by a model, so a fabricated quote cannot read as confirmed. The floors ADR-0014 set for research still hold where they apply: public terms and identifiers only, never case data; fetches by GET over `https` with size and count limits through the guarded fetcher; never deciding; evaluation cases with known-wrong, correct and adversarial versions ([#465](https://github.com/fernandolisboa/arca/issues/465)).
- **Validation.** A `RuleValidator` port on a model other than research's (settings refuse the same model for both) receives each item with its verified quote, not whole laws and not a passage locator, and answers per item only *supports*, *does not support* or *cannot tell*, with a short reason.
- **Correction.** Only the items the validator rejected or code failed, with their reasons, go back to the research model, with the same tools and limits.
- **Final validation.** Only the corrected items.
- **The result** is a proposed version with three lists for the admin: confirmed items; divergent items with the reason; items nobody could confirm, with their official links. Items that could not be confirmed are information, never a reason for another round.

### A new country's first official-domain list

Research cannot write the list it is limited to. For a new route in a country with no approved list:

- The admin names, in the request, the official hosts to start from; research runs limited to them, and may propose more.
- Every host of the proposed list cites a registry page (the country's domain authority, or an official directory of its public bodies) that sits on a host the admin named or on an already approved list; code fetches that page and checks the host appears on it, as spec 0002 R6 asks of a first list. A list that cites itself as proof, or that holds a registry suffix such as a whole top-level domain, is refused.
- The proposed list is shown apart, host by host with its registry proof, and decided on its own before the route: until it is approved, every item resting on its hosts sits under "Não confirmados", and the fetcher treats its hosts as unapproved, except that hosts the admin named may be fetched for the registry check.
- A request on an existing country never widens its approved list: a new host goes through a new list version the admin approves on its own.

### Review, approval and editing

- The activation screen shows a request's proposal as the three lists, each item with its source and quote.
- **Approval with a passkey.** As the spec asks, every new decision takes a step-up of the `knowledge_decision` purpose bound to the subject's content hash: activating or rejecting any route version (imported, proposed, hand-edited, or an active one being rejected), any official-domain list version (a new subject kind) and any comparison version, so no decision path is left on a session alone. ADR-0027 dropped the step-up when every version had passed a reviewed pull request; under this ADR a signed-in session could otherwise both write content (by editing an item) and activate it. The database enforces it, not only the API: a new proof kind carries the copied assertion and public key (re-verified against the expected purpose and subject, as under ADR-0022) together with the admin basis (as under ADR-0027) and names its spent step-up, and the insert policy requires the actor's own consumed `knowledge_decision` step-up, as `admin_grant` rows already do, and stops accepting new `session` rows. Rows stored under ADR-0022 and ADR-0027 keep counting as they say. A rejected proposal never blocks the route: selection falls back as before.
- **Edit item.** The admin fixes one item by hand, with its source URL and quote, which writes a new proposed version that `corrects` the proposal; nothing is changed in place (domain rule 6). The edited version passes the same checks in code as a proposal (schema, official host, quote and value on the fetched page, rule cases and their coverage) before it is stored, and is decided like any other.
- The route's history lists every version with its state, superseded and rejected ones included.

### Settings › IA

- An admin-only screen ("Configurações › IA") holds, per environment: the Anthropic API key; a test with one minimal call; the model and effort per stage; the source-change notice switch and its weekday; and what each request cost.
- **The key.** Encrypted on the server with AES-256-GCM from `node:crypto`: a random 96-bit nonce per encryption, a 128-bit tag (`authTagLength: 16` on both sides, any other stored length refused), associated data with length prefixes and a domain tag binding the environment, the key row and a format version, and a key-version field. The key-encryption key is 32 bytes from a CSPRNG, base64url, distinct per environment, set as a Sensitive Vercel variable through the Vercel API and never read back; config decodes it and checks its length, with no passphrase or KDF. A key that fails to decrypt fails closed; the fallback to the `ANTHROPIC_API_KEY` variable applies only while no key is stored. **Storage apart from the settings:** the key lives in its own insert-only rows (set, replaced, removed), inserted only by `app_auth` in the transaction that consumes the step-up, under a policy that requires the actor's own consumed `ai_key` step-up, whose subject is the action `setAiKey` with the SHA-256 of the new key (removing it takes the same purpose, with the action `removeAiKey` and the key row's ID as its subject); models, effort and the notice switch are written through a definer function with no access to the key rows, and `app_api` and `app_jobs` read only the ciphertext. Only an owner-list admin may set, replace or remove the key, which the API checks since the list lives in code; each change is audited with identifiers only and emails the owner-list admins. The key travels only in a `POST` body, answered with `Cache-Control: no-store`, is dropped from client state after the request (TanStack Query mutation variables included), never persisted, and the field has `autocomplete="off"`; the test call is rate limited per account in Postgres. It is never returned (only "set" and its last four characters). The log scrubber and the secret scan learn the `sk-ant-` format. **Rotation:** set a new key-encryption key; the stored key then fails closed and the owner enters it again. Replacing the key in the app means revoking the old one in the Console too.
- **Whose key.** The owner's Console API key, so usage draws first on the monthly API credit his plan includes; the app never uses the claude.ai subscription login (OAuth), which the plan of 2026-11-16 found reserved to Claude Code and claude.ai. A key from a Console workspace used only by Arca keeps Arca's spend apart from his other apps, and a workspace limit can contain it; both are his choice, not a requirement.
- **Models.** Defaults live in reviewed code and settings override them: research and correction on the strongest model at high effort; validation on a different, cheaper model at medium effort. Settings offer only models listed in reviewed code, and a model joins that list only after the update request's evaluation cases pass on it ([#465](https://github.com/fernandolisboa/arca/issues/465)), which is how ADR-0004's evaluation gate applies to a choice made in the app. Free-text intake and the rule summary keep their own models and take the key from settings, with the same fallback.
- **Cost display.** Each stage stores its token usage; cost is computed with the existing price table and shown per request and per month. There are no caps.

### Prompt caching

One cache breakpoint per stage, after its stable prefix (instructions, then the route's current version and the verified source excerpts), with the five-minute lifetime, so the second round reads the same sources from cache. What is cached is public rule data and official page text, never case data; this is an exception to ADR-0004's rule that only instructions are cached.

### Source-change notice (optional, no model)

One daily Vercel cron that does nothing unless the switch is on and today is the chosen weekday; when it runs, it starts a workflow that fetches the official pages active versions cite with the existing fetcher, stores a hash of each page's text, and tells the admins through the notification service which routes' sources changed, with a "Pedir atualização" link. It never calls a model and never starts a request.

### What goes, and what stays

- **Goes**, in one ticket ([#463](https://github.com/fernandolisboa/arca/issues/463)) once the new review screen works: the corrector run, its routine, key, trigger and routes; the catalog check; the independent-check report flow and its starts; the flagged-versions route; the check's evaluation suite; country guides used only by the checker; the rule audit's monthly run; and the `ruleCheckPromptVersion` fingerprint. Until then the old code stays as it is, with nothing starting a check automatically since #454; the corrector and monthly scheduled tasks on claude.ai are the owner's to pause.
- **Stays**, because the pipeline uses it: the SSRF-safe fetcher, the quote and value checks, the PDF text layer, the price table and the `Summarizer`.

### Unchanged

CLAUDE.md domain rules 1, 2, 5, 6 and 7 hold: every requirement has a source; eligibility is pure functions; only a person approves; versions are immutable; the catalog is open, and adding a country or visa is a request, never a code change.

## Alternatives

| Option | Why not |
| --- | --- |
| Keep the check and corrector loop with tighter limits | Its termination depended on a model's verdict over pages it often cannot read; caps per day did not stop the same version being reworked ten times |
| Keep rules in the repository, written by the in-app pipeline through pull requests | Every fix would still need a GitHub write path from production, reviewers and a deploy, for data a person approves in the app anyway |
| Use the claude.ai subscription login from the app | Reserved to Claude Code and claude.ai; an API key on the owner's Console draws on the plan's API credit |
| Spend caps per request or per month | Rejected by the owner on 2026-11-16; the two rounds bound every request |
| "Tudo bate" only when every item matches | About 40% of items rest on pages a model cannot read; requiring them blocks convergence. They become a list the admin reads |
| A model checks the quotes | Whether a quote is on its page is a string comparison; code does it exactly and for free |
| Send a member's note to the research model as a lead | It may hold personal data and instructions; an admin re-entering an official link gives research the same lead without either |

## Consequences

- A rule update costs at most two rounds of model calls, and only when a person asks for it.
- Fixing a rule no longer needs a Claude Code session, a pull request or a deploy; the admin's approval with a passkey is the step that makes it count.
- Database tests must prove the rule tables are insert-only for every runtime role, that reading refuses a changed row, and that the import is idempotent and refuses a hash mismatch.
- The repository is no longer the history of rule content after the import; the database rows and their decisions are, under Neon's point-in-time restore, whose window is short on the current plan ([ADR-0021](0021-stay-on-vercel-and-neon.md)). Losing rows beyond it would lose versions old evaluations name; the owner accepts this as he accepts it for case data, and a lost version can be researched again by request.
- The app now holds a secret it did not hold before, the API key, in the database instead of the platform's variables, encrypted under a key that lives only in Vercel's function environment, with no KMS (ASVS 5.0 13.3.3 at Level 3 is not met): code running in a function or the build reads the key-encryption key and the database together, so the encryption covers exposure of the database alone. A leaked key-encryption key plus any copy of the database, Neon's restore history included, exposes every API key stored within that window, so the API key is also revoked in the Console. The threat model in [SECURITY.md](../SECURITY.md) records the new assets and boundaries.
- Research reads the web from Anthropic's infrastructure through its server tools; a fetched page can try to steer the research model, but code checks, not the model's account of what it read, decide whether a quote stands, and the admin decides with a passkey.
- With no caps, a stolen admin session could spend credit by filing and releasing requests, one live per route or country at a time; a Console workspace limit is the containment available.
- Route content changes already planned (EB-5 2027 amounts, Portugal's 2027 minimum wage, pre-2012 Polish descent) become update requests once this ships.
- Docs that still describe the old flow (spec 0002 R6, spec 0003 R5's purpose list, spec 0007 R7, SETUP.md, the incident runbook's secrets table, RETENTION.md, REVIEW.md's paths, the rule audit runbook) are updated by the ticket that changes the behavior they describe.
