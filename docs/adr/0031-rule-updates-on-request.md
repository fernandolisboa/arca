# ADR-0031: Rule updates on request, in two rounds, with rules in the database

- Status: Accepted
- Amended by: [ADR-0032](0032-session-reviews-activate-through-a-reviewed-pull-request.md) (session reviews store and activate a version through a reviewed pull request, with no passkey, and since 2026-11-25 the first version of a new route on the country's approved, pinned lists)
- Date: 2026-11-16
- Spec: [#455](https://github.com/fernandolisboa/arca/issues/455)
- Supersedes: [ADR-0029](0029-correction-requests-and-the-corrector-session.md) (the corrector run, its key and its trigger; the correction request becomes the update request)
- Amends: [ADR-0010](0010-stack-revised.md) (TypeSafe Jev serves the `RuleValidator` port by the owner's choice on #455, ahead of the evaluation gate that ADR-0010 set for its `Classifier` use); [ADR-0002](0002-rules-as-versioned-data.md) and [ADR-0014](0014-knowledge-base-as-reviewed-data.md) (where the base lives; how a version is proposed; how a first official-domain list is trusted); [ADR-0027](0027-admins-and-the-checked-batch-activation.md) (the independent check, its starts, country guides, the checked batch, the audit loop and the catalog check; activation takes a step-up again); [ADR-0025](0025-rule-summary-for-the-approver.md) (summaries read versions from the database); [ADR-0004](0004-ai-providers-behind-ports.md) (two ports; the key and the model come from settings; rule data and page text may be cached); [ADR-0006](0006-auth.md) and [ADR-0015](0015-identity-enrollment-step-up-and-recovery.md) (the `ai_key` step-up purpose; `knowledge_decision` offered again); [ADR-0008](0008-database-security-and-environments.md) (rule, request and settings tables, their roles, a secret in the database); [ADR-0009](0009-background-jobs-guarantees.md) (an update request's ID as a workflow argument); [ADR-0021](0021-stay-on-vercel-and-neon.md) (rule history lives in the database; members' files in the Blob store); [ADR-0028](0028-pdf-text-in-the-independent-check.md) (its PDF reading serves the quote check); [ARCHITECTURE.md](../ARCHITECTURE.md); CLAUDE.md (where rules live, how a rule changes)

## Context

Route versions live as JSON files in the repository, so every fix is a Claude Code session, a pull request, six to ten reviewers and a deploy. On top of that, the independent check re-read every proposed version whenever its prompt changed (eight prompt versions, `rule-check-1` to `rule-check-8`, from 2026-11-07 to 2026-11-15), an hourly cron re-checked them, and a daily corrector routine on claude.ai turned each "Difere" or "Confira" into another version. The check was unstable (the owner saw 5 of 8 production "differs" match in CI on the same rule), and "Tudo bate" required every item matched while about 40% of items sit on pages the checker cannot read, so the loop had no fixed point. By 2026-11-15 it had spent, by the owner's account, more than US$230 of API credit plus subscription usage; the credit ran out and took the owner's other apps down with it; some versions were corrected about ten times with the same problems returning.

The owner asked on 2026-11-16 for something simple: gather a country's requirements per visa, have a second agent validate them, fix once, validate again, approve, use; at most two rounds; no external routine and no AI cron; everything run and configured from inside the app. He approved the plan the same day in the project thread, including moving rules out of the repository (in his words, in pt-BR, "nunca fez sentido no repositório"), and rejected spend caps ("sou só eu"): the fixed number of rounds is the bound. The first step, removing every automatic check start, shipped in [#454](https://github.com/fernandolisboa/arca/pull/454).

## Decision

### Rules live in the database

- Route versions, country sets and official-domain lists become insert-only rows in the `knowledge` schema, keyed by ID and number, each with its content, its content hash (computed in code with the existing canonical hashing, spec 0002 R6) and, for a route version, its rule cases. No runtime role holds update or delete on them. Decisions (activate, reject) stay in `knowledge.decision`, bound to the content hash.
- **Reading re-checks the hash.** The API recomputes each row's content hash when it reads it and refuses a row whose hash differs from the stored one or from the hash its decision names, so a row changed outside the insert-only grants (for example with the owner connection, which bypasses them) is never evaluated.
- The repository keeps the engine, the rule schema, the country dataset (CLDR and former states) and fixture routes for tests. It stops receiving route versions once the import lands.
- **Import.** A one-time, idempotent data migration, run by the build's migration step like any migration ([ADR-0012](0012-automation-first-setup.md)), loads every bundled version, country set and official-domain list with its existing hash; a hash mismatch aborts the whole import. It writes no decision and no state: states stay computed from `knowledge.decision` as before (ADR-0022 rows re-verified, ADR-0027 rows counted by their basis), so the move keeps every active, proposed and rejected state and cannot launder a decision row. Old evaluations keep naming the route, number and hash they used, so they stay reproducible.
- **Selection** keeps its pure functions in `packages/domain`; the API feeds them versions read from the database instead of the bundled catalog, and the API bundle stops shipping route data.
- **As built ([#457](https://github.com/fernandolisboa/arca/issues/457)).** Official-domain lists had no hash before; each got its first one at import, over its content with no pins. A refused row withholds every version of its route, so selection never falls back to a version the refused one superseded or corrected; the refusal is logged by error name only. The API re-reads the rows only when their counts change, so a row changed in place keeps serving the content already verified until the next cold start, which refuses it. A route version's rule cases sit beside its content, outside its hash: today only the migrator writes them, but before [#459](https://github.com/fernandolisboa/arca/issues/459) lets another role insert rows, the cases must be bound to a hash the read re-checks, since the admin reads them before approving. Reading does not yet compare a row's hash with the hash its decisions name, and a decision request carries no hash: a row whose content and hash are both rewritten in place reads as a new proposed version, even of a rejected one. Only an actor who can already forge a decision can do that (ADR-0022's residual); [#460](https://github.com/fernandolisboa/arca/issues/460) closes it by refusing a stored decision's route and number under another hash and binding the decision, with its step-up, to the hash the admin saw. #459 must not let another role insert rows before then.

### Roles

Following [ADR-0008](0008-database-security-and-environments.md): `app_jobs` inserts a pipeline's stage results and proposals under no account; `app_api` inserts requests and an admin's edited version through reviewed `SECURITY DEFINER` functions owned by `knowledge_definer`, each re-checking the admin basis as ADR-0027 computes it; `app_auth` inserts decisions and settings changes after a spent step-up. A member's request is personal data: row-level security lets its author read their own requests and admins read all, and it joins the personal-data registry for erasure and export. The access-matrix suite covers every table and function for each role.

### An update request, never an automatic run

- **Update request** (UI "Pedido de atualização") replaces the correction request. An admin asks for one route ("Pedir atualização"), or for a new route of one country by naming the visa or entry type. A member may ask for the route they are looking at, with an optional note, links and a file; their request waits until an admin releases it, and only a released request starts anything. A member sees received, released, finished or declined.
- **What reaches a model.** No free text from any request reaches a model: not a member's or an admin's note, nor a file. The one exception, built with [#461](https://github.com/fernandolisboa/arca/issues/461), is the visa or entry type an admin names for a new route, 2 to 120 characters with no run of five digits and no `@`, which research reads as the request's subject, inside the data block. A request's links feed research only when they sit on the route's approved official-domain list, and only as addresses. Everything else is for the admin to read; an admin who finds an official page in a member's note re-enters it in their own request. So a member's words never leave Arca, and a planted instruction in a note cannot steer research.
- **Files.** A member's or admin's file goes to the private Blob store under the existing `corrections/` prefix, with the upload checks, the attachment-only download and the retention ADR-0029 set for request files (erased 30 days after the request ends, or 180 days after it was filed), now covering members' uploads; erasure and export follow the author's account. The form asks for copies of official pages only, never personal documents, and only owner-list admins can download a member's file; a member who attaches a personal document anyway leaves a plaintext copy for up to 180 days, a residual the owner accepts, recorded in the threat model's vendor-compromise row.
- **One live request per route**, and for a new route one per country, so two clicks never pay twice. A new request for a route or country with one already running is refused.
- **Nothing runs by itself.** No request starts on a prompt or model change, on a timer, or when a screen opens. There is no claude.ai routine, no corrector key and no AI cron.

### The pipeline, bounded at two rounds

One Vercel Workflow per request, whose argument is the request's ID and whose step inputs and outputs are identifiers only ([ADR-0009](0009-background-jobs-guarantees.md)): each stage writes its result to the database and returns its ID. A pure controller in `packages/domain` picks the next stage from the stored stage results and enforces the bound: **research → validation → at most one correction → final validation → done**. Any failure (provider down, timeout, an answer that does not parse) ends the request with a fixed code and no proposal, and nothing retries it on its own.

- **Research.** The research model, through a `RuleResearcher` port, with Anthropic's web search and web fetch server tools limited to the route's approved official-domain list, answers in the rule schema through structured output: every item with its source URL and the quoted passage, plus rule cases. Its input is the route's ID, its current version, its official-domain list and the request's qualifying links: public data and identifiers only. Whether the tools' domain limit also admits subdomains is checked against Anthropic's documentation when the adapter is built ([#459](https://github.com/fernandolisboa/arca/issues/459)); either way, Arca's own host matching decides what counts as official.
- **Checks in code, between stages.** Schema validation; every official source's host on an approved official-domain list, by Arca's own matching; the existing SSRF-safe fetcher (with the PDF text layer of [ADR-0028](0028-pdf-text-in-the-independent-check.md)) reads each cited page and verifies that each quote is a verbatim substring and carries the item's value, with the existing quote and value checks; `verifiedAt` set from the code's clock when the page was read, never by a model; the engine runs the proposal's rule cases, and the coverage rule of spec 0002 R8 (every requirement exercised every way) holds. An item whose quote is not on its page is marked by code, never by a model, so a fabricated quote cannot read as confirmed. The floors ADR-0014 set for research still hold where they apply: public terms and identifiers only, never case data; fetches by GET over `https` with size and count limits through the guarded fetcher; never deciding; evaluation cases with known-wrong, correct and adversarial versions ([#465](https://github.com/fernandolisboa/arca/issues/465)).
- **Validation.** A `RuleValidator` port on a model other than research's (settings refuse the same model for both) receives each item with its verified quote, not whole laws and not a passage locator, and answers per item only *supports*, *does not support* or *cannot tell*, with a short reason.
- **Correction.** Only the items the validator rejected or code failed, with their reasons, go back to the research model, with the same tools and limits.
- **Final validation.** Only the corrected items.
- **The result** is a proposed version with three lists for the admin: confirmed items; divergent items with the reason; items nobody could confirm, with their official links. Items that could not be confirmed are information, never a reason for another round.

### A new country's first official-domain list

Research cannot write the list it is limited to. For a new route in a country with no approved list:

- The admin names, in the request, the official hosts to start from; research runs limited to them, and may propose more. *Amended as built (#461): the list holds only hosts the admin named or their subdomains; see the note below.*
- Every host of the proposed list cites a registry page (the country's domain authority, or an official directory of its public bodies) that sits on a host the admin named or on an already approved list; code fetches that page and checks the host appears on it, as spec 0002 R6 asks of a first list. A list that cites itself as proof, or that holds a registry suffix such as a whole top-level domain, is refused.
- The proposed list is shown apart, host by host with its registry proof, and decided on its own before the route: until it is approved, every item resting on its hosts sits under "Não confirmados", and the fetcher treats its hosts as unapproved, except that hosts the admin named may be fetched for the registry check. *Amended as built (#461): validation reads them, since those hosts are now only ones the admin named; see the note below.*
- A request on an existing country never widens its approved list: a new host goes through a new list version the admin approves on its own.

### Review, approval and editing

- The activation screen shows a request's proposal as the three lists, each item with its source and quote.
- **Approval with a passkey.** As the spec asks, every new decision takes a step-up of the `knowledge_decision` purpose bound to the subject's content hash: activating or rejecting any route version (imported, proposed, hand-edited, or an active one being rejected), any official-domain list version (a new subject kind) and any comparison version, so no decision path is left on a session alone. ADR-0027 dropped the step-up when every version had passed a reviewed pull request; under this ADR a signed-in session could otherwise both write content (by editing an item) and activate it. The database enforces it, not only the API: a new proof kind carries the copied assertion and public key (re-verified against the expected purpose and subject, as under ADR-0022) together with the admin basis (as under ADR-0027) and names its spent step-up, and the insert policy requires the actor's own consumed `knowledge_decision` step-up, as `admin_grant` rows already do, and stops accepting new `session` rows. Rows stored under ADR-0022 and ADR-0027 keep counting as they say. A rejected proposal never blocks the route: selection falls back as before.
- **Edit item.** The admin fixes one item by hand, with its source URL and quote, which writes a new proposed version that `corrects` the proposal; nothing is changed in place (domain rule 6). The edited version passes the same checks in code as a proposal (schema, official host, quote and value on the fetched page, rule cases and their coverage) before it is stored, and is decided like any other.
- The route's history lists every version with its state, superseded and rejected ones included.

### Settings › IA

- An admin-only screen ("Configurações › IA") holds, per environment: the Anthropic API key; a test with one minimal call; the model and effort per stage; the source-change notice switch and its weekday; and what each request cost.
- **The key.** Encrypted on the server with AES-256-GCM from `node:crypto`: a random 96-bit nonce per encryption, a 128-bit tag (`authTagLength: 16` on both sides, any other stored length refused), associated data with length prefixes and a domain tag binding the environment, the key row and a format version, and a key-version field. The key-encryption key is 32 bytes from a CSPRNG, base64url, distinct per environment, set as a Sensitive Vercel variable through the Vercel API and never read back; config decodes it and checks its length, with no passphrase or KDF. A key that fails to decrypt fails closed; the fallback to the `ANTHROPIC_API_KEY` variable applies only while no key is stored. **Storage apart from the settings:** the key lives in its own insert-only rows (set, replaced, removed), inserted only by `app_auth` in the transaction that consumes the step-up, under a policy that requires the actor's own consumed `ai_key` step-up, whose subject is the action `setAiKey` with the SHA-256 of the new key (removing it takes the same purpose, with the action `removeAiKey` and the key row's ID as its subject); models, effort and the notice switch are written through a definer function with no access to the key rows, and `app_api` and `app_jobs` read only the ciphertext. Only an owner-list admin may set, replace or remove the key, which the API checks since the list lives in code; each change is audited with identifiers only and emails the owner-list admins. The key travels only in a `POST` body, answered with `Cache-Control: no-store`, is dropped from client state after the request (TanStack Query mutation variables included), never persisted, and the field has `autocomplete="off"`; the test call is rate limited per account in Postgres. It is never returned (only "set" and its last four characters). The log scrubber and the secret scan learn the `sk-ant-` format. **Rotation:** set a new key-encryption key; the stored key then fails closed and the owner enters it again. Replacing the key in the app means revoking the old one in the Console too.
- **Whose key.** The owner's Console API key, so usage draws first on the monthly API credit his plan includes; the app never uses the claude.ai subscription login (OAuth), which the plan of 2026-11-16 found reserved to Claude Code and claude.ai. A key from a Console workspace used only by Arca keeps Arca's spend apart from his other apps, and a workspace limit can contain it; both are his choice, not a requirement.
- **Models.** Defaults live in reviewed code and settings override them: research and correction on the strongest model at high effort; validation on a different, cheaper model at medium effort. Settings offer only models listed in reviewed code, and a model joins that list only after the update request's evaluation cases pass on it ([#465](https://github.com/fernandolisboa/arca/issues/465)), which is how ADR-0004's evaluation gate applies to a choice made in the app. Free-text intake and the rule summary keep their own models and take the key from settings, with the same fallback.
- **Cost display.** Each stage stores its token usage; cost is computed with the existing price table and shown per request and per month. There are no caps.

### Prompt caching

One cache breakpoint per stage, after its stable prefix (instructions, then the route's current version and the verified source excerpts), with the five-minute lifetime, so the second round reads the same sources from cache. What is cached is public rule data and official page text, never case data; this is an exception to ADR-0004's rule that only instructions are cached.

### Source-change notice (optional, no model)

One daily Vercel cron that does nothing unless the switch is on and today is the chosen weekday; when it runs, it starts a workflow that fetches the official pages active versions cite with the existing fetcher, stores a hash of each page's text, and tells the admins through the notification service which routes' sources changed, with a "Pedir atualização" link. It never calls a model and never starts a request.

### What goes, and what stays

- **Goes**, in one ticket ([#463](https://github.com/fernandolisboa/arca/issues/463)) once the new review screen works: the corrector run, its routine, key, trigger and routes; the catalog check; the independent-check report flow and its starts; the flagged-versions route; the check's evaluation suite; country guides used only by the checker; the rule audit's monthly run; and the `ruleCheckPromptVersion` fingerprint. Until then the old code stays as it is, with nothing starting a check automatically since #454; the corrector and monthly scheduled tasks on claude.ai are the owner's to pause.
- **As built ([#463](https://github.com/fernandolisboa/arca/issues/463)).**
  - *Code.* The corrector key, run, trigger and `/v1/corrector/*` routes, the check's starts, reports, progress and queue routes, the check workflow, the second look, the passage locator, the scripted checker, the `catalog-check` and independent-check evaluations, the `ruleCheckPromptVersion` fingerprint and the corrector script are gone, with their screens and strings. What the update request uses stays and is renamed for it: the page reader in `apps/api/src/knowledge/pages` (the fetcher, HTML and PDF text, machine-readable addresses) and the quote and value checks in `packages/domain/src/quote-check`. The intake-eval workflow runs the intake and rule summary evaluations only.
  - *Country guides.* The guide files, their hash entries, their build kind and `countryGuide` are deleted. `knowledge-immutable` lets a guide and its hash entry go and refuses a new one ([#476](https://github.com/fernandolisboa/arca/pull/476), merged first, since the required check runs `main`'s rules).
  - *Tables kept as history.* `check_start`, `independent_check`, `check_progress` and `corrector_key` stay, read-only: dropping them would delete production history for no gain. A new migration (`knowledge_retired_check_and_corrector`, with its grants) drops their write and read policies and revokes every runtime role's privileges on the check's tables and the insert on `corrector_key`; RLS stays forced, so with no policy no runtime role reads them. `knowledge_definer` keeps reading `corrector_key`, so a person's data export still lists the keys they made, and the registry keeps all four tables.
  - *Definer functions kept, keys closed.* The corrector's `SECURITY DEFINER` functions are owned by `knowledge_definer`, and the repository's migration policy lets the migrator take that role only to hand it a new function, so they stay, and `app_api` keeps EXECUTE on them; the API no longer calls them. So that no key made before this change still opens them, a following migration (`knowledge_corrector_key_digest_closed`) takes from `knowledge_definer` its SELECT on the key digest: `live_corrector_key()`, which every key-gated read and answer function goes through, now fails with a permission error, while the export, which reads a key row's kind, time and author only, still works. `correction_page_copies` also stays executable by `app_jobs`, unused. The access-matrix suite checks both.
  - *Kept for the record.* The `corrector_key` step-up purpose stays allowed by the database, the `corrector_*` audit kinds and the `corrector_key_changed` notice still parse old rows, and gitleaks keeps the corrector key's pattern until every such key has expired. Correction requests ("Apontar erro") and the old new-route requests stay as notes for admins, with no session to answer them; their screens no longer promise one.
  - *Owner steps.* None: the corrector routine, the monthly rule audit routine and `ARCA_CORRECTOR_FIRE_TOKEN` were already deleted on 2026-11-16.
- **Stays**, because the pipeline uses it: the SSRF-safe fetcher, the quote and value checks, the PDF text layer, the price table and the `Summarizer`.

### Unchanged

CLAUDE.md domain rules 1, 2, 5, 6 and 7 hold: every requirement has a source; eligibility is pure functions; only a person approves; versions are immutable; the catalog is open, and adding a country or visa is a request, never a code change.

### TypeSafe Jev validates (amendment 2026-11-16)

The owner's amendment to the spec ([#455](https://github.com/fernandolisboa/arca/issues/455#issuecomment-6931739213)) moves validation from Claude to TypeSafe's Jev; [#458](https://github.com/fernandolisboa/arca/issues/458) built the settings for it. Where this section and the text above differ, this section holds.

- **Validation on Jev.** The `RuleValidator` port runs on Jev ([docs](https://docs.typesafe.ai/introduction), read 2026-11-16): one call per stage, each item its own Choice question of *supports*, *contradicts* or *cannot tell* over a state of the item and its quote, already verified verbatim on the page, with low confidence counted as *cannot tell* ([#459](https://github.com/fernandolisboa/arca/issues/459)). Jev charges per input token only ([models](https://docs.typesafe.ai/models.md), read 2026-11-16). It is a model other than research's by construction, so the settings need no check that the two differ. Claude stays for research and correction.
- **A new vendor.** TypeSafe is a new service under ADR-0010's rule, recorded here; the data-flow table in [ARCHITECTURE.md](../ARCHITECTURE.md#data-flows) carries its row: only public rule data and official-page excerpts, never case data. The adapter calls the HTTP API with `fetch` and no SDK, so no dependency joins the lockfile.
- **Two keys, one table.** The TypeSafe key lives beside the Anthropic key, on the same terms: `knowledge.ai_key` rows name their provider (`anthropic` or `typesafe`), a removal names a key of its own provider (a composite foreign key), a provider's key is its newest `set` row that no removal names (so removing an older key never ends a newer one stored meanwhile), and the `ai_key` step-up's subject is the action `setAiKey` with the fields `provider` and `keySha256` (the hex SHA-256 of the new key), or `removeAiKey` with the key row's ID as its target and the provider as its field. Only Anthropic has a variable to fall back to.
- **The key-encryption key's version** is derived from the key itself (the first 31 bits of a tagged SHA-256), so a rotated key is told apart without a second variable, and a row sealed under another one reads as unreadable before anything is opened. The variable is `ARCA_AI_KEY_ENCRYPTION_KEY`.
- **The test** lists the models the key may use (`GET /v1/models` on each provider), which spends no tokens, and answers `ok`, `no_key`, `unreadable`, `rejected` (401 or 403) or `unavailable`, never the provider's words; ten tests per admin per hour.
- **Stage settings** are insert-only rows written through `knowledge.set_ai_stage`, which re-checks the admin basis; any admin may choose, and the audit log names who did, so a row names no account. Validation takes no effort. Until the update request's evaluation cases run ([#465](https://github.com/fernandolisboa/arca/issues/465)), the reviewed list holds only the defaults: Opus 5.5 for research and correction, at any effort, and `jev-1.14.0`, a pinned version rather than the moving `jev-latest` alias ([models](https://docs.typesafe.ai/models.md#aliases), read 2026-11-16), for validation. On 2026-11-19 the owner added Fable 5.2 to the research and correction list himself, ahead of those cases: the default stays Opus 5.5, and choosing Fable 5.2 is an admin's audited choice. A stored choice the list no longer offers falls back to the default.

- **As built ([#459](https://github.com/fernandolisboa/arca/issues/459)).**
  - *Where the proposal waits.* The ended request keeps the checked proposal, its content hash and the three lists in `knowledge.update_end`; no role but the migrator inserts a `route_version` row yet, as the #457 note requires. [#460](https://github.com/fernandolisboa/arca/issues/460) writes the approved proposal as a version, bound with its step-up to a hash it recomputes from the stored proposal against verified rows, never to the stored column, and covering the proposal's rule cases as well as its content, since the content hash leaves the cases out (the lists stay evidence, not signed content; see the #460 note).
  - *Tables.* `update_request` is inserted only through `knowledge.start_update_request`, owned by `knowledge_definer`, which re-checks the admin basis and, under a lock per route, refuses a second live request. A request with no end is live for an hour, then shows as *stalled* and blocks nothing, so a crashed run never locks its route. `update_stage` (one row per stage, in order, checked by the table), `update_end` and `rule_verdict` are inserted by `app_jobs` only; nobody updates or deletes. Each stage keeps its token usage and web searches, and the cost is computed in code from a reviewed price table plus US$ 10 per thousand searches. The start is audited as `update_requested` and limited to 10 per admin an hour, a guard against repeated taps, not a spend cap. The base is the route's newest version only when the read verifies its hash; research's hosts come from its verified official-domain lists, and with none research does not run, since an empty list would leave the tools unlimited.
  - *Code checks added.* The proposal check runs the build's version order (spec 0002, R6: it starts after every version of the route, and research is told to leave `corrects` out) and its country-set membership check. A new source no code read gets no verification date: the proposal is refused for the correction instead.
  - *Structured output.* The rule schema is recursive, which structured output refuses ([structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), read 2026-11-17), so research answers the version and its cases as JSON text plus one quote per item, and code parses both with the rule schema. A reply that does not parse ends the stage as *unparsable*, with its usage kept.
  - *Tools.* Research uses `web_search_20250305` and `web_fetch_20250910`, the versions without dynamic filtering, so no model-written code runs in Anthropic's sandbox; each is limited to the hosts on the base version's pinned official-domain lists, which also admits their subdomains ([web search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool), [web fetch](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool), read 2026-11-17), and a fetched page adds at most 30,000 tokens. Arca's own host matching still decides what is official when the pages are read. A search costs US$ 10 per thousand ([pricing](https://platform.claude.com/docs/en/about-claude/pricing), read 2026-11-17).
  - *Data, not instructions.* Only the instructions are system text, cached for five minutes; the route's data (its ID, hosts, current version and cases) is the user turn's first block, closed by the second five-minute breakpoint, and the correction's earlier proposal and problems follow in tags; the instructions say all of it is data. No quote from an earlier request is sent: until an admin approves one ([#460](https://github.com/fernandolisboa/arca/issues/460)), none is trusted.
  - *Correction and final validation.* The correction receives the whole proposal it corrects, with code's problems and the divergent items and their reasons, and answers a whole proposal; the final validation checks all of it again in code, and the validator is asked only about items with no stored answer, so unchanged items cost nothing.
  - *Verdict cache.* `rule_verdict` is keyed by the SHA-256 of the item's kind, title and values, each quote with its page's text hash, the validator model and its prompt version; a changed page or item asks again. Jev answers below 0.5 confidence count as *cannot tell*.
  - *Outside production* the scripted researcher re-proposes the current version and the scripted validator can tell nothing; both call nothing, and their answers are stored under the scripted model's name, never a real one's.
  - *The function duration limit.* A research call times out after 270 seconds and a validation reads six pages at a time, so a stage ends inside the 300-second default as a fixed failure, never a stall; [#465](https://github.com/fernandolisboa/arca/issues/465) measures real runs and may raise the limit. A failed call stores no usage, so its cost is not shown.

- **As built ([#460](https://github.com/fernandolisboa/arca/issues/460)).**
  - *A proposal is a version at once.* When a request ends with a proposal, `app_jobs` inserts it as a `route_version` that names the request (`request_id`, unique) in the transaction that writes `update_end`; the insert policy admits only a row whose request ended with no failure, for the same route, under the same content hash; it does not bind the number or the cases, which only `app_jobs` writes, within its documented residual, and which the decision's cases hash binds. The row reads as proposed, its hash recomputed on every read like any row, so approve and reject are the existing decision routes and the review needs no second store. The progress names the number it took.
  - *What a decision binds.* A route decision's step-up action carries two fields, `contentHash` and `casesHash`, the SHA-256 of the canonical `{cases}` read from the row (the content hash leaves the cases out). The client sends the hashes it showed; the API rebuilds the action from the current read, so a version that changed since the screen loaded spends nothing and answers 403 `step_up_required`, shown as "changed". A comparison decision binds its content hash alone, since it has no cases. The lists are not bound: they are evidence beside the version, kept in the insert-only `update_end` row the version names, and only a writer who can already forge a decision could change them.
  - *Proof kind.* New rows are `admin_step_up`: the copied assertion, the passkey's public key, the admin basis (`owner_list`, or `grant` with its grant), the cases hash for a route, and the spent step-up's ID. `app_auth` inserts one only under its own identity and only when `auth.step_up` holds that account's consumed `knowledge_decision` step-up with the same credential, server nonce, authenticator data, client data and signature; the `session` insert policy is dropped, so no runtime role can store a decision without a passkey. A row counts when its basis holds at its time and its assertion re-verifies against the rebuilt action; a rejection counts either way.
  - *Changed in place.* An `admin_step_up` decision whose route and number now read under another content or cases hash marks that identity rejected and logs `KnowledgeDecidedVersionChanged`, closing the #457 residual. Rows stored under ADR-0022 and ADR-0027 are left as they count: they were stored when every version passed a reviewed pull request, and refusing them could flip production's active versions over data nobody can now check.
  - *Hand edits.* `knowledge.edit_route_version`, owned by `knowledge_definer`, re-checks the admin basis, takes the update requests' lock for the route, refuses while a request of the route is live (409 `update_live`), requires the next number and an existing corrected version (409 `version_taken`), and inserts the version with no `request_id` plus a `version_edit` row (item key, official URL and quote). Before calling it, the API rebuilds the version from the stored one (number, `corrects`, the edited item, the cited source added or its date renewed), runs the proposal check, requires the item to cite the URL, reads that one page through the guarded fetcher and verifies the quote in code. Audited as `version_edited`, 10 per admin an hour. The review of an edit follows `corrects` back to the request's lists, at most 50 edits deep, with the edited item first as confirmed and marked.
  - *Limit, lifted by [#472](https://github.com/fernandolisboa/arca/issues/472).* A proposal's cases must carry their snapshots inline, since the API has no synthetic families at run time; 21 of the 65 imported versions (`us-eb5` 1–8, `pt-d7` 1–6, `pt-d8` 1–6, `is-remote-work` 1) named one, so neither an update request nor a hand edit of those routes could pass the proposal check.
  - *Not here, lifted by [#461](https://github.com/fernandolisboa/arca/issues/461).* The official-domain list as a decision subject comes with the new-route request; until then only route and comparison versions are decided.
  - *Refusal reasons.* A refused edit shows the reasons as code states them, in English, as the proposal check writes them for an update request; the screen says so in pt-BR.
  - *Scope.* Any version that is not rejected may be edited, an imported or active one included, since a wrong item in the active version is the case that most needs a fix; the edit is only ever a new proposed version.
  - *Removed.* The checked-batch activation (`POST /v1/knowledge/versions/activate-checked`) stored `session` rows, which the database now refuses, so it is gone with its screen.

- **As built ([#472](https://github.com/fernandolisboa/arca/issues/472)).** The migration `knowledge_inline_rule_cases`, generated from the data directory and `eval/families` and compared with a fresh generation by a test, rewrites the `cases` column of those 21 rows once, in place: each family reference becomes the snapshot of the file it pins, read after checking the pinned SHA-256, exactly as the cases runner reads it, so every case means what it meant. It is the one exception to insert-only rule rows, and it is narrow: the content and content hash stay, a row is rewritten only while it stores the imported cases under the imported hash, the migrator lends itself an update of the column and a policy for that statement and gives both up in the same migration, and the migration aborts if a passkey decision binds one of those versions' cases hash or if any row still names a family afterwards. The cases hash of those versions changes; their decisions are ADR-0022 and ADR-0027 rows, which bind no cases hash, so every version keeps its state. The repository's cases files keep their family references, since the import is generated from them.

- **As built ([#461](https://github.com/fernandolisboa/arca/issues/461)).**
  - *The request.* `POST /v1/knowledge/new-route-requests` takes a country from the dataset, the visa or entry type as free text (2 to 120 characters) and up to 10 https links. It is inserted only through `knowledge.start_new_route_request`, owned by `knowledge_definer`: it re-checks the admin basis and, under a lock per country, refuses a second live new-route request of the country (409 `update_live`), live meaning no end within the hour, as for updates. The row has no `route_id` or base; it stores the country, the visa, the links and `list_pins`, the approved lists the request may read. Audited as `update_requested` with the country, 10 per admin an hour. The pipeline, its stages, failures, cost and progress are an update request's; the visa reaches research as the request's subject, inside the data block, never as instructions.
  - *Which lists.* A country's approved lists (`approvedOfficialDomainLists`) are those pinned by any stored version of its routes, kept when imported (no `request_id`) or activated by a decision. With approved lists, research runs on their hosts, the proposal pins only those lists, and only links on those hosts reach research, as addresses. With none, the request needs at least one link (400 `links_needed`), the hosts of its links (never a registry suffix) are the named hosts research starts on, and research must also propose the country's first list, with ID the country code in lowercase and the next free number.
  - *The proposal check.* A new route's version must be number 1 of a route ID that starts with the country code and no stored route holds, of the same country, and pin only the lists the request allowed plus the proposed list; then the usual checks (schema, cases and coverage, quotes on fetched pages). A first list passes `firstListProblems`: at most 20 hosts, each a host the admin named or a subdomain of one and never a registry suffix, so research never widens what it may read past what a person typed; each host's proof on a named host or on an imported list's host, never on a host of the same list, its parent or a subdomain, and at an address with no query or fragment that does not itself name the host, since a search or not-found page echoes its address. Proofs may sit on imported lists' hosts but not on lists a request proposed, so a list a model wrote never vouches for another. Code then reads every proof page through the guarded fetcher limited to those trusted hosts, six at a time, and checks it names the host as a whole name. Any problem is a proposal problem, so the correction sees it and a list still wrong after it ends the request as `proposal_invalid`.
  - *Reading the proposed hosts.* Unlike the plan above, the hosts of a first list that passed the registry check are read during validation, since otherwise no source of a new country could get a verification date and every proposal would be refused. They are hosts the admin typed or their subdomains, so what is read is what a person chose. Until the list is active, the review masks every item of a version as not confirmed (reason `list_pending`) unless every list it pins is approved, activating the version is refused with 409 `list_pending`, and an update request of a route that pins it is refused with 409 `list_pending`, so research never runs on those hosts again before a person approves them.
  - *Rejecting a list.* Only a proposed list is rejected; an active one answers 409 `list_active`, since a route that pins it may be active and a rejection would leave it standing. Residuals: two admins deciding the list and its route at the same moment can still leave an active route on a rejected list, as only Fernando decides today; and the registry-suffix check is a short list of common suffixes, not the public-suffix list, so a shared-hosting suffix (`github.io`) is refused only because no admin would name one; vendoring the public-suffix list would need its own ADR. Rejecting an active list is refused rather than taking down the routes that pin it, so an active list is revoked only by rejecting those route versions and asking for a new route; and whether a list came from a request is its `request_id`, outside its hash, so only a writer with the owner connection could make a proposed list read as imported (ADR-0022's residual). The review shows each proof's address as stored, with the page title the model wrote marked as the Arca's.
  - *Stored.* `update_end.list_hash` names the proposed list; in the same transaction `app_jobs` inserts the `official_domain_list` row with the request's ID (unique), admitted by policy only for a request that ended with no failure, of no route, under the list's ID and that hash; then the route version, admitted for a new-route request only as number 1 of a route ID that starts with the country code.
  - *The list decision.* A new decision subject `official_domains` (`decision.list_id`), always an `admin_step_up` row bound to the list's content hash, the SHA-256 of `{version, pinned: {}}`; routes `POST /v1/knowledge/official-domains/activate|reject`. Only a list a request proposed is decided (404 for an imported one). The review shows the list host by host with its registry page, apart and above the items, with its own decision.
  - *Screen.* "Rota nova pesquisada pelo Arca" on the activation screen: the form (countries from the dataset, the visa, links one per line, saying when a link is needed), then the ten newest requests with their stages, cost and a way to the proposed version.
- **As built ([#462](https://github.com/fernandolisboa/arca/issues/462)).**
  - *Stored as correction requests.* A member's request is a `correction_request` row of the new `request_kind` `update` (ADR-0029's rows are `correction`), naming the whole version (`item_kind` `version`), with an optional note (the row's note check now allows none on an update request), up to five links and files together, and the same uploads, attachment-only download, retention and erasure. New definer functions serve it, since only their owner could replace ADR-0029's: `file_update_request` (any confirmed account; an unconfirmed one gets 403 `account_unconfirmed`, as on uploads), `start_update_upload` and `attach_update_file` (a member's file names no page, so the independent check's page copies never include it), `own_update_requests` (the author's own only), `member_update_requests` (any admin; the 50 newest, or one by ID before a release), `member_request_ids` (so ADR-0029's per-version list and its Close leave members' requests out), `release_update_request` and `decline_update_request`.
  - *One live request per route.* Filing takes the lock `start_update_request` takes for the route and answers 409 `update_live` while a member's request of the route waits (no release or decline) or an update request of the route runs; a member's request never names a country, so new routes stay admin-only.
  - *Release.* `POST /v1/knowledge/member-update-requests/release` runs `start_update_request` as an admin's "Pedir atualização" does (same refusals and hourly limit), then, in the same transaction, `release_update_request` stores a `released` event naming that update request, which must be of the same route and made in that transaction; if the request was released or declined meanwhile, the whole transaction rolls back (409 `decided`). The update request reads the route's newest version, whatever version the member saw.
  - *Decline.* `decline_update_request` stores a `declined` event with an optional reason of up to 500 characters, which the member reads; it is allowed while the request waits, or once its release ended with no proposal (failed, or no end an hour after it was asked for), so a member's request never stays released for good. It takes the route's lock, so a release and a decline never both land.
  - *States.* `memberRequestState` in `packages/domain`: received, released (also after a release that failed), finished (the update request ended with a proposal) or declined. `memberRequestPending` (waiting, or released into a running update) decides whether the member may ask again; a release that failed or stalled shows its own hint and lets them. Retention counts a request as ended at its release or decline, so its note, links and files go 30 days after that.
  - *What reaches a model.* Nothing from the request, not even a link on an approved official domain (the Decision's "links feed research" holds for an admin's request only): research reads the route's data and approved lists only, and a test checks that a released request's research input holds neither the note, the link nor the file. The corrector run's routes, which would list members' notes and files, stay unserved (401) and its trigger is not built (503 `corrector_off`), so ADR-0029's loop is dormant until [#463](https://github.com/fernandolisboa/arca/issues/463) removes it; its database functions still read every request until then.
  - *Files.* Any confirmed account may start an upload; only owner-list admins download a request's file (403 `owner_list_only` for an admin by grant), for ADR-0029's requests too. Accepted residuals: a member's PDF or HTML may carry script, which ADR-0029 accepted when only owner-list sessions uploaded; it is downloaded as an attachment with `nosniff` from the Blob origin, so it reaches only the admin's local viewer. And, as for ADR-0029, the database checks an owner-list basis only as "an account is set" (the owner list lives in code), so owner-list-only reads and release rest on the API's check.
  - *Notice.* Owner-list admins get the `update_requested` email and push, which says a family member asked and the request waits for them. Admins by grant see the list but get no notice, as with ADR-0029's requests.
  - *Screens.* On the results, each route has "Pedir atualização desta regra" (note, links one per line, one file) and the member's newest request's state; on the activation screen, "Pedidos dos participantes" lists the 50 newest with note, links, files for owner-list admins, and Liberar or Recusar.

## Alternatives

| Option | Why not |
| --- | --- |
| Keep the check and corrector loop with tighter limits | Its termination depended on a model's verdict over pages it often cannot read; caps per day did not stop the same version being reworked ten times |
| Keep rules in the repository, written by the in-app pipeline through pull requests | Every fix would still need a GitHub write path from production, reviewers and a deploy, for data a person approves in the app anyway |
| Use the claude.ai subscription login from the app | Reserved to Claude Code and claude.ai; an API key on the owner's Console draws on the plan's API credit |
| Spend caps per request or per month | Rejected by the owner on 2026-11-16; the two rounds bound every request |
| "Tudo bate" only when every item matches | About 40% of items rest on pages a model cannot read; requiring them blocks convergence. They become a list the admin reads |
| A model checks the quotes | Whether a quote is on its page is a string comparison; code does it exactly and for free |
| Send a member's note to the research model as a lead | It may hold personal data and instructions; an admin re-entering an official link gives research the same lead without either |

## Consequences

- A rule update costs at most two rounds of model calls, and only when a person asks for it.
- Fixing a rule no longer needs a Claude Code session, a pull request or a deploy; the admin's approval with a passkey is the step that makes it count.
- Database tests must prove the rule tables are insert-only for every runtime role, that reading refuses a changed row, and that the import is idempotent and refuses a hash mismatch.
- The repository is no longer the history of rule content after the import; the database rows and their decisions are, under Neon's point-in-time restore, whose window is short on the current plan ([ADR-0021](0021-stay-on-vercel-and-neon.md)). Losing rows beyond it would lose versions old evaluations name; the owner accepts this as he accepts it for case data, and a lost version can be researched again by request.
- The app now holds a secret it did not hold before, the API key, in the database instead of the platform's variables, encrypted under a key that lives only in Vercel's function environment, with no KMS (ASVS 5.0 13.3.3 at Level 3 is not met): code running in a function or the build reads the key-encryption key and the database together, so the encryption covers exposure of the database alone. A leaked key-encryption key plus any copy of the database, Neon's restore history included, exposes every API key stored within that window, so the API key is also revoked in the Console. The threat model in [SECURITY.md](../SECURITY.md) records the new assets and boundaries.
- Research reads the web from Anthropic's infrastructure through its server tools; a fetched page can try to steer the research model, but code checks, not the model's account of what it read, decide whether a quote stands, and the admin decides with a passkey.
- With no caps, a stolen admin session could spend credit by filing and releasing requests, one live per route or country at a time; a Console workspace limit is the containment available.
- Route content changes already planned (EB-5 2027 amounts, Portugal's 2027 minimum wage, pre-2012 Polish descent) become update requests once this ships.
- Docs that still describe the old flow (spec 0002 R6, spec 0003 R5's purpose list, spec 0007 R7, SETUP.md, the incident runbook's secrets table, RETENTION.md, REVIEW.md's paths, the rule audit runbook) are updated by the ticket that changes the behavior they describe.
