# Spec 0003: Identity and access

- Status: Ready for tickets
- Date: 2026-11-02
- Epic: cross-platform foundations ([ROADMAP.md](../ROADMAP.md#phase-1--family-mvp-web)), after [spec 0001](0001-foundations-scaffold.md)
- Decisions: [ADR-0015](../adr/0015-identity-enrollment-step-up-and-recovery.md), [ADR-0006](../adr/0006-auth.md), [ADR-0008](../adr/0008-database-security-and-environments.md), [ADR-0012](../adr/0012-automation-first-setup.md); consumers: future knowledge-base decisions (ADR-0014, proposed in pull request #39), [ADR-0017](../adr/0017-data-lifecycle-and-backups.md) (deletion and export), [ADR-0018](../adr/0018-vault-encryption.md) (vault unlock)

## Goal

Members of the family sign in with passkeys, invited by someone already in, on every environment; sensitive actions ask for a fresh passkey verification bound to what is being done; a lost device is recoverable without making the inbox the master key; every security event is recorded and visible to the person it concerns.

## Scope

**In:** Better Auth with the passkey plugin behind an endpoint allow-list; the `auth` schema and the `app_auth` pool; owner enrollment and invites; passkey sign-in and registration in the web client through the `platform` passkey port; sessions, device list and revocation; purpose-bound step-up; recovery with the email link and the recovery code; the audit log and security notices by email; email through Resend with a non-production outbox; rate limits; the relying party per environment; the `app.account_id` rename.

**Out:** bearer tokens for native apps (Phase 4); the designated-adult recovery factor (with the case model); push notices (spec 0005); account deletion and export (spec 0004, which uses this spec's step-up); the vault (spec 0005).

**No case data.** Accounts hold an email address, passkeys and sessions; the seed and tests use synthetic addresses on reserved domains (`example.com`, `example.org`).

## Requirements

### R1. Auth module, schema and pool

- `better-auth` and `@better-auth/passkey` at the newest release at least 7 days old (1.7.x as of 2026-11-02), and `@simplewebauthn/server` and `@simplewebauthn/browser` as direct dependencies at the 13.x the plugin resolves (one copy of the verifier; move to 14 when the plugin does), added to the Versions table of spec 0001 with a supply-chain PASS.
- Better Auth runs inside `apps/api` under `/v1/auth`, with the Drizzle adapter on its own pool connected as `app_auth` (pooled host, explicit user and password, `current_user` checked per connection, as spec 0001 R7 does for `app_api`). `bootstrap.sql` sets the `app_auth` password from a new Sensitive variable, `ARCA_DB_AUTH_PASSWORD` (Production and Preview), which an agent generates as it did the others. `BETTER_AUTH_SECRET` (Production and Preview, distinct values) is agent-generated the same way.
- Tables in schema `auth`, created by migrations owned by `app_migrator`, with DML for `app_auth`; `app_backup` gets `SELECT` on the tables spec 0004 R12 lists and nothing else; no other role has privileges. Workflow steps that touch `auth` use the `app_auth` pool. The schema and its tables join the guard allow-list for tables without row-level security, each with the reason. IDs are UUIDs. `auth.user` records the last sign-in time (for the inactivity rule in RETENTION.md). No foreign key from another schema cascades into `auth`.
- Exactly one module in `apps/api` reads the passkey plugin's credential rows; step-up and the device list go through it.
- Better Auth telemetry is disabled in configuration, asserted by a unit test.
- Packages beyond Better Auth and SimpleWebAuthn: none; Resend is called with `fetch` against its REST API.
- Only allow-listed Better Auth endpoints are reachable; every other path under `/v1/auth` answers 404 before Better Auth sees it. The allow-listed endpoints, and the routes of R2 to R7, are declared in `packages/api-contract` with Zod schemas, so they appear in the OpenAPI document and the typed client. The web client never imports a Better Auth client.
- Email and password, magic link, social and anonymous sign-in are not configured. Changing the email address is not offered in this slice and its endpoint is not allow-listed; when it is added, it needs a `sensitive_settings` step-up, confirmation at both addresses and a notice to the old one.
- The request identity helper and the pool's connection check use `app.account_id` instead of `app.person_id`; tests, guards and spec 0001's wording follow.
- `GET /v1/session` returns the signed-in account's ID, email and device description, or 401.

### R2. Enrollment

- **Owner enrollment.** `POST /v1/auth/enroll-owner {code, email}` works only while the `auth` user table is empty **and** the code's hash is not recorded in `auth.setup` as used; otherwise 404. The code's SHA-256 hash is in a repository configuration file; comparison is over hashes in constant time. On success it sends a verification email; the link opens passkey-first registration (R3) with a registration context built like an invite token (256 random bits, stored hashed, single use) that expires after 30 minutes. Issuing a context invalidates any earlier one, and `resolveUser` first inserts the code's hash into `auth.setup` (its primary key, so a concurrent enrollment fails on conflict), then re-checks in the same transaction that the user table is still empty. `auth.setup` is on the no-personal-data list, untouched by erasure and retention, and backed up (spec 0004 R12), so an emptied user table never revives a used code; a later enrollment needs a new code whose hash lands by a reviewed change. The owner generates the code locally with `pnpm enrollment-code` (128 bits from `crypto.randomBytes`, base64url, printed with its SHA-256 hash), keeps it and gives only the hash to an agent to commit; the code never reaches a model or any GitHub surface. The registration request that completes enrollment carries the code again (typed by the owner, never in the email), and `resolveUser` checks its hash before creating the account, so a reader of the stored email cannot enroll.
- **Invites.** A signed-in account (every account is an adult by construction; children are case persons without accounts) creates an invite for an email address (`POST /v1/invites`); the token is 256 random bits, stored as a SHA-256 hash, single use, expiring after 48 hours; at most 10 open invites per account. The invite email carries the link. Opening it shows who invited the person (the inviter's email) and starts passkey-first registration with the token as the passkey plugin's registration context; `resolveUser` creates the account only when the token is valid, unexpired and unused, and marks it used in the same transaction. The account link between inviter and invitee (`account.link`, spec 0005 R4) is written only when the inviter confirms the new account in the app, shown its email and its recipient fingerprint (the invitee is asked to create the vault identity first; if they have not, the screen says so and the fingerprint is compared at the first share), with a `sensitive_settings` step-up, writing an `invite confirmed` event (declining writes `invite declined`); the inviter gets a notice when the invite is accepted, saying the account is unconfirmed. Confirmation sets `confirmed_at` on the account's auth user (owner enrollment sets it at creation); while it is null the account is restricted: the API refuses its invites, case creation, document upload and sharing, and any route that calls a model; it may create its vault identity (no documents), so the inviter can compare its fingerprint at confirmation; declining, or the daily cleanup finding `confirmed_at` still null 30 days after creation, erases it through `eraseAccount` (spec 0004 R9) and frees the address.
- **Link tokens** (invite, enrollment, recovery) travel only in the URL fragment. The web app reads the fragment, clears it from the address bar and sends the token in a POST body; no API route takes these tokens in a path or query parameter, checked by a test over the contract.
- Enrollment ends by showing the account part of the recovery kit (R6) once; the person confirms they saved it before continuing.
- Sign-up by any other path is impossible: the passkey plugin's `resolveUser` rejects a missing or invalid context.
- Owner enrollment, as built: the hash lives in `apps/api/src/auth/enrollment-code-hash.ts` (a development server may override it with `ARCA_ENROLLMENT_CODE_HASH`); the email links to `/enroll#<token>`. `POST /v1/auth/registration/options {token, code}` and `POST /v1/auth/registration/verify {token, code, response}` wrap the passkey plugin's registration endpoints, which stay off the allow-list. Options answer 404 to a dead link, 403 `invalid_code` to a wrong code and 409 `signed_in` to a browser with a live session, so a typo or a signed-in browser costs no passkey; the plugin never sees the request's session cookies, so a link only ever registers the account its context names, even when a session is one Arca no longer counts or appears between options and verify, and a registration replaces the browser's session with the new account's; verify answers 403 `registration_refused` to every refusal. The registration runs in one database transaction (Better Auth's adapter with transactions on, joined by Arca's callbacks): the plugin's `afterVerification`, which runs after the attestation is verified, deletes the context (`DELETE … RETURNING`, so it is single use), checks the code, inserts its hash into `auth.setup`, re-checks that the user table is empty and creates the account with `confirmed_at` set; then the plugin stores the passkey and the session, and the session hook records the passkey's PRF report. `resolveUser`, at options time, only checks the context. Production, which has no sending domain yet, answers 503 `email_unavailable` to enrollment. `owner enrolled` is recorded before the commit, like every security event, so a ceremony that then rolls back leaves that event for an account that never existed. The sign-in event and the last-sign-in time are written after the commit; if they fail, the session is deleted and verify answers 403 although the account and passkey exist, so the enrollment page offers sign-in after a refusal. The web screens, as built: `/enroll` without a fragment asks for the code and the address; with one, it reads the token, clears it from the address bar (also when a link opens in a tab already on the page), asks for the code again and creates the passkey, then goes to `/recovery-kit`. A dead link offers a new one, a refusal offers sign-in. A browser already signed in sees which account it is in and a button to sign out, instead of the passkey prompt; the same holds on `/invite`. The Playwright `enrollment` project runs this flow on an emptied database before every other project, with a synthetic code whose hash the development server reads from `ARCA_ENROLLMENT_CODE_HASH`. Invites, as built: `POST /v1/invites {email}` (403 `account_unconfirmed` from an unconfirmed account, 409 `too_many_invites` past 10 open, 503 `email_unavailable` without a sending domain) stores the token's hash in `auth.invite` (its 48-hour default matches `inviteLifetimeHours` in the contract, which the screens and the email quote, checked by a database test) and emails a link to `/invite#<token>` whose text never names the inviter; a new invite to an address the inviter already invited replaces the open one, and invites never accepted are deleted once expired, with an `invite expired` event, whenever any account sends one. `POST /v1/invites/details {token}` gives the inviter's email for a live link. The same registration routes accept an invite token without a code: in the ceremony's transaction, afterVerification creates the account unconfirmed and marks the invite accepted by it (an update conditioned on the invite being live and unaccepted, so it is single use), recording `invite accepted` in the inviter's trail; once the registration commits, the inviter gets the `invite accepted` notice, which names no one. `GET /v1/invites` lists the inviter's invites that are open or accepted, as `open`, `accepted` (waiting for a decision) or `confirmed`, and `GET /v1/session` says whether the account is `confirmed`. `POST /v1/invites/confirm {inviteId}` and `POST /v1/invites/decline {inviteId}` each need a `sensitive_settings` step-up for their own operation with the invite as the only target (403 `step_up_required` otherwise, 404 unless the invite is the caller's and its account is unconfirmed). Confirming sets `confirmed_at`; declining erases the account's auth rows (the invite goes with it by its cascade) and frees the address. An unconfirmed account cannot hold anything outside the auth schema yet, so this stands in for `eraseAccount` until spec 0004 R9 lands; the 30-day erasure of accounts never confirmed and the daily sweep of expired invites come with the retention jobs (spec 0004 R10); an invite to an address that already has an account opens no registration (404), so no passkey is created for it; the fingerprint comparison and the `account.link` insert come with the vault (spec 0005). The web screens: `/invite` reads the token like `/enroll`, shows who sent the invite and creates the passkey with no code, then goes to `/recovery-kit`; `/invites` sends invites, lists them and, for an accepted one, shows the account's address with the note that its vault identity does not exist yet, and confirms or declines it after the step-up. The home page links to it, or says the account waits for confirmation. Of the restricted routes, only invites exist so far; each later restricted route checks `confirmed_at` the same way. The registration's single transaction relies on Better Auth's Drizzle adapter opening it with `db.transaction` (1.7.14); an upgrade that stops doing so refuses every registration, which the database tests catch.

### R3. Passkeys in the client

- `packages/platform` gains a `Passkeys` port: `create(optionsJSON)` and `get(optionsJSON, { autofill })`, with WebAuthn JSON in and out, plus `isAvailable()`, `supportsAutofill()` and `cancel()` for a ceremony still waiting. The web adapter uses `@simplewebauthn/browser`. UI code calls only the port.
- Registration asks for a resident key, user verification required, and the PRF extension enabled; the server records whether the authenticator reported PRF support (in `auth.passkey_capability`, as built). The options carry exactly `extensions: { prf: {} }`, without the `credProps` SimpleWebAuthn adds, and the contract refuses any extension result but `prf.enabled`. The `Passkeys` port refuses options carrying `prf.eval`, `prf.evalByCredential` or any extension outside its allow-list, and sends only `prf.enabled` among the extension results (ADR-0018); tests: an options fixture with `prf.eval` is refused, and a captured verify request never contains PRF results.
- Sign-in uses discoverable credentials (no email typed) and conditional UI where the browser supports it: the account field offers saved passkeys, and the button starts a ceremony of its own, ending the waiting autofill one. Each ceremony fetches fresh options, since a challenge is single use. Authentication options require user verification, and the server rejects any assertion without the UV flag, with a test. Playwright signs in through Chromium's virtual authenticator against a server with a Postgres database, at phone and desktop sizes, by button and by autofill.
- Screens, all through i18n in pt-BR: sign in, accept invite, owner enrollment, recovery kit, device list, add a passkey, recovery. Touch targets and layouts follow spec 0001 R5.

### R4. Sessions and devices

- Every cookie Arca or Better Auth sets or reads (session, session cache, challenge and the rest) is `__Host-` prefixed (`Path=/`, no `Domain`), so a sibling `filx.app` subdomain cannot plant one; a test checks every `Set-Cookie`. The session cookie is also `Secure`, `HttpOnly`, `SameSite=Lax`; idle timeout 3 days, slid at most once a day and only by `GET /v1/session` (which forwards Better Auth's cookie; every other route reads the session without refreshing it); absolute lifetime 30 days, enforced by a check on the session's creation time. Better Auth's answers on the allow-listed routes are re-encoded through the contract's schemas, so no session token reaches a response body and errors carry Arca's codes.
- Better Auth's origin check on, trusted origins limited to the environment's own origin. Every state-changing `/v1/*` route of our own (not only Better Auth's) passes a Hono middleware that rejects a request whose `Origin` is not the environment's own origin (or, without it, whose `Sec-Fetch-Site` is not `same-origin`, so a sibling `filx.app` subdomain counts as cross-origin), and one that carries neither (a test covers the no-header case); `SameSite=Lax` is not the only guard.
- The session stores a device description derived on the server from the user agent as two closed enums (browser family, operating system family), rendered by the client and the notice templates through i18n; never the raw user agent or the IP address.
- The session stores the credential ID that signed it in (a foreign key that cascades, so deleting a passkey ends its sessions); a session created by any path but a verified passkey ceremony is refused.
- Adding a passkey to an account that already has one needs a `sensitive_settings` step-up. The new passkey cannot sign in or satisfy a step-up for 24 hours; during that window any older active passkey can cancel it from the device list with a `sensitive_settings` step-up, every session shows a banner, and the account gets notices (R7). This is the same rule as a recovery passkey (R6).
- `GET /v1/devices` lists the account's passkeys, each with the sessions it signed in (device description, created, last used, state); `DELETE /v1/devices/sessions/:id` and `DELETE /v1/devices/passkeys/:id` revoke one, after a `sensitive_settings` step-up bound to that target. Revoking a passkey revokes every session it signed in, in the same action. The last **active** passkey cannot be removed; a pending one does not count.
- `POST /v1/devices/sessions/revoke-others` signs out every other session, after a `sensitive_settings` step-up.
- Devices, as built: the revocations are `POST /v1/devices/sessions/revoke {sessionId}`, `POST /v1/devices/passkeys/revoke {passkeyId}` and `POST /v1/devices/sessions/revoke-others {}`, with the target in the body like the invite decisions, since the contract has no path parameters; each spends a `sensitive_settings` step-up for its own operation with its target as the only one (none for the other sessions), and answers 403 `step_up_required` without it and 404 to a target that is not the caller's. `GET /v1/devices` lists the passkeys oldest first, each with its sessions that are unexpired and within the 30-day lifetime, newest use first; last used is the session's last slide, and a session's state is whether it is the caller's own (only live sessions are listed), and a passkey's is `active` or `pending`, with when it becomes active. Revoking a passkey locks the account's passkey rows in one order, so two revocations at once cannot both pass and a step-up the passkey is still recording (its counter update and its row commit in one transaction) is in place before the revocation ends it, answers 409 `last_active_passkey` to the last active one (a pending one does not count), deletes it (its sessions and recorded clients go by their cascades) and deletes the step-ups it verified and nothing spent, an open `vault_unlock` window included, in whichever session; spent ones stay for re-verification. Each revocation records its events before the commit (`passkey revoked`, or one `session revoked` per live session; "sign out others" also deletes the account's dead sessions without recording them); a revoked passkey and "sign out others" (when it ended any session) send their notices after the commit, and a notice that fails is logged without undoing the revocation. Cancelling a pending passkey is the same revocation, with the `pending passkey cancelled` notice instead.
- Adding a passkey, as built: `POST /v1/devices/passkeys/options {}` spends a `sensitive_settings` step-up for its own operation with no target and answers creation options with the same extensions as registration, the account's passkeys as `excludeCredentials` and a fresh user handle; its 32-byte challenge is stored in `auth.passkey_challenge`, bound to the session and the account, for 2 minutes, and expired ones are swept on every new one. `POST /v1/devices/passkeys/add {challengeId, response}` (limited to 10 per hour per session, R10) deletes the challenge first, so it is single use, verifies the attestation with SimpleWebAuthn (user verification required, the environment's origin and RP ID) and, in one transaction, stores the passkey, its PRF report and its `auth.passkey_activation` row (`active_from` 24 hours on), recording `passkey added` before the commit; the `passkey added` notice goes after it. It answers 403 `passkey_refused` to every refusal and creates no session, so the passkey plugin's registration, which signs the new passkey in, is not used. A passkey whose activation row is still in the future cannot sign in (Better Auth's `afterVerification` refuses it, 401), is left out of step-ups and does not count as active; every check compares `active_from` with the time, so the passkey is active once the wait is over, and the row is deleted, recording `passkey activated` with no actor, at the account's next signed-in request, so no job is needed; the trail can therefore show the passkey signing in before its `passkey activated` event, and none at all for one revoked before any such read. A failed activation record is logged and the read still answers. The added passkey starts with the families of the session that added it (R7), as a registered one does. The web screen `/devices` ("Dispositivos", the name the notices use), linked from the home page, lists each passkey with its sessions and its wait, and offers adding a passkey, cancelling a pending one, removing one, disconnecting a session (not the current one) and disconnecting the others, each after its step-up; removing the passkey of the current session forgets the account's cached data. While a passkey waits, the home page of every session shows when it becomes active, with a link to the list. The Playwright `devices` tests add, show and cancel a passkey, and check that a disconnected session's cookie gets 401. `GET /v1/session` carries `pendingPasskeyUntil`, the end of the newest wait, for the banner.

### R5. Step-up

- `POST /v1/auth/step-up/options {purpose, target}` and `POST /v1/auth/step-up/verify {challengeId, response}`, exactly as ADR-0015 describes: the server computes the subject hash from the target, the challenge uses ADR-0015's 4-byte big-endian length-prefixed encoding with a committed test vector, and the challenge row is consumed with `DELETE … RETURNING` before verification. The challenge row stores the session ID and the account ID; verify rejects a `challengeId` from another session and any credential that is not an active credential of that account. Closed purpose enum (`sensitive_settings`, `account_deletion`, `data_export`, `financial_action`, `vault_unlock`, `vault_write`; knowledge-base purposes come with their own spec). A subject hash is required for every purpose except `vault_unlock`, where it is forbidden; for the others it is SHA-256 over the canonical action (route, target IDs, a hash of the security-relevant body fields where the body carries them, such as new bank details, an amount or an export scope, and a 128-bit action nonce the client generates and sends again with the action), defined per route in `packages/api-contract`; single use; 2-minute expiry; RP ID, origin, user presence and user verification checked; revoked credentials rejected; signature counter updated.
- The verified assertion is stored in `auth.step_up` (account, session ID, credential ID, purpose, subject hash, nonce, authenticator data, client data JSON, signature, verified time). A pure function in `apps/api` re-verifies a stored assertion: it recomputes the challenge from the purpose and subject hash **the caller expects** (never the ones stored in the row) and the stored nonce, compares it with `clientDataJSON.challenge`, checks `clientDataJSON.type` is `webauthn.get`, the RP ID hash, origin and flags, that the stored credential ID is the one the caller's key belongs to, and verifies the signature against a public key **the caller supplies**. Consumers that must not trust the database, such as future knowledge-base decisions (keys pinned in the repository), pass their pinned key; nothing in the function reads a credential row. It does not check the signature counter, which verify already did.
- A server-side guard, `requireStepUp(purpose, subject)`, used by routes: it recomputes the subject hash from the request it is serving and consumes atomically (a single `UPDATE … WHERE consumed_at IS NULL … RETURNING`) one step-up of that purpose and subject verified by the same session within 5 minutes. `vault_unlock` alone is a 15-minute window for reading the vault and is not consumed.
- Encoding, as built: the options body carries the target as the route's operation ID (`action`), its target IDs in order (`targets`), its security-relevant body fields as strings (`fields`, at most 16) and the 16-byte action nonce (base64url); the subject hash is SHA-256 over the same 4-byte length-prefixed framing as the challenge: the tag `arca-step-up-action/v1`, the action, the target count and each target, the field count and each key and value in key order, then the nonce. A guarded route reads the nonce from the `arca-step-up-nonce` header. The options list the account's active passkeys as `allowCredentials`, ask for user verification, request no extensions and time out after 2 minutes. Expired challenges, and step-ups never spent once no action can spend them (15 minutes), are swept on every new challenge. Options and verify are each limited to 20 per hour per session (R10). A refused verification answers 403 `step_up_refused`, the same for every reason, so a client can tell it from a lost session (401). The database also refuses a subject for `vault_unlock` and a missing one for the other purposes, and `app_auth` may update only `consumed_at`. The caps (32 targets, 16 fields) are revisited by the first `vault_write` route, whose batch carries one SHA-256 per new object. A pending passkey (R4) is left out of `allowCredentials` and refused by verify, and a revoked one is deleted; adding a passkey opens no session, so the 401 for sessions from pending registrations is needed only by recovery (#60). The first Playwright step-up is the recovery kit's replacement (R6).
- Re-verification tests: an assertion stored for subject A offered as approval of subject B, and one with a mismatched credential, are rejected.
- Tests: a session obtained through a recovery or pending-passkey registration ceremony gets 401 on `GET /v1/session`; a step-up approved for one action (for example, revoking a session) and presented to another of the same purpose (regenerating the kit) is rejected; a challenge replayed, expired, for another purpose, for another subject hash, from another session, signed by a credential of another account, signed by a revoked credential, or signed by a passkey still in its 24-hour inactive window is rejected.

### R6. Recovery

- The recovery kit holds two secrets of 128 random bits each, each shown once as a printable page (to print or copy by hand; a text file is offered only behind a warning that synced folders put it in cloud storage): the account part, the recovery code, shown at enrollment and stored as SHA-256 over a per-account 128-bit salt and the code; and the vault part, the vault recovery secret, shown when the vault is created (spec 0005 R2) only after the recovery envelope is sealed and opened once, and never stored by the server (ADR-0018). Generating a new kit invalidates the old code and needs a `sensitive_settings` step-up. As built: `GET /v1/account/recovery-kit` says whether the kit is missing, unsaved or saved, never the code; `POST /v1/account/recovery-kit` issues the code (16 random bytes as 26 Crockford base32 symbols), without a step-up only when the account has no kit yet and is under a day old, and otherwise only after a step-up for the action `regenerateRecoveryKit` with no targets (403 `step_up_required` without one), recording `recovery kit regenerated` and sending its notice; `POST /v1/account/recovery-kit/confirm` records that it was saved. The web page `/recovery-kit` shows the code once, in groups of four, from the page's own state (never cached or stored in the browser), with print, the text file behind its warning, and a checkbox before continuing; once a kit exists it offers only a new code, after the step-up. Until the kit is saved, the home page says so and links to it.
- `POST /v1/auth/recovery/start {email}` always answers the same way; if the account exists and has no recovery passkey pending, it emails a link valid for 30 minutes, built like an invite token (256 random bits, stored hashed, single use). The link page asks for the recovery code, which is **consumed the moment it is accepted** and exchanged for a single-use recovery-registration context valid until the link's 30 minutes end, so a failed or abandoned passkey ceremony can be retried inside that window with the context, not the code; if the context expires unused, the new code it issued is invalidated too and every session shows that a new kit is needed; the new account recovery code is shown at that moment, before the ceremony, so a lost tab never leaves the account without one; with both, the person registers a new passkey, which stays inactive for 24 hours. Registering the recovery passkey restricts every existing session of the account for the 24 hours (with a notice; this is the moment of the `recovery completed` event): a restricted session can only show the banner and cancel the recovery with a `sensitive_settings` step-up, and every other route answers 403; activation revokes them all and has its own `passkey activated` event. During the 24 hours any other active passkey can cancel the recovery passkey from the device list with a `sensitive_settings` step-up; every session shows a banner while it is pending, and the account gets notices (R7). Cancelling also invalidates the code the recovery issued and closes recovery for the account until the person generates a new kit, which every session shows. After 24 hours the passkey becomes active, and the vault part of the kit follows at the first vault unlock in this order: if the person has a vault, they open it with the old vault recovery secret, an envelope is sealed for the new passkey, then the vault recovery secret is regenerated and the recovery envelope is re-sealed before the vault part of the kit is shown (the account recovery code issued at the start of recovery stays; it is not regenerated twice). A kit is never shown with a vault secret that is not sealed in; if the vault cannot be opened, the kit says the old vault secret still applies.
- Registering a recovery passkey (or a passkey added while another is pending) yields no session: any session the ceremony creates is revoked in the same transaction, and sign-in with a pending credential is refused on the server.
- Five wrong recovery codes lock recovery for the account for 24 hours and send a notice.
- Recovery, as built: `POST /v1/auth/recovery/start {email}` answers `{}` after at least 1.5 seconds whatever the address, and sends the link only when the account has a recovery code that counts, is not locked and has no recovery passkey pending; production, which has no sending domain yet, answers 503 `email_unavailable` to everyone. The floor covers the lookup and a normal send: the answer waits for the send, so a send slower than 1.5 seconds would show that the account exists, and the send moves behind the answer (a workflow carrying identifiers only) before production gets its sending domain. The link is `/recover#<token>` (256 random bits; the server stores its SHA-256 in `auth.recovery_link`, one per account, expiring `recoveryLinkMinutes` from the contract after it is issued); a new start replaces the account's link or open context (a page lost after its code was accepted is resumed this way: only the new code that context issued redeems the new link, and it now lasts as long as the new link; redeeming issues another), deletes every expired one, records `recovery started` with no actor and sends the `recovery started` notice. `POST /v1/auth/recovery/redeem {token, code}` normalizes the typed code (case, spaces, hyphens, O for 0, I or L for 1), compares hashes in constant time and, when it matches, in one transaction replaces the code with a new one whose `provisional_until` is the link's end and swaps the link's token for a new 256-bit registration token; it answers the new code and that token, so the emailed link stops working and someone who also reads the inbox cannot finish the recovery the page opened. A code that counts is one with no `provisional_until` or one still before it, so a lapsed recovery leaves the account with no kit (status `none`), which closes recovery until the person makes a new kit. Wrong codes count per account in `auth.recovery_lock` across links (each records `recovery failed`); the fifth locks recovery for 24 hours, deletes the link and sends the `recovery locked` notice, and a new code a redeemed context issued then lasts until `recoveryLinkMinutes` after the lock ends, so someone holding only the inbox who locks an owner's recovery under way cannot leave the account with no code; the right code resets the count. Someone holding only the inbox can also replace an open context with a new start, which ends the ceremony on the owner's page; the owner resumes with a new link and the new code, and this nuisance is accepted. A redeem while a recovery passkey is pending answers `not_found`, so a start that raced the registration opens nothing. `POST /v1/auth/recovery/options {token}` takes the registration token, stores a 32-byte challenge on the link for 2 minutes (never past the link's end) and answers creation options built like the device list's; `POST /v1/auth/recovery/verify {token, response}` spends the challenge on its first attempt, verifies the attestation and, in one transaction, stores the passkey pending with `recovery` set on its activation row and the families of the device that made it, deletes the link, makes the new code permanent and marks it saved (the page asks the person to confirm they kept it before the passkey step) and records `passkey added` and `recovery completed` with no actor; the `recovery completed` notice goes after the commit. No session is created (no Better Auth endpoint takes part). While a recovery passkey is pending, every session of the account is restricted: `GET /v1/session` says `recoveryPending`, and only the session, the device list, step-up options and verify, revoking that passkey, signing in and out (so a shared device can change hands) and the recovery routes answer; every other `/v1` route answers 403 `recovery_pending`, and so does revoking any other passkey; the device list marks the recovery passkey (`recovery`). Revoking the recovery passkey cancels the recovery: the recovery code goes too and `recovery cancelled` is recorded. Its activation, at the account's first signed-in request after the wait, deletes every session of the account created before `active_from`; each request checks, after the activation, that its own session still exists, so a restricted session is never answered once the wait is over, even when another request ran the activation. Starting is limited to 3 per hour per email HMAC and 10 per hour per IP; redeem, options and verify to 30 per hour per IP each (R10). The web screens, as built: the sign-in page links to `/recover`, which without a fragment asks for the email address and says only that a link is on its way if the address has an account; with one, it reads the token like `/enroll`, asks for the recovery code, shows the new code with the same print, file and checkbox as `/recovery-kit`, and then creates the passkey, ending on a page that says when it becomes active; the new code and the registration token live only in the page's state. While a recovery passkey waits, the home page of every session shows only the recovery notice and a link to the device list, where the recovery passkey is marked and can be cancelled after a step-up, and nothing else is offered. The Playwright `recover` tests run the flow through the outbox in a browser with no session, check that it opens none, that the old session gets 403 `recovery_pending` and can cancel, after which the home page asks for a new kit, and that the old session gets 401 once the passkey is active.

### R7. Audit log and security notices

- Schema `audit`, table `audit.event` (ID, time, actor account ID, subject account ID, event code, request ID, a JSON `details` limited per event code to identifiers and enum values). `time` is a database default that `app_audit` has no column privilege to set, so no caller can backdate an event (an access-matrix case asserts it). Inserted only by `app_audit` through its own pool and password (`ARCA_DB_AUDIT_PASSWORD`, set like the others); no role but `app_migrator` may update or delete; row-level security lets an account read the events whose subject it is. Every event code and its allowed `details` keys are a closed list in code.
- Events: sign-in, sign-in failure (per credential, rate-limited in the log), passkey added, activated, revoked; session revoked; step-up verified (with purpose); invite created, accepted (also a notice to the inviter), confirmed, declined, expired; owner enrolled; recovery started, failed, completed, cancelled; recovery kit regenerated.
- Resend keeps message content (turning it off is not available to Arca, ADR-0015), so the invite email's link is live in Resend's copy for 48 hours, and the account it creates links to nobody until the inviter confirms it; the recovery link is live for 30 minutes and is useless without the recovery code. RETENTION.md records what Resend keeps.
- Notices by email for (spec 0005 later routes every notice through the notification service, which then becomes the only producer; this direct path is replaced, not kept beside it): new passkey (every passkey after the account's first, so always one in its 24-hour window; the first passkey creates the account and sends no notice), new sign-in from a browser or system family not seen before for that passkey (synced passkeys sign in anywhere; the families seen are kept per passkey in `auth.passkey_client`, credential ID plus the two enums and first-seen time, seeded with the registering device's families at registration, deleted with the passkey, registered for erasure and listed in RETENTION.md), passkey revoked, pending passkey cancelled, recovery kit regenerated, recovery started and completed, recovery locked, every session revoked by "sign out others". The email says what happened and when, with the device description at most. Spec 0005 adds the same notices on every device. Because the recovery threat includes a stolen inbox, a pending passkey (added or recovery) is also shown as a banner in every active session and at the next sign-in until it activates or is cancelled.
- `GET /v1/audit/events` lists the signed-in account's events, paginated.

### R8. Email

- An `EmailSender` port in `apps/api` (which may now use `packages/i18n` for the templates, spec 0001 R2) with two adapters: Resend (production only) and an outbox writer (every other environment). Messages are built from i18n templates in pt-BR with generic text and one link; no personal data beyond the recipient address.
- Resend: the sending domain `arca.filx.app` (ADR-0015) added with the São Paulo sending region, SPF and DKIM set, and a DMARC record at `_dmarc.arca.filx.app` with `p=reject; adkim=s; aspf=s`, so mail signed by a sibling `filx.app` subdomain cannot pass as Arca's; the API key is a Sensitive Vercel variable (Production only). The email domain counts as configured when the relying-party configuration file names a sender domain and the Resend key is present; production checks both at startup. The ticket records Resend's log retention for the plan in [RETENTION.md](../RETENTION.md).
- Outbox: table `auth.outbox`, present in every environment so schemas never diverge; production refuses to select the outbox adapter; shown at `/internal/outbox` only on preview deployments, behind Vercel Deployment Protection; rows expire after 7 days.

### R9. Relying party and environments

- A repository configuration file names the production relying-party ID and origin (`arca.filx.app`, ADR-0015). While it is empty, or while no email domain is configured (R8), production refuses owner enrollment, invites, registration and recovery with a clear error code, and the web app shows that sign-in is not available yet.
- A preview uses its branch URL host (`VERCEL_BRANCH_URL`) as relying-party ID and origin; ceremonies from any other origin, including the per-deployment URL, are rejected.
- Local development uses `localhost`, which WebAuthn treats as a secure context.

### R10. Rate limits

- Every allow-listed auth endpoint is limited per IP HMAC through our own limiter below. Better Auth's built-in limiter cannot be used: it needs IP tracking, which Arca turns off so no address is stored (checked in Better Auth 1.7.14). Abandoned sign-in challenges are also swept whenever a new one is issued, so `auth.verification` stays bounded. The per-route limits live in `apps/api/src/auth/limits.ts`, keyed by operation ID so an allow-listed route does not compile without one: sign-in options 120 per hour, sign-in 30 per hour, sign-out 60 per hour, per IP (generous for a family behind one address, whose open sign-in screen refreshes its options every 4 minutes). Over a limit the API answers 429 `rate_limited` with `Retry-After`, before Better Auth or body validation. The IP is Vercel's `x-vercel-forwarded-for`, which the edge overwrites, so a client cannot choose its own counter; a local server counts as one client. An IPv6 client counts by its /64, the block one home or phone usually gets, and an IPv4-mapped address as its IPv4 address. Every open sign-in tab counts, background ones included, so many tabs left open behind one address spend the options budget sooner. A request whose `Sec-Fetch-Site` is present and not `same-origin` is refused with 403 `cross_origin` before it is counted, so another site cannot spend the budget of the people behind an address; clients that send no such header, such as native apps, are counted as usual. The app refuses to start with auth routes but no limits.
- Our own limits, stored in `auth.rate_limit` (written by `app_auth`, on the no-row-level-security allow-list, never backed up), keyed by an HMAC of the IP address or the email address (never the value itself), or by account; the HMAC key is a Sensitive Vercel variable per environment, `ARCA_RATE_LIMIT_KEY` (at least 32 characters), never stored in the database, generated by an agent and rotated monthly (rotation simply resets the counters). Counters are fixed windows updated by one upsert, so concurrent hits never lose a count, and a daily cron route deletes ended windows. The `sign_in_failed` event (R7) uses the same helper: one event per credential per hour, only for a passkey that exists, with no actor. Step-up options and verify are each limited to 20 per hour per session, and storing an added passkey to 10 per hour per session. Owner enrollment is limited to 5 per hour per IP, and registration options and verify to 30 per hour per IP each. Sending invites is limited to 20 per day per account, and reading who sent an invite link to 30 per hour per IP. Recovery start is limited to 3 per hour per email HMAC and 10 per hour per IP, and recovery redeem, options and verify to 30 per hour per IP each.
- An edge rule in Vercel Firewall limits `/v1/auth/*` per IP. If the rule cannot be versioned in the repository, an agent applies it through the Vercel API after the owner's OK, and the ticket records it. As built: Vercel WAF rate-limit rules cannot live in `vercel.json` (only deny and challenge routes can; [Vercel WAF rate limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting), checked 2026-11-04), so after the owner's OK the rule `arca-auth-rate-limit` was applied through the API on 2026-11-04: paths starting with `/v1/auth/`, a fixed window of 60 requests per minute per IP, denied (429) for one minute beyond it.

## Threat model for this slice

Assets: passkeys, sessions, recovery codes, invites, the enrollment code, stored step-up assertions, the audit log.

| Threat (STRIDE, agentic) | Where | Control |
| --- | --- | --- |
| Spoofing: account takeover by phishing | Sign-in | Passkeys only, bound to the relying-party ID; no passwords or magic links |
| Spoofing: takeover through the inbox | Recovery | Email link and recovery code both required; code consumed on use; 24-hour inactive period, cancellable only with an active passkey; a cancel closes recovery until a new kit; existing sessions stay alive, restricted to the banner and cancel, so the warning reaches the person's own devices; notices; removing a notification channel needs a step-up |
| Spoofing: strangers creating accounts | Enrollment, invites | Invite-only; an invited account stays restricted until its inviter confirms it, and is erased if declined or unconfirmed after 30 days; enrollment code works on an empty database only and never twice (`auth.setup`); `resolveUser` rejects any other context |
| Tampering: replay or reuse of a step-up | Step-up | Single-use challenge bound to purpose, subject and session; 2-minute expiry; UV required; counter checked |
| Elevation: a step-up spent on another action by someone sharing the session | Step-up | Subject = hash of the canonical action for every purpose but `vault_unlock`; the route recomputes it and consumes atomically |
| Spoofing: a thief with an unlocked device takes over through one passkey | Devices, recovery | Notices on every factor change; device list tells the person to revoke a lost device first; accepted residual in ADR-0015 until the designated-adult factor |
| Spoofing: a lost device keeps its session after its passkey is revoked | Devices | Sessions record their credential; revoking a passkey revokes its sessions; completing recovery restricts every session to the banner and cancel, and activation of the recovery passkey revokes them |
| Information disclosure: link tokens in logs or history | Email links | Tokens only in the URL fragment, sent in POST bodies |
| Repudiation: "I never approved that" | Step-up, audit | Stored assertion re-verifiable against the credential; append-only audit log |
| Information disclosure: account enumeration | Recovery, invites | Identical responses; rate limits |
| Information disclosure: device fingerprinting data at rest | Sessions | Browser and OS family only; no IP or raw user agent stored |
| Spoofing: a synced passkey used elsewhere without a notice | Sign-in | New-family notice per passkey; accepted residual: the families come from the user agent, which the person holding the passkey controls, so copying the victim's browser and system families avoids the notice |
| Elevation: a preview passkey used in production | Relying party | RP ID per environment; production RP ID fixed in the repository |
| Denial of service: brute force on codes | Enrollment, recovery | 128-bit codes; per-IP and per-account limits; recovery lockout |
| Elevation: `app_auth` reaching case data | Database | `app_auth` has privileges on `auth` only; guards unchanged for every other schema |
| Tampering: a DB-owner attacker writing to `auth` | Database | Accepted residual of ADR-0012: someone holding the owner connection can insert a credential, a session row (sign-in with no passkey, notice or audit event) or `auth.step_up` rows the guard trusts. Only consumers that pin keys outside the database resist (planned for knowledge-base decisions); new passkeys notify the account |

## Definition of done

- Every requirement is covered by a test: unit tests for the step-up challenge and re-verification, database tests for privileges and the audit log's grants, and Playwright with a virtual authenticator (with PRF) for enrollment, invite, sign-in, step-up, recovery and device revocation at phone and desktop sizes.
- The access-matrix suite covers `app_auth` and `app_audit`.
- A preview shows invite, sign-in, step-up, recovery and devices with the outbox; owner enrollment is proven in Playwright against an empty database, since seeded previews already have accounts; production refuses enrollment until the relying-party file names the host and an email domain is configured.
- No user-facing string outside i18n; no personal data in fixtures, logs or telemetry.
