# Spec 0003: Identity and access

- Status: Ready for tickets
- Date: 2026-11-02
- Epic: cross-platform foundations ([ROADMAP.md](../ROADMAP.md#phase-1--family-mvp-web)), after [spec 0001](0001-foundations-scaffold.md)
- Decisions: [ADR-0015](../adr/0015-identity-enrollment-step-up-and-recovery.md), [ADR-0006](../adr/0006-auth.md), [ADR-0008](../adr/0008-database-security-and-environments.md), [ADR-0012](../adr/0012-automation-first-setup.md); consumers: future knowledge-base decisions (ADR-0014, proposed in pull request #39), [ADR-0017](../adr/0017-data-lifecycle-and-backups.md) (deletion and export), [ADR-0018](../adr/0018-vault-encryption.md) (vault unlock)

## Goal

Members of the family sign in with passkeys, invited by someone already in, on every environment; sensitive actions ask for a fresh passkey verification bound to what is being done; a lost device is recoverable without making the inbox the master key; every security event is recorded and visible to the person it concerns.

## Scope

**In:** Better Auth with the passkey plugin behind an endpoint allow-list; the `auth` schema and the `app_auth` pool; owner enrollment and invites; passkey sign-in and registration in the web client through the `platform` passkey port; sessions, device list and revocation; purpose-bound step-up; recovery with the email link and the recovery code; the audit log and security notices by email; email through Resend with a non-production outbox; rate limits; the relying party per environment; the `app.account_id` rename.

**Out:** bearer tokens for native apps (Phase 4); the designated-adult recovery factor (with the case model); push notices (spec 0005); account deletion and export (spec 0004, which uses this spec's step-up); the vault (spec 0005).

**No case data.** Accounts hold an email address, passkeys and sessions; the seed and tests use synthetic addresses on reserved domains (`example.com`, `example.org`).

## Requirements

### R1. Auth module, schema and pool

- `better-auth` and `@better-auth/passkey` at the newest release at least 7 days old (1.7.x as of 2026-11-02), and `@simplewebauthn/server` and `@simplewebauthn/browser` as direct dependencies at the 13.x the plugin resolves (one copy of the verifier; move to 14 when the plugin does), added to the Versions table of spec 0001 with a supply-chain PASS.
- Better Auth runs inside `apps/api` under `/v1/auth`, with the Drizzle adapter on its own pool connected as `app_auth` (pooled host, explicit user and password, `current_user` checked per connection, as spec 0001 R7 does for `app_api`). `bootstrap.sql` sets the `app_auth` password from a new Sensitive variable, `ARCA_DB_AUTH_PASSWORD` (Production and Preview), which an agent generates as it did the others. `BETTER_AUTH_SECRET` (Production and Preview, distinct values) is agent-generated the same way.
- Tables in schema `auth`, created by migrations owned by `app_migrator`, with DML for `app_auth`; `app_backup` gets `SELECT` on the tables spec 0004 R12 lists and nothing else; no other role has privileges. Workflow steps that touch `auth` use the `app_auth` pool. The schema and its tables join the guard allow-list for tables without row-level security, each with the reason. IDs are UUIDs. `auth.user` records the last sign-in time (for the inactivity rule in RETENTION.md). No foreign key from another schema cascades into `auth`.
- Exactly one module in `apps/api` reads the passkey plugin's credential rows; step-up and the device list go through it.
- Better Auth telemetry is disabled in configuration, asserted by a unit test.
- Packages beyond Better Auth and SimpleWebAuthn: none; Resend is called with `fetch` against its REST API.
- Only allow-listed Better Auth endpoints are reachable; every other path under `/v1/auth` answers 404 before Better Auth sees it. The allow-listed endpoints, and the routes of R2 to R7, are declared in `packages/api-contract` with Zod schemas, so they appear in the OpenAPI document and the typed client. The web client never imports a Better Auth client.
- Email and password, magic link, social and anonymous sign-in are not configured. Changing the email address is not offered in this slice and its endpoint is not allow-listed; when it is added, it needs a `sensitive_settings` step-up, confirmation at both addresses and a notice to the old one.
- The request identity helper and the pool's connection check use `app.account_id` instead of `app.person_id`; tests, guards and spec 0001's wording follow.
- `GET /v1/session` returns the signed-in account's ID, email and device description, or 401.

### R2. Enrollment

- **Owner enrollment.** `POST /v1/auth/enroll-owner {code, email}` works only while the `auth` user table is empty **and** the code's hash is not recorded in `auth.setup` as used; otherwise 404. The code's SHA-256 hash is in a repository configuration file; comparison is over hashes in constant time. On success it sends a verification email; the link opens passkey-first registration (R3) with a registration context built like an invite token (256 random bits, stored hashed, single use) that expires after 30 minutes. Issuing a context invalidates any earlier one, and `resolveUser` first inserts the code's hash into `auth.setup` (its primary key, so a concurrent enrollment fails on conflict), then re-checks in the same transaction that the user table is still empty. `auth.setup` is on the no-personal-data list, untouched by erasure and retention, and backed up (spec 0004 R12), so an emptied user table never revives a used code; a later enrollment needs a new code whose hash lands by a reviewed change. The owner generates the code locally with `pnpm enrollment-code` (128 bits from `crypto.randomBytes`, base64url, printed with its SHA-256 hash), keeps it and gives only the hash to an agent to commit; the code never reaches a model or any GitHub surface. The registration request that completes enrollment carries the code again (typed by the owner, never in the email), and `resolveUser` checks its hash before creating the account, so a reader of the stored email cannot enroll.
- **Invites.** A signed-in account (every account is an adult by construction; children are case persons without accounts) creates an invite for an email address (`POST /v1/invites`); the token is 256 random bits, stored as a SHA-256 hash, single use, expiring after 48 hours; at most 10 open invites per account. The invite email carries the link. Opening it shows who invited the person (the inviter's email) and starts passkey-first registration with the token as the passkey plugin's registration context; `resolveUser` creates the account only when the token is valid, unexpired and unused, and marks it used in the same transaction. The account link between inviter and invitee (`account.link`, spec 0005 R4) is written only when the inviter confirms the new account in the app, shown its email and its recipient fingerprint (the invitee is asked to create the vault identity first; if they have not, the screen says so and the fingerprint is compared at the first share), with a `sensitive_settings` step-up, writing an `invite confirmed` event (declining writes `invite declined`); the inviter gets a notice when the invite is accepted, saying the account is unconfirmed. Confirmation sets `confirmed_at` on the account's auth user (owner enrollment sets it at creation); while it is null the account is restricted: the API refuses its invites, case creation, document upload and sharing, and any route that calls a model; it may create its vault identity (no documents), so the inviter can compare its fingerprint at confirmation; declining, or the daily cleanup finding `confirmed_at` still null 30 days after creation, erases it through `eraseAccount` (spec 0004 R9) and frees the address.
- **Link tokens** (invite, enrollment, recovery) travel only in the URL fragment. The web app reads the fragment, clears it from the address bar and sends the token in a POST body; no API route takes these tokens in a path or query parameter, checked by a test over the contract.
- Enrollment ends by showing the account part of the recovery kit (R6) once; the person confirms they saved it before continuing.
- Sign-up by any other path is impossible: the passkey plugin's `resolveUser` rejects a missing or invalid context.

### R3. Passkeys in the client

- `packages/platform` gains a `Passkeys` port: `create(optionsJSON)` and `get(optionsJSON)`, with WebAuthn JSON in and out, plus `isAvailable()`. The web adapter uses `@simplewebauthn/browser`. UI code calls only the port.
- Registration asks for a resident key, user verification required, and the PRF extension enabled; the server records whether the authenticator reported PRF support. The `Passkeys` port refuses options carrying `prf.eval`, `prf.evalByCredential` or any extension outside its allow-list, and sends only `prf.enabled` among the extension results (ADR-0018); tests: an options fixture with `prf.eval` is refused, and a captured verify request never contains PRF results.
- Sign-in uses discoverable credentials (no email typed) and conditional UI where the browser supports it. Authentication options require user verification, and the server rejects any assertion without the UV flag, with a test.
- Screens, all through i18n in pt-BR: sign in, accept invite, owner enrollment, recovery kit, device list, add a passkey, recovery. Touch targets and layouts follow spec 0001 R5.

### R4. Sessions and devices

- Cookie `__Host-` prefixed, `Secure`, `HttpOnly`, `SameSite=Lax`; idle timeout 3 days; absolute lifetime 30 days, enforced by a check on the session's creation time.
- Better Auth's origin check on, trusted origins limited to the environment's own origin. Every state-changing `/v1/*` route of our own (not only Better Auth's) passes a Hono middleware that rejects a request whose `Origin` (or, without it, `Sec-Fetch-Site`) is not the environment's own origin, and one that carries neither (a test covers the no-header case); `SameSite=Lax` is not the only guard.
- The session stores a device description derived on the server from the user agent as two closed enums (browser family, operating system family), rendered by the client and the notice templates through i18n; never the raw user agent or the IP address.
- The session stores the credential ID that signed it in.
- Adding a passkey to an account that already has one needs a `sensitive_settings` step-up. The new passkey cannot sign in or satisfy a step-up for 24 hours; during that window any older active passkey can cancel it from the device list with a `sensitive_settings` step-up, every session shows a banner, and the account gets notices (R7). This is the same rule as a recovery passkey (R6).
- `GET /v1/devices` lists the account's passkeys, each with the sessions it signed in (device description, created, last used, state); `DELETE /v1/devices/sessions/:id` and `DELETE /v1/devices/passkeys/:id` revoke one, after a `sensitive_settings` step-up bound to that target. Revoking a passkey revokes every session it signed in, in the same action. The last **active** passkey cannot be removed; a pending one does not count.
- `POST /v1/devices/sessions/revoke-others` signs out every other session, after a `sensitive_settings` step-up.

### R5. Step-up

- `POST /v1/auth/step-up/options {purpose, target}` and `POST /v1/auth/step-up/verify {challengeId, response}`, exactly as ADR-0015 describes: the server computes the subject hash from the target, the challenge uses ADR-0015's 4-byte big-endian length-prefixed encoding with a committed test vector, and the challenge row is consumed with `DELETE … RETURNING` before verification. The challenge row stores the session ID and the account ID; verify rejects a `challengeId` from another session and any credential that is not an active credential of that account. Closed purpose enum (`sensitive_settings`, `account_deletion`, `data_export`, `financial_action`, `vault_unlock`, `vault_write`; knowledge-base purposes come with their own spec). A subject hash is required for every purpose except `vault_unlock`, where it is forbidden; for the others it is SHA-256 over the canonical action (route, target IDs, a hash of the security-relevant body fields where the body carries them, such as new bank details, an amount or an export scope, and a 128-bit action nonce the client generates and sends again with the action), defined per route in `packages/api-contract`; single use; 2-minute expiry; RP ID, origin, user presence and user verification checked; revoked credentials rejected; signature counter updated.
- The verified assertion is stored in `auth.step_up` (account, session ID, credential ID, purpose, subject hash, nonce, authenticator data, client data JSON, signature, verified time). A pure function in `apps/api` re-verifies a stored assertion: it recomputes the challenge from the purpose and subject hash **the caller expects** (never the ones stored in the row) and the stored nonce, compares it with `clientDataJSON.challenge`, checks `clientDataJSON.type` is `webauthn.get`, the RP ID hash, origin and flags, that the stored credential ID is the one the caller's key belongs to, and verifies the signature against a public key **the caller supplies**. Consumers that must not trust the database, such as future knowledge-base decisions (keys pinned in the repository), pass their pinned key; nothing in the function reads a credential row. It does not check the signature counter, which verify already did.
- A server-side guard, `requireStepUp(purpose, subject)`, used by routes: it recomputes the subject hash from the request it is serving and consumes atomically (a single `UPDATE … WHERE consumed_at IS NULL … RETURNING`) one step-up of that purpose and subject verified by the same session within 5 minutes. `vault_unlock` alone is a 15-minute window for reading the vault and is not consumed.
- Re-verification tests: an assertion stored for subject A offered as approval of subject B, and one with a mismatched credential, are rejected.
- Tests: a session obtained through a recovery or pending-passkey registration ceremony gets 401 on `GET /v1/session`; a step-up approved for one action (for example, revoking a session) and presented to another of the same purpose (regenerating the kit) is rejected; a challenge replayed, expired, for another purpose, for another subject hash, from another session, signed by a credential of another account, signed by a revoked credential, or signed by a passkey still in its 24-hour inactive window is rejected.

### R6. Recovery

- The recovery kit holds two secrets of 128 random bits each, each shown once as a printable page (to print or copy by hand; a text file is offered only behind a warning that synced folders put it in cloud storage): the account part, the recovery code, shown at enrollment and stored as SHA-256 over a per-account 128-bit salt and the code; and the vault part, the vault recovery secret, shown when the vault is created (spec 0005 R2) only after the recovery envelope is sealed and opened once, and never stored by the server (ADR-0018). Generating a new kit invalidates the old code and needs a `sensitive_settings` step-up.
- `POST /v1/auth/recovery/start {email}` always answers the same way; if the account exists and has no recovery passkey pending, it emails a link valid for 30 minutes, built like an invite token (256 random bits, stored hashed, single use). The link page asks for the recovery code, which is **consumed the moment it is accepted** and exchanged for a single-use recovery-registration context valid until the link's 30 minutes end, so a failed or abandoned passkey ceremony can be retried inside that window with the context, not the code; if the context expires unused, the new code it issued is invalidated too and every session shows that a new kit is needed; the new account recovery code is shown at that moment, before the ceremony, so a lost tab never leaves the account without one; with both, the person registers a new passkey, which stays inactive for 24 hours. Registering the recovery passkey restricts every existing session of the account for the 24 hours (with a notice; this is the moment of the `recovery completed` event): a restricted session can only show the banner and cancel the recovery with a `sensitive_settings` step-up, and every other route answers 403; activation revokes them all and has its own `passkey activated` event. During the 24 hours any other active passkey can cancel the recovery passkey from the device list with a `sensitive_settings` step-up; every session shows a banner while it is pending, and the account gets notices (R7). Cancelling also invalidates the code the recovery issued and closes recovery for the account until the person generates a new kit, which every session shows. After 24 hours the passkey becomes active, and the vault part of the kit follows at the first vault unlock in this order: if the person has a vault, they open it with the old vault recovery secret, an envelope is sealed for the new passkey, then the vault recovery secret is regenerated and the recovery envelope is re-sealed before the vault part of the kit is shown (the account recovery code issued at the start of recovery stays; it is not regenerated twice). A kit is never shown with a vault secret that is not sealed in; if the vault cannot be opened, the kit says the old vault secret still applies.
- Registering a recovery passkey (or a passkey added while another is pending) yields no session: any session the ceremony creates is revoked in the same transaction, and sign-in with a pending credential is refused on the server.
- Five wrong recovery codes lock recovery for the account for 24 hours and send a notice.

### R7. Audit log and security notices

- Schema `audit`, table `audit.event` (ID, time, actor account ID, subject account ID, event code, request ID, a JSON `details` limited per event code to identifiers and enum values). `time` is a database default that `app_audit` has no column privilege to set, so no caller can backdate an event (an access-matrix case asserts it). Inserted only by `app_audit` through its own pool and password (`ARCA_DB_AUDIT_PASSWORD`, set like the others); no role but `app_migrator` may update or delete; row-level security lets an account read the events whose subject it is. Every event code and its allowed `details` keys are a closed list in code.
- Events: sign-in, sign-in failure (per credential, rate-limited in the log), passkey added, activated, revoked; session revoked; step-up verified (with purpose); invite created, accepted (also a notice to the inviter), confirmed, declined, expired; owner enrolled; recovery started, failed, completed, cancelled; recovery kit regenerated.
- Resend keeps message content (turning it off is not available to Arca, ADR-0015), so the invite email's link is live in Resend's copy for 48 hours, and the account it creates links to nobody until the inviter confirms it; the recovery link is live for 30 minutes and is useless without the recovery code. RETENTION.md records what Resend keeps.
- Notices by email for (spec 0005 later routes every notice through the notification service, which then becomes the only producer; this direct path is replaced, not kept beside it): new passkey, new sign-in from a browser or system family not seen before for that passkey (synced passkeys sign in anywhere; the families seen are kept per passkey in `auth.passkey_client`, credential ID plus the two enums and first-seen time, deleted with the passkey, registered for erasure and listed in RETENTION.md), passkey revoked, pending passkey cancelled, recovery kit regenerated, recovery started and completed, recovery locked, every session revoked by "sign out others". The email says what happened and when, with the device description at most. Spec 0005 adds the same notices on every device. Because the recovery threat includes a stolen inbox, a pending passkey (added or recovery) is also shown as a banner in every active session and at the next sign-in until it activates or is cancelled.
- `GET /v1/audit/events` lists the signed-in account's events, paginated.

### R8. Email

- An `EmailSender` port in `apps/api` with two adapters: Resend (production only) and an outbox writer (every other environment). Messages are built from i18n templates in pt-BR with generic text and one link; no personal data beyond the recipient address.
- Resend: the email domain (one the project owns; ADR-0015) added with the São Paulo sending region, SPF, DKIM and DMARC set; the API key is a Sensitive Vercel variable (Production only). The ticket records Resend's log retention for the plan in [RETENTION.md](../RETENTION.md).
- Outbox: table `auth.outbox`, present in every environment so schemas never diverge; production refuses to select the outbox adapter; shown at `/internal/outbox` only on preview deployments, behind Vercel Deployment Protection; rows expire after 7 days.

### R9. Relying party and environments

- A repository configuration file names the production relying-party ID and origin (for now the project's `vercel.app` host, ADR-0015). While it is empty, production refuses owner enrollment, invites, registration and recovery with a clear error code, and the web app shows that sign-in is not available yet. While no email domain is configured, production refuses invites and recovery with their own error code.
- A preview uses its branch URL host (`VERCEL_BRANCH_URL`) as relying-party ID and origin; ceremonies from any other origin, including the per-deployment URL, are rejected.
- Local development uses `localhost`, which WebAuthn treats as a secure context.

### R10. Rate limits

- Better Auth's rate limiter with database storage, on by default for every auth endpoint.
- Our own limits, stored in `auth.rate_limit` (written by `app_auth`, on the no-row-level-security allow-list, never backed up), keyed by an HMAC of the IP address or the email address (never the value itself), or by account; the HMAC key is a Sensitive Vercel variable per environment, never stored in the database, generated by an agent and rotated monthly (rotation simply resets the counters): enrollment 5 per hour per IP; recovery start 3 per hour per email HMAC and 10 per hour per IP; step-up options 20 per hour per session; invites 20 per day per account.
- An edge rule in Vercel Firewall limits `/v1/auth/*` per IP. If the rule cannot be versioned in the repository, an agent applies it through the Vercel API after the owner's OK, and the ticket records it.

## Threat model for this slice

Assets: passkeys, sessions, recovery codes, invites, the enrollment code, stored step-up assertions, the audit log.

| Threat (STRIDE, agentic) | Where | Control |
| --- | --- | --- |
| Spoofing: account takeover by phishing | Sign-in | Passkeys only, bound to the relying-party ID; no passwords or magic links |
| Spoofing: takeover through the inbox | Recovery | Email link and recovery code both required; code consumed on use; 24-hour inactive period, cancellable only with an active passkey; a cancel closes recovery until a new kit; existing sessions stay alive, restricted to the banner and cancel, so the warning reaches the person's own devices; notices; removing a notification channel needs a step-up |
| Spoofing: strangers creating accounts | Enrollment, invites | Invite-only; an invited account stays restricted until its inviter confirms it, and is erased if declined or unconfirmed after 30 days; enrollment code works on an empty database only and never twice (`auth.setup`); `resolveUser` rejects any other context |
| Tampering: replay or reuse of a step-up | Step-up | Single-use challenge bound to purpose, subject and session; 2-minute expiry; UV required; counter checked |
| Elevation: a step-up spent on another action by someone sharing the session | Step-up | Subject = hash of the canonical action for every purpose but `vault_unlock`; the route recomputes it and consumes atomically |
| Spoofing: a thief with an unlocked device takes over through one passkey | Devices, recovery | Notices on every factor change; device list tells the person to revoke a lost device first; accepted residual in ADR-0015 until the designated-adult factor |
| Spoofing: a lost device keeps its session after its passkey is revoked | Devices | Sessions record their credential; revoking a passkey revokes its sessions; completing recovery restricts every session to the banner and cancel, and activation of the recovery passkey revokes them |
| Information disclosure: link tokens in logs or history | Email links | Tokens only in the URL fragment, sent in POST bodies |
| Repudiation: "I never approved that" | Step-up, audit | Stored assertion re-verifiable against the credential; append-only audit log |
| Information disclosure: account enumeration | Recovery, invites | Identical responses; rate limits |
| Information disclosure: device fingerprinting data at rest | Sessions | Browser and OS family only; no IP or raw user agent stored |
| Elevation: a preview passkey used in production | Relying party | RP ID per environment; production RP ID fixed in the repository |
| Denial of service: brute force on codes | Enrollment, recovery | 128-bit codes; per-IP and per-account limits; recovery lockout |
| Elevation: `app_auth` reaching case data | Database | `app_auth` has privileges on `auth` only; guards unchanged for every other schema |
| Tampering: a DB-owner attacker writing to `auth` | Database | Accepted residual of ADR-0012: someone holding the owner connection can insert a credential, a session row (sign-in with no passkey, notice or audit event) or `auth.step_up` rows the guard trusts. Only consumers that pin keys outside the database resist (planned for knowledge-base decisions); new passkeys notify the account |

## Definition of done

- Every requirement is covered by a test: unit tests for the step-up challenge and re-verification, database tests for privileges and the audit log's grants, and Playwright with a virtual authenticator (with PRF) for enrollment, invite, sign-in, step-up, recovery and device revocation at phone and desktop sizes.
- The access-matrix suite covers `app_auth` and `app_audit`.
- A preview shows invite, sign-in, step-up, recovery and devices with the outbox; owner enrollment is proven in Playwright against an empty database, since seeded previews already have accounts; production refuses enrollment until the relying-party file names the host, and invites and recovery until an email domain is configured.
- No user-facing string outside i18n; no personal data in fixtures, logs or telemetry.
