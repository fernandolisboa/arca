# Spec 0005: Vault, device capabilities and notifications

- Status: Ready for tickets
- Date: 2026-11-02
- Epic: cross-platform foundations ([ROADMAP.md](../ROADMAP.md#phase-1--family-mvp-web)), after [spec 0003](0003-identity-and-access.md)
- Decisions: [ADR-0018](../adr/0018-vault-encryption.md), [ADR-0005](../adr/0005-platform-strategy.md), [ADR-0008](../adr/0008-database-security-and-environments.md), [ADR-0017](../adr/0017-data-lifecycle-and-backups.md) (registry), [ADR-0021](../adr/0021-stay-on-vercel-and-neon.md) (Vercel Blob, sensitive fields in the vault, no AWS), [ADR-0009](../adr/0009-background-jobs-guarantees.md)

## Goal

The pieces that native phases will only add adapters to: an encrypted document vault with a documented, platform-neutral format and tested recovery; sensitive fields (bank account and document numbers) kept in the vault too; the `platform` port with web adapters and a conformance suite; and a notification service with per-device channels, web push first.

## Scope

**In:** `packages/vault`; vault identity, envelopes, unlock and recovery; document storage as ciphertext in a private Vercel Blob store; sharing, revocation and rotation; sensitive fields in the vault; `platform` capabilities with web adapters; notifications through web push and email.

**Out:** document review, OCR and the `DocumentReader` adapter (Phase 2), but the processing path is fixed by ADR-0018; any document type catalog (data, with the consultancy core); native adapters (Phases 4 to 6).

**Not on the critical path of the consultancy core's case model**, which stores no documents. The vault must exist before any document upload is built; notifications before the plan sends reminders.

## Requirements

### R1. Vault core

- New package `packages/vault`, pure TypeScript with no workspace dependencies and no platform calls (boundary matrix: `apps/web` may depend on it; the API never decrypts and does not depend on it). `packages/platform` also depends on `age-encryption` for the envelope port (R5), and on `packages/vault` for its `VaultIdentity` and share-key types only (type imports, enforced by the boundary rule); the boundary matrix lists all three. It wraps `age-encryption` (newest release at least 7 days old; 0.3.x as of 2026-11-02), added to the Versions table with a supply-chain PASS.
- A sharing-state module in `packages/vault` owns ADR-0018's sharing state: encode (length-prefixed), tag, verify, compare versions, compute the difference the owner confirms, and re-tag under a new share key; table-driven vectors cover a valid state, a wrong tag, an older state relabelled with a higher version, another account's state and a lower restored version. `apps/web` only renders the confirmation.
- API: generate a hybrid identity; encrypt and decrypt documents as streams to a recipient set; seal and open the scrypt recovery envelope with the vault recovery secret; re-encrypt to a new recipient set. Passkey envelopes are not sealed here: the `VaultEnvelopes` port (R5) owns them, and `packages/vault` never receives a PRF recipient (ADR-0018).
- The C2SP age test vectors run in CI against the package, plus vectors pinned at adoption for the `mlkem768x25519` stanza where CCTV does not cover it (ADR-0018). Round-trip, multi-recipient, revocation, rotation and wrong-key tests are table-driven.
- The format is documented in `docs/vault-format.md`: file layout (plain age), recipient types, envelope kinds, how native apps reproduce each with other age implementations.

### R2. Vault identity, unlock and recovery

- Tables in schema `vault`, under row-level security by account, registered in the personal-data registry (ADR-0017): `vault.recipient` (account, age recipient, created, rotated), `vault.envelope` (account, the recipient whose identity it holds, kind `passkey_prf` or `recovery`, credential ID for `passkey_prf`, the age ciphertext) and `vault.sharing_state` (account, version, the serialized state, its HMAC-SHA-256 tag over the domain tag, account ID, version and state, length-prefixed; ADR-0018). After a rotation the old identity's envelopes stay beside the new ones until every sharing owner has re-encrypted, or 90 days.
- First use: the device generates the identity, the share key and the vault recovery secret; seals one envelope per PRF-capable passkey through the `VaultEnvelopes` port and one with the recovery secret; opens the recovery envelope once as a check; uploads the recipient and envelopes; and only then shows the vault part of the recovery kit (spec 0003 R6). Playwright covers that the recovery envelope opens before the vault is used. A new passkey with PRF gets its envelope at its next unlock.
- Unlock: the API serves envelopes and download URLs only after a `vault_unlock` step-up less than 15 minutes old (spec 0003 R5); then the platform port's PRF ceremony opens the matching envelope; without PRF, the person enters the recovery secret once and the identity is kept wrapped by a non-extractable key through the key-storage port, with the AES-GCM construction ADR-0018 names (R5). The identity stays in memory only and is dropped on sign-out, after 15 minutes idle, or after 15 minutes hidden.
- Revoking a passkey, or cancelling one in its 24-hour window, first deletes its `passkey_prf` envelope (keyed by credential ID, as `app_api` under the account's identity, idempotent), then revokes the passkey on the `app_auth` pool; the envelope route reads the account's active credential IDs on the `app_auth` pool and serves envelopes only for those, so an orphan is never served. It also offers identity rotation (ADR-0018), on by default when the passkey had PRF or its device held a wrapped identity.
- Recovery after losing every passkey: account recovery (spec 0003) then the recovery secret opens the recovery envelope; new envelopes are sealed for the new passkey.
- Regenerating the recovery kit re-seals every recovery envelope the account keeps to the new secret (a rotated identity's still-retained one included), so the old secret stops working for any of them, in the order spec 0003 R6 fixes; a kit is never shown with a vault secret that is not sealed in.
- Recipient authenticity, rotation of shared documents and the non-PRF residual follow ADR-0018; the Playwright run without PRF asserts that no document opens without a fresh `vault_unlock` step-up.
- Tests run in Playwright with a virtual authenticator with PRF, and without PRF.
- As built so far (#81): the `vault` schema with forced row-level security, column grants and the access matrix; `GET /v1/vault` (status: the current recipient or null, no window needed); `POST /v1/vault` (set-up: the recipient, the recovery envelope and up to 16 passkey envelopes, one per active passkey of the account, inside a `vault_unlock` window; 409 `vault_exists` once a current recipient exists, decided by its unique index so a concurrent set-up loses); `GET /v1/vault/envelopes` (inside the window: the kept recipients, the recovery envelopes and only the active passkeys' envelopes, recorded as `vault_envelopes_fetched`); `POST /v1/vault/envelopes` (inside the window: a passkey's envelope for the current recipient, an existing one kept). Revoking or cancelling a passkey deletes its envelopes as `app_api` once the revocation is allowed, while the passkey rows are locked, so a refused revocation (the last active passkey) keeps them and a failed delete keeps the passkey. `POST /v1/vault/rotate` (a `sensitive_settings` step-up whose target is the recipient being rotated and whose fields carry the new one: marks that recipient rotated, if it is still current, and stores the new one with its envelopes in one transaction, the old envelopes kept; 409 `vault_changed` to a device that missed another rotation, so it never rotates the newer identity away), `PUT /v1/vault/recovery-envelopes` (a `sensitive_settings` step-up whose targets are the recipient IDs in order: replaces every recovery envelope or none, with the account's recipients locked first so a rotation cannot slip a new one in, 409 `vault_changed` unless the list names exactly the recipients that have one) and `DELETE /v1/vault` (a `sensitive_settings` step-up: deletes the recipients, their envelopes and the sharing state, so a vault whose secret was lost before it held anything can be set up again; the documents table must make it refuse while the account owns documents). Audit events `vault_created`, `vault_envelopes_fetched`, `vault_identity_rotated`, `vault_recovery_resealed` and `vault_reset`. Each of these is audited before its transaction commits. A passkey envelope that does not open is replaced by removing that passkey and adding it again; with a single passkey, that means adding a second first, and the recovery secret opens the vault meanwhile. Re-tagging the sharing state at rotation comes with the sharing routes (R4); the `VaultEnvelopes` adapter is in R5, and the screens follow.
- The web screen, as built (#81): `/vault`, linked from the home page. Set-up opens the `vault_unlock` window with the device's passkey, generates the identity and the vault recovery secret, opens the recovery envelope once, seals an envelope for that passkey (a passkey without PRF gets none, and the device keeps the identity wrapped through the key-storage port instead), uploads, and only then shows the secret once with the recovery kit's print, text-file and checkbox steps. Unlock opens the window, then tries this passkey's envelope, then the identity wrapped on this device, then asks for the recovery secret; after the secret, it seals an envelope for this passkey when none exists and the passkey has PRF (a cancelled prompt leaves that for the next unlock), or else keeps the identity wrapped. An opened identity whose recipient is not the current one is refused. The identity lives only in memory and closes by hand, when the page is left, and 15 minutes after the last activity or after the page was hidden, checked against a deadline so a late timer still closes it. Sign-out, every account reset (sign-in, enrollment, an accepted invite, deletion, this session revoked), a completed account recovery and a session that turns into a 401 also delete the wrapped identity, so a non-PRF device asks for the secret again after signing in anew. The vault code loads with this screen only. Playwright covers set-up and unlock with PRF (a credential the virtual authenticator created, since it evaluates PRF only for those) and without PRF (the wrapped identity, then the recovery secret after sign-out, with a wrong secret refused), and the idle close with activity keeping it open, on a mocked clock. A new vault recovery secret follows an account recovery or a new recovery kit: `GET /v1/vault` says `resealDue` when the account's latest `recovery_kit_regenerated`, or its latest `recovery_completed` not followed by a `recovery_cancelled`, is newer than its latest `vault_created` or `vault_recovery_resealed` (read from the account's own audit trail, which row-level security lets `app_api` read; the retention purge keeps those events). Saving a new kit's account code then leads to `/vault`, which says the old vault secret still applies until the vault opens; once it opens (with a passkey, the wrapped identity or the old secret, which also seals for a recovered passkey as above), the device seals the identity to a new secret, opens it once, replaces every recovery envelope after a `sensitive_settings` step-up, and only then shows the new secret with the kit's steps. A page lost after the swap but before the secret was kept leaves the vault opening by passkey or wrapped identity only, and a new kit gives it a secret again. An account that keeps a rotated identity's recovery envelope is refused with nothing re-sealed until the rotation screens can open that identity. Playwright covers a new kit: the vault part follows at the next opening, the old secret is refused and the new one opens. Still to come, with documents (R4): the rotation offer on revocation, since rotation re-encrypts documents and has nothing to protect before they exist, and the no-document-without-step-up assertion.

### R3. Document storage

Amended by [ADR-0021](../adr/0021-stay-on-vercel-and-neon.md) on 2026-11-04: no AWS account; documents go to Vercel Blob.

- One private Vercel Blob store per environment, created in São Paulo (`gru1`) and connected to the project for that environment only (production, preview), so a preview never reaches production's documents. The preview store holds synthetic data only. The API reaches its store through Vercel's OIDC; no long-lived token is stored, except the read-write token the SDK needs to issue client upload tokens, which stays a Sensitive variable of that environment.
- Blob pathnames are random UUIDs under a fixed prefix; they never contain names or document types. Overwrites stay off (the store's default); a replace writes a new pathname and deletes the old blob.
- Uploads go straight from the device with a client token the API issues for one pathname, with a maximum size of 25 MB and a short expiry. Downloads go through the API, which streams the ciphertext from the store, or through a signed URL valid for 5 minutes; either way only after the checks in R4.
- The owner connects the store in Vercel's dashboard once per environment (one click each); the ticket records the region.
- The data-flow table in ARCHITECTURE.md lists Vercel Blob.
- As built (#82 part 2a): no read-write token exists. The API issues every grant through OIDC with `@vercel/blob`'s `issueSignedToken`, scoped to the store, one pathname and one operation for 5 minutes: an upload is the SDK's presigned upload (`handleUploadPresigned`, which the client's `uploadPresigned` calls) capped at the document's declared size, `application/octet-stream` only, overwrites off and no upload callback; a download is a presigned `GET` URL, since a Vercel function response cannot carry a 25 MB document. Each environment sets its store ID and the store's webhook public key (`BLOB_STORE_ID` and `BLOB_WEBHOOK_PUBLIC_KEY`, previews `BLOB_PREVIEW_…`); the SDK's presigned helper refuses to run without the key, which only checks callbacks Arca never asks for. Without them the document routes are absent. Development uses the in-memory store, which serves its own one-time upload and 5-minute download URLs under `/internal/objects`.

### R4. Documents

- Table `vault.document` (owner account, type key, size, created, object key) and table `vault.document_recipient` (document ID, document owner ID, recipient account ID), one row per share, with a composite foreign key `(document_id, document_owner_id)` to `vault.document (id, owner_id)` `ON DELETE CASCADE`, backed by a `UNIQUE (id, owner_id)` constraint on `vault.document` (the primary key on `id` alone cannot be the target), under row-level security. Owner-side policies on `document_recipient` read its own `document_owner_id` column (no subquery into `vault.document`, so the two tables' policies never recurse): only the owner inserts, changes or deletes recipient rows (`WITH CHECK document_owner_id` = identity); a recipient reads only their own row. The owner and the accounts with a recipient row read the document row. Both registered with the `delete` strategy (the recipient table's owner column is the recipient account).
- **Reading another account's recipient** (to share with them): table `account.link` (inviter account, invitee account), one row per link, under row-level security: either party reads it and can delete it, and only the inviter inserts it (`WITH CHECK` inviter = identity). No foreign key reaches the auth schema (the registry guard forbids a cascade across it), so the link is registered with the `delete` strategy on either column: erasing the inviter or the invitee removes the row. The confirm route (spec 0003 R2) checks on the `app_auth` pool that the invite is accepted, unconfirmed and the session's own, then inserts the row as `app_api` under the inviter's identity (`ON CONFLICT DO NOTHING`, so a retry is safe) and marks the invite confirmed. Row-level security alone does not prove an invite exists, so a compromised API could link an inviter to any account; that exposes only the other account's public recipient, which the sharing state's fingerprint confirmation (ADR-0018) still guards. An account reads the `vault.recipient` row of an account it has a link row for, until the case model adds shared case membership; the target is named by account ID from that link, never looked up by email. `auth` stays unreadable to `app_api`. No other cross-account read exists.
- **Encryption follows the owner's authenticated sharing state** (ADR-0018), never the server's recipient rows: the device verifies the state's tag and version, encrypts only to the recipients it lists, and shows any recipient row it does not list, with its fingerprint, for the owner to confirm or remove.
- Audit events (added to spec 0003 R7's closed list): envelope fetched, download URL issued, document created, shared, share revoked, replaced, deleted, identity rotated, recipient pin changed. Notification channel added and removed are audited too (R7).
- Storage goes through an `ObjectStorage` port in `apps/api` with upload token, download, size-and-hash check and delete (a Vercel Blob adapter and an in-memory adapter that production refuses to select, as spec 0003 does for email); document routes and `eraseAccount` use it, never the Blob SDK directly.
- Limits, checked on the server before any upload token: a per-account quota of 1 GB and 300 documents, create and confirm-upload rate-limited (60 per hour per account, in spec 0003 R10's table), create writes the document row as pending and counts it against the quota, confirm-upload checks the blob's real size and SHA-256 before marking it confirmed (deleting it otherwise), and the daily cleanup deletes pending rows older than 24 hours with their blobs.
- Routes: create (returns a client upload token), confirm upload, list (cursor-paginated, page size capped in the contract), get download URL, replace (a batch, for sharing, revocation and rotation, which happen on the owner's device), delete (a batch). Replace and delete are batch routes (an ordered list of documents, with each new object's SHA-256 for a replace) that need one consumed `vault_write` step-up per batch, whose subject is spec 0003 R5's canonical action (the batch route, the ordered document IDs as targets, a hash of the new objects' SHA-256 values as the body hash, and the action nonce), so a share, revocation, rotation or deletion is one ceremony; confirming a replace checks each new blob's SHA-256 against the approved hash and deletes a blob that differs, so only the approved ciphertext is kept. The Playwright case for R2 also asserts that no document changes or disappears with only a `vault_unlock` window. Each in `packages/api-contract`.
- Resetting the vault (`DELETE /v1/vault`, R2) refuses while the account owns a document, with a test (409 `vault_has_documents`).
- As built so far (#82 part 1): `vault.document` (owner, type key, size, SHA-256, object key `documents/<uuid>`, created, confirmed; at most 25 MiB), `vault.document_recipient` and `account.link`, with forced row-level security, column grants and their access matrix. A share's `WITH CHECK` also needs a link between the owner and the recipient, so the server cannot add a recipient the owner has no link to. A linked account's current recipient is readable, never a rotated one, and only by `app_api`. The registry gains owners matched on any of several columns, used by `account.link`. The invite confirmation inserts the link as `app_api` under the inviter's identity before the `app_auth` transaction commits. Invites confirmed before this migration get no link; none exist outside synthetic previews, since production had no accounts yet when it landed.
- As built (#82 part 2a): create, presigned upload, confirm upload, list and download URL, with the quota counted under a lock on the account's current recipient, which a vault reset takes too, so neither runs beside the other. Create needs a `vault_unlock` window, since only an open vault can encrypt to the sharing state, and is refused to an account still awaiting its inviter's confirmation. An upload is presigned only in the hour after create. Confirm reads the stored object back: a missing object answers 409 `not_uploaded`, and a size or SHA-256 other than the declared one deletes the object; either way the document stays pending, and only the daily cleanup deletes the row, long after every grant for it has ended, so no object outlives the row that names it. Pending documents count against the quota and block a vault reset until then. The list is in document ID order. The download URL needs a `vault_unlock` window and is audited. `eraseAccount` deletes the objects in its own step before any row, and the daily cleanup deletes uploads pending for 24 hours, objects first. Replace, delete and sharing came in part 2b.
- As built (#82 part 2b): sharing, revoking and rotating are all a replace, since age ciphertext must be encrypted again for a new set of recipients. `POST /v1/vault/documents/replace` names up to 32 confirmed documents of the account, each with its new size and SHA-256, and one recipient list (ascending, at most 16 linked accounts) for all of them; the `vault_write` step-up's canonical action has the document IDs in order as targets and two fields, `recipients` (the list joined by commas) and `objects` (each `size:sha256`, in order), so the passkey approves exactly those ciphertexts for exactly those accounts, within the existing caps of 32 targets and 16 fields of 4096 characters. Each approved replacement is a `vault.document_replacement` row with its own pathname, presigned like a new document in the hour after approval and counted against the quota; a new approval for the same document discards the earlier one. `POST /v1/vault/documents/replace/confirm` takes up to 32 document IDs, counted once by the confirm limit, and answers one outcome each: a stored object with the approved size and SHA-256 takes the document's place, the shares become the replacement's recipients (row-level security still refuses an account without a link), the old object is deleted, and `document replaced`, `document shared` and `document share revoked` are recorded; any other object is deleted and the replacement stays until the daily cleanup. A pending document or a replacement can be confirmed only in the 2 hours after its row was made, so a confirm never races the cleanup deleting the same object; a recipient whose link went since the approval (only an erased account today) ends that replacement as `not_linked`, its object discarded, while the rest of the batch goes on. One confirm call reads every object it names, up to 32 of 25 MB, so the client confirms in batches small enough for the function's time limit. `POST /v1/vault/documents/delete` deletes up to 32 of the account's documents, pending or confirmed, all or none, with their shares, replacements and objects, after its own `vault_write` step-up over the document IDs, recording `document deleted` for each. Every object deleted this way is also written to `vault.discarded_object`, and the daily cleanup deletes it again an hour later, when no upload grant for its pathname can still be live, so a late upload never leaves ciphertext that no row names; erasure deletes those objects too. A recipient's copy downloaded before a revocation is outside the server's reach; the revocation stops new download URLs and replaces the stored ciphertext.
- As built (#82 part 3a): each document carries a sealed label, its file name and media type encrypted with age to the same recipients as its ciphertext, so the list can show names while the server never sees one. Create and replace take the label (base64url, at most 32 KiB of ciphertext, enough for 17 hybrid recipients), the list returns it, and a confirmed replacement moves its label onto the document with its object. The `vault_write` step-up for a replace binds each label too: each entry of the `objects` field is `size:sha256:labelSha256`, still within the 4096-character cap for a full batch. The label columns were added as `NOT NULL` with no default: no screen could create a document before this, so no environment should hold one, and a migration that meets one fails rather than invent a label.
- As built (#82 part 3b): the documents section of the open vault screen. Adding a document picks one file through the file-picking port, encrypts it on the device to the owner's own recipient (a document the sharing state does not list is the owner's alone), seals its label the same way, creates it, uploads the ciphertext (`uploadPresigned` to Vercel Blob, or the development store's URL) and confirms it. The label also names the ciphertext's SHA-256, so a label moved onto another document does not open; anyone holding a recipient can still seal a label to it, as with the document itself, so a label is a name, never proof of who wrote it; the name may hold no control, invisible or bidirectional format characters, so it cannot pass for another, and a saved file is always `application/octet-stream`, whatever type its label names. The list opens each label in memory and forgets the names when the vault closes; opening a document downloads it, checks its SHA-256 against the list, decrypts it and saves the file under its own name. Deleting one takes its own `vault_write` step-up. When the server's `vault_unlock` window has ended while the vault stayed open on the device, the passkey opens it again once. Until the document catalog arrives, every document has the type key `other`. Playwright covers adding, listing, saving and deleting a document, that the server receives only ciphertext, and that a delete with only the `vault_unlock` window is refused.
- As built (#82 part 3c, server): `GET /v1/vault/sharing-state` serves the stored state, its version and its tag, or null, to a session; `PUT /v1/vault/sharing-state` stores one within a `vault_unlock` window, named with the current recipient the device tagged it under and the version it read (null for the first), so a state is kept only over the version it changes (409 `sharing_state_changed` otherwise) and only for the identity still current (409 `vault_changed` after a rotation, 404 before set-up); it shares the lock that a rotation and a reset take on the current recipient, raises the version by at most 2^20, and is rate-limited per account. A rotation now carries the stored state re-tagged under the new identity's share key, over the stored version, in the same transaction (null only when none is stored); otherwise it changes nothing and answers 409 `sharing_state_changed`, so no state is ever left under a rotated key, which no other device could verify. It also carries every kept recipient's recovery envelope, the rotated one included, sealed again to the new identity's recovery secret and named exactly as a re-seal names them (409 `vault_changed` otherwise), so the kit shown after a rotation opens every identity the account keeps, the old secret opens none, and the rotation is recorded as a re-seal too. A rotation, a re-seal and a reset lock every recipient of the account first, in one order, so they wait for each other instead of deadlocking. A re-seal names at most 32 recipients, so an account stops rotating once it keeps 32; the cleanup of rotated identities no document needs keeps it well below that. As with a re-seal, the new secret is committed before it is shown, so a device that closes in between leaves every kept identity under a secret nobody saw (a residual: the person recovers with a passkey, or resets the vault). A stored state that pins another recipient for a linked account already pinned is audited as `recipient_pin_changed`, read from the state's pins for the audit trail only, so the events are bounded by the account's links; a pin removed and re-added later is not reported as changed. The device alone verifies a state, under the current identity's share key only, and encrypts from it. `GET /v1/account/links` lists the accounts linked to this one, in either direction, each with its email (read on `app_auth`) and its current recipient, or null before its vault is set up, in email order.
- As built (#82 part 3c, sharing screen): each of the owner's documents offers "Compartilhar", which lists the linked accounts with the fingerprint of the recipient a share would use: the pinned one, or the server's for a first share (marked, so the owner compares it with the person first). A person whose server recipient differs from the pin keeps the pinned recipient, shown beside the new fingerprint, until the owner presses "Aceitar a chave nova" for them; only then does the save encrypt to the new key and move the pin. A first share is never pre-chosen. The starting choice is the verified sharing state's, never the server's recipient rows, and a share the rows hold but the state does not is called out and dropped by the next save. Saving stores the new state first, then re-encrypts the document on the device to the owner and exactly the chosen people with its label, and replaces it after the `vault_write` step-up; a failed upload therefore leaves the state stricter than, or ahead of, the ciphertext, and the next save re-encrypts to it. The device remembers the highest version it has verified in local storage; a stored state that fails verification turns sharing off, and a lower version than remembered (or none, after one was seen) is reported to the owner with each document it shares and with whom, which the owner checks and confirms as it stands before anything else changes, re-tagged above both versions. The device keeps only the version, not the newer state, so it cannot list the differences ADR-0018 asks for; each later share still shows that document's resulting recipients. Listing the differences needs the remembered state and is a follow-up, as are a way out of an invalid state and forgetting the remembered version when the vault is reset (the version is kept per account, not per vault). Playwright covers sharing with a linked account, that account opening the document, and revoking it; unit tests cover the trust of each person and the recipients a save uses.
- `connect-src`, as built: `https://vercel.com/api/blob/` (uploads) and `https://*.private.blob.vercel-storage.com` (presigned downloads), as `@vercel/blob` 2.8.2 builds them.
- Deleting a link and existing shares: no route deletes a link yet. When one comes, it revokes, in the same transaction, the shares between the two accounts, and the owner's device re-encrypts those documents with the next replace; until then no share can outlive its link, since links are only ever added.
- `eraseAccount` (spec 0004 R9) deletes the account's blobs first, then its envelopes, recipient and document rows, so a step that fails in between is retried with the object keys still known; it also deletes the account's own recipient rows on other owners' documents; those documents stay encrypted to the deleted recipient until their owner's next re-encryption, and the deleted recipient's key no longer exists.
- Packages: `@vercel/blob`, in the Versions table with a supply-chain PASS.
- `connect-src` gains the Blob upload origin the client SDK uses, and only it (checked against the SDK when the ticket lands; downloads come from our origin or a signed URL on the store's own host, added the same way); nothing else changes in the CSP.
- Retention of documents, versions and notifications follows [RETENTION.md](../RETENTION.md).
- The plaintext processing path of ADR-0018 is built with the first `DocumentReader` use: one request bound to a `vault.document` row **owned by the requester** (a share recipient is refused, with an access-matrix and an evaluation case), rate-limited and audited; memory only, nothing persisted, logged or traced; the schema-validated result returned to the client, which stores it in the vault; only confirmed, minimized fields enter the case model.

### R5. Platform port and web adapters

- `packages/platform` defines one port per capability in ARCHITECTURE.md (document capture, file picking, key storage, notifications, receiving shared files, sharing, deep links), plus `Passkeys` (spec 0003) and `VaultEnvelopes`. `Capabilities.has()` reports what the running adapter really supports.
- Web adapters: document capture and file picking with `<input type=file>` (with `capture` where useful); key storage with non-extractable WebCrypto keys in IndexedDB, reporting eviction as "not stored"; notifications with the Push API through the service worker; sharing with the Web Share API; receiving shared files with the Web Share Target where supported, otherwise unavailable; deep links as plain URLs; `VaultEnvelopes` (`seal(identity, credentialId)` and `open(envelope)`, typed on our own types, never the library's) with `age-encryption`'s WebAuthn recipient and identity; it is the only producer of passkey envelopes. It pins `fido2prf` vectors generated at adoption (fixed credential, PRF output and nonce) in CI, and the ticket proves one envelope opens with the Go `age-plugin-fido2prf`. Key storage wraps with AES-GCM-256 (`extractable: false`, usages `encrypt` and `decrypt`, a fresh random 96-bit IV per wrap, additional authenticated data of account ID, relying-party ID and format version) and deletes the blob on sign-out, account change and recovery, and whenever the client finds its session revoked; a device that never comes back is covered by the identity rotation offered on revocation (R2). Native adapters follow ADR-0018's native path: the same `age-encryption` code runs in the app's JavaScript runtime with PRF output from the platform passkey API, or, if the library cannot take injected PRF output, the device unlocks with the recovery kit and keeps the identity wrapped in Keystore or Keychain; never a hand-built stanza.
- As built (#81): `createWebVaultEnvelopes(relyingPartyId)` seals and opens with `age-encryption`'s WebAuthn recipient and identity, for the credential the envelope names, and reports a failure with a reason the screens act on: `cancelled` (a refused or cancelled ceremony: retry), `prf_unavailable` (no PRF on that passkey or browser: the recovery kit) or `not_opened` (another passkey or a changed envelope), as `EnvelopeNotSealedError` or `EnvelopeNotOpenedError`. The library reports a missing PRF result only by its error message, so the tests pin those messages. The library builds the `AGE-PLUGIN-FIDO2PRF-1…` identity string only when it creates the credential itself, and Arca's passkeys are registered at sign-up, so the adapter encodes that string (CBOR version 1, credential ID, relying-party ID, no transport hints) and the library decodes it on every use. The pinned vector (synthetic credential and authenticator secret, the nonce inside the envelope) and the identity string are checked in CI with a software authenticator that answers PRF as CTAP2 hmac-secret does. The proof against Go ran on 2026-11-04: `fido2prf.NewIdentity` and `age.Decrypt` from typage v0.2.4 (and its `main` branch's `fido2prf.go`) opened the pinned envelope, with only `go-libfido2` replaced by the same software authenticator; a wrong authenticator secret did not open it. The program and the stand-in device are in the pull request that added this bullet, to run again whenever `age-encryption` changes. Injected PRF output: the library has no public way to take it. It reads PRF only from `navigator.credentials.get`, so the tests replace that global, and otherwise only through its protected `getCredential`. Native devices therefore take ADR-0018's fallback (recovery kit once, identity wrapped in Keystore or Keychain) unless a later decision accepts a `navigator.credentials` bridge.
- A conformance suite per port, written once (key storage includes: a blob moved to another account or origin fails to open; eviction reports "not stored"), that every adapter (web now, Capacitor and Tauri later) must pass, with fakes for headless runs.
- Lint stays as in spec 0001 R2: no OS checks, no native imports outside `packages/platform`.

### R6. Sensitive fields in the vault

Amended by [ADR-0021](../adr/0021-stay-on-vercel-and-neon.md) on 2026-11-04: no KMS and no server-side field encryption.

- Bank account and identity document numbers are vault items: small age files sealed on the device to the owner's recipient and the recipients of the people they are shared with, exactly like documents (R4), stored as `bytea` in a `vault.item` table under row-level security with the same recipient model, and never decrypted on the server.
- The case model refers to an item by ID; any feature that needs the number (a form draft, a review) decrypts it on the device. The export carries the ciphertext with the person's decryption path, like documents.
- Built with the first slice that adds such a number; until then nothing is built.

### R7. Notifications

- Tables in schema `notification`, under row-level security by account and registered: `notification.channel` (account, kind `web_push` or `email`, push subscription for `web_push`, device description, created, last success), `notification.message` (account, message code, entity ID, created) and `notification.delivery` (account, message ID, channel ID, delivered at; `ON DELETE CASCADE` from both).
- Producing a notification inserts a `message` and starts `deliverNotification(accountId, messageId)` (identifiers only; the step sets the account's identity before reading, per spec 0004 R9). The workflow runs one step per channel of the account, and each records its own delivery in `notification.delivery` (message ID, channel ID, delivered at), so a retry after a partial failure only resends to channels without a delivery row. The step runs as `app_jobs` with the account's identity set, through identity-bound `TO app_jobs` policies: `INSERT` on `notification.delivery`, `UPDATE` of the last-success time on `notification.channel`, and `DELETE` of a channel the push service reports gone; the access-matrix suite covers each, and that identity A cannot write B's rows. Web push uses VAPID with one key pair per environment: the public keys in a repository configuration file, keyed by environment, the private keys Sensitive Vercel variables, generated by an agent after the owner's OK. A subscription that the push service reports gone is deleted.
- **Payloads carry no text:** the push payload is the message code and ID; the service worker turns the code into pt-BR text from the i18n catalog. Email uses spec 0003's sender with the same codes.
- Security notices from spec 0003 R7 go to every channel; this service becomes their only producer, replacing spec 0003's direct email path, except the account-deletion completion notice, which spec 0004 R9 sends by email directly because the account's channels are already erased. Subscribing needs a user gesture; the notifications adapter reports through the `Capabilities` port an unavailability reason such as `needs-install` (derived inside the adapter from the standalone display mode and Push API availability, never from the user agent), and the UI shows the i18n message for that reason, which on iOS explains that push works after adding the app to the home screen ([WebKit: web push for web apps on iOS and iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), checked 2026-11-02).
- Preferences: security notices cannot be turned off; other codes can, per account. Removing a notification channel needs a `sensitive_settings` step-up, so a stolen session cannot silence a channel.
- As built so far (#84): the `notification` schema with forced row-level security, column grants and the access matrix. `channel` holds one `email` row per account (the address stays in auth) or a `web_push` subscription (HTTPS endpoint, P-256 key, auth secret, and the browser and system families); `message` holds the code, an optional entity ID and `details` limited per code to enum values and times, at most 1 KB; `delivery` is keyed by message and channel, both composite foreign keys with the account, so a delivery never ties two accounts' rows. `app_api` adds push channels and messages, removes channels and reads every table for the data export; `app_jobs` also adds messages (for the daily jobs) and the email channel, records deliveries, updates a channel's last success and deletes channels; every policy holds only under the row owner's identity. The three tables are registered for erasure and export, and messages expire after 90 days, with their deliveries, in the daily cleanup. Every security notice but the erasure notice now goes through one `Notifier`: it inserts the message under the notified account's identity, on `app_api` for a request (also when the request is someone else's, as an accepted invite or a recovery start), then starts `deliverNotification` with the account and message IDs. The inactivity warning is recorded on `app_jobs` and delivered by the same steps inside the daily job, before the account is marked, so a warning that cannot be sent marks nothing and no account is erased unwarned. Its first step creates the account's email channel if missing and lists the channels without a delivery for the message; then one step per channel reads the address on `app_auth`, words the code and details through the email notice templates (the message's own time, details checked against the closed per-code list), sends, and records the delivery with the channel's last success. A send whose record fails is sent again on retry; a message whose account was erased gets nothing. A producer whose notification cannot be recorded or started logs it and keeps its change, as before; the new-sign-in notice forgets the family again so the next sign-in retries it. Push channels, as built: `GET /v1/notifications/channels` lists the account's channels with the environment's VAPID public key (null where push is not set up), `POST /v1/notifications/channels` adds a browser's subscription (503 `push_unavailable` without a key, 409 `too_many_push_channels` past 10 push channels, rate-limited per account; the same endpoint returns its channel, renewed keys replace it and audit the old one's removal), and `POST /v1/notifications/channels/remove` deletes a push channel after a `sensitive_settings` step-up bound to it, never the email channel; adding and removing are audited as `notification_channel_added` and `notification_channel_removed`. Endpoints are limited to the browsers' push services (FCM, Mozilla, Apple, Microsoft), HTTPS on the default port without credentials, and the sender re-checks before posting and follows no redirect. The push step sends `{code, id}` with `@block65/webcrypto-web-push` (urgency high, kept up to 24 hours), records the delivery, and deletes a channel the service refuses for good (400, 401, 403, 404 or 410, as after a key rotation), logging `notification_push_gone` so a refusal of our own making shows; any other answer or a timeout retries that channel's step. The channel steps run side by side, email first, so a failing channel holds back no other. Inside the daily job's warning, the channels are sent side by side and a push that fails is logged and left pending: only the email gates marking the account. A subscription key that is not a P-256 point is refused (400 `invalid_request`). The public keys live in `apps/api/src/notification/vapid.ts` and the private scalar in `ARCA_VAPID_PRIVATE_KEY`, checked against the public key at start-up; a missing or mismatched one leaves push channels pending, and a set one that is refused is logged as `vapid_key_rejected`. Production and preview have their key pairs (created 2026-11-04 with the owner's OK); development has none, so local runs and the end-to-end suite show push as not set up. The device of a push channel is described from the request's User-Agent, like a session's, never from the body. The screens, as built: the settings page's "Avisos de segurança" section lists the email channel (always on) and each push channel with its browser and system, marks this browser's own (its channel ID kept in local storage, since the list carries no endpoint), and offers turning push on here (a user gesture, then the platform `Notifications` port subscribes with the environment's key; a subscription made for another key is replaced) or says why it cannot: `needs-install`, unsupported, not set up, or blocked by the browser. Stopping a channel takes its step-up and, for this browser's own, also ends the subscription. Sign-out, an account change and a session found revoked end this browser's subscription, so a shared browser never shows another account's notices; its channel is then deleted at the next notice, when the push service answers gone. The service worker words a push from its code with the `push` block of the i18n catalog (`@arca/i18n/catalog`, no i18next in the worker), shows the generic notice for anything unexpected, tags it by message ID so a repeated delivery shows once, and on a click focuses an open Arca tab or opens the home page; a notice carries no link and no remote image.
- The web push library is chosen at ticket time with a supply-chain PASS, preferring a maintained one built on WebCrypto with provenance: the common [`web-push`](https://www.npmjs.com/package/web-push) package's last release, 3.6.7, is from 2024-01-16 (npm registry checked 2026-11-02), is MPL-2.0 (needs a license exception), has no provenance and depends on the unmaintained `asn1.js`.

## Threat model for this slice

| Threat | Where | Control |
| --- | --- | --- |
| Information disclosure: server or storage breach reads documents | Blob store, database | Client-side age encryption; recipient set from the owner-tagged sharing state, never from server rows; server holds recipients and envelopes only; residuals: the first share's fingerprint check, and state rollback on a device that never saw the newer state |
| Information disclosure: future quantum attack on stored ciphertext | Documents | Hybrid ML-KEM-768 + X25519 recipients |
| Elevation: a case member reads another's document | Database, Blob store | Per-document recipients; row-level security; upload tokens and downloads issued only after the check |
| Loss of keys | Vault | Recovery envelope from the printed kit; per-passkey envelopes; tested recovery path |
| Tampering: XSS steals the unlocked identity | Web | Strict CSP and Trusted Types; identity in memory only, dropped on idle |
| Information disclosure: personal data in pathnames or push payloads | Blob store, push services | Random UUID pathnames; payloads carry codes only |
| Spoofing: notification phishing | Notifications | Generic text from our own catalog; no links in push |
| Elevation: preview reaching production storage | Vercel Blob | One store per environment, connected to that environment only |

## Definition of done

- Every requirement covered by tests; the C2SP vectors and the platform conformance suite run in CI.
- The access-matrix suite covers every new table: the owner reads and writes; a recipient reads the document row and their own recipient row but cannot change, add or delete one; a non-recipient sees nothing; an envelope is readable only by its account, never by a recipient of a shared document; another account's `vault.recipient` is readable only with an `account.link` row (later, a shared case), and not otherwise; `vault.sharing_state` only by its account; a recipient or `vault.document_recipient` row the server inserts outside the sharing state is never encrypted to (the device shows it for the owner's confirmation), and a validly tagged older state relabelled with a higher version fails verification; erasing the owner of a shared document, or its recipient, succeeds in either order; `app_jobs` under identity A erases nothing of B; erasing either account of an `account.link` removes the row; notification rows only by their account.
- `docs/vault-format.md` written; a document round-trips between two synthetic accounts with sharing and revocation in Playwright; after the recipient rotates on device A, the shared document still opens on their device B before the owner re-encrypts, and after a restored lower sharing-state version the owner's device asks for confirmation instead of using it.
- A preview receives a web push for a synthetic message.
- No personal data anywhere in the diff.
