# Spec 0005: Vault, device capabilities and notifications

- Status: Ready for tickets
- Date: 2026-11-02
- Epic: cross-platform foundations ([ROADMAP.md](../ROADMAP.md#phase-1--family-mvp-web)), after [spec 0003](0003-identity-and-access.md)
- Decisions: [ADR-0018](../adr/0018-vault-encryption.md), [ADR-0005](../adr/0005-platform-strategy.md), [ADR-0008](../adr/0008-database-security-and-environments.md), [ADR-0017](../adr/0017-data-lifecycle-and-backups.md) (registry), [ADR-0021](../adr/0021-stay-on-vercel-and-neon.md) (Vercel Blob, sensitive fields in the vault, no AWS), [ADR-0009](../adr/0009-background-jobs-guarantees.md)

## Goal

The pieces that native phases will only add adapters to: an encrypted document vault with a documented, platform-neutral format and tested recovery; sensitive fields (bank account and document numbers) kept in the vault too; the `platform` port with web adapters and a conformance suite; and a notification service with per-device channels, web push first.

## Scope

**In:** `packages/vault`; vault identity, envelopes, unlock and recovery; document storage as ciphertext in a private Vercel Blob store; sharing, revocation and rotation; sensitive fields in the vault; `platform` capabilities with web adapters; notifications through web push and email.

**Out:** document review, OCR and the `DocumentReader` adapter (Phase 2), but the processing path is fixed by ADR-0018; any document type catalog (data, with the consultancy core); native adapters (Phases 4 to 6).

**Not on the critical path of the consultancy core's case model**, which stores no documents. The vault must exist before any document upload is built; notifications before the plan sends reminders.

## Requirements

### R1. Vault core

- New package `packages/vault`, pure TypeScript with no workspace dependencies and no platform calls (boundary matrix: `apps/web` may depend on it; the API never decrypts and does not depend on it). `packages/platform` also depends on `age-encryption` for the envelope port (R5), and on `packages/vault` for its `VaultIdentity` and share-key types only (type imports, enforced by the boundary rule); the boundary matrix lists all three. It wraps `age-encryption` (newest release at least 7 days old; 0.3.x as of 2026-11-02), added to the Versions table with a supply-chain PASS.
- A sharing-state module in `packages/vault` owns ADR-0018's sharing state: encode (length-prefixed), tag, verify, compare versions, compute the difference the owner confirms, and re-tag under a new share key; table-driven vectors cover a valid state, a wrong tag, an older state relabelled with a higher version, another account's state and a lower restored version. `apps/web` only renders the confirmation.
- API: generate a hybrid identity; encrypt and decrypt documents as streams to a recipient set; seal and open the scrypt recovery envelope with the vault recovery secret; re-encrypt to a new recipient set. Passkey envelopes are not sealed here: the `VaultEnvelopes` port (R5) owns them, and `packages/vault` never receives a PRF recipient (ADR-0018).
- The C2SP age test vectors run in CI against the package, plus vectors pinned at adoption for the `mlkem768x25519` stanza where CCTV does not cover it (ADR-0018). Round-trip, multi-recipient, revocation, rotation and wrong-key tests are table-driven.
- The format is documented in `docs/vault-format.md`: file layout (plain age), recipient types, envelope kinds, how native apps reproduce each with other age implementations.

### R2. Vault identity, unlock and recovery

- Tables in schema `vault`, under row-level security by account, registered in the personal-data registry (ADR-0017): `vault.recipient` (account, age recipient, created, rotated), `vault.envelope` (account, the recipient whose identity it holds, kind `passkey_prf` or `recovery`, credential ID for `passkey_prf`, the age ciphertext) and `vault.sharing_state` (account, version, the serialized state, its HMAC-SHA-256 tag over the domain tag, account ID, version and state, length-prefixed; ADR-0018). After a rotation the old identity's envelopes stay beside the new ones until every sharing owner has re-encrypted, or 90 days.
- First use: the device generates the identity, the share key and the vault recovery secret; seals one envelope per PRF-capable passkey through the `VaultEnvelopes` port and one with the recovery secret; opens the recovery envelope once as a check; uploads the recipient and envelopes; and only then shows the vault part of the recovery kit (spec 0003 R6). Playwright covers that the recovery envelope opens before the vault is used. A new passkey with PRF gets its envelope at its next unlock.
- Unlock: the API serves envelopes and download URLs only after a `vault_unlock` step-up less than 15 minutes old (spec 0003 R5); then the platform port's PRF ceremony opens the matching envelope; without PRF, the person enters the recovery secret once and the identity is kept wrapped by a non-extractable key through the key-storage port, with the AES-GCM construction ADR-0018 names (R5). The identity stays in memory only and is dropped on sign-out, after 15 minutes idle, or after 15 minutes hidden.
- Revoking a passkey, or cancelling one in its 24-hour window, first deletes its `passkey_prf` envelope (keyed by credential ID, as `app_api` under the account's identity, idempotent), then revokes the passkey on the `app_auth` pool; the envelope route reads the account's active credential IDs on the `app_auth` pool and serves envelopes only for those, so an orphan is never served. It also offers identity rotation (ADR-0018), on by default when the passkey had PRF or its device held a wrapped identity.
- Recovery after losing every passkey: account recovery (spec 0003) then the recovery secret opens the recovery envelope; new envelopes are sealed for the new passkey.
- Regenerating the recovery kit re-seals every recovery envelope the account keeps to the new secret (a rotated identity's still-retained one included), so the old secret stops working for any of them, in the order spec 0003 R6 fixes; a kit is never shown with a vault secret that is not sealed in.
- Recipient authenticity, rotation of shared documents and the non-PRF residual follow ADR-0018; the Playwright run without PRF asserts that no document opens without a fresh `vault_unlock` step-up.
- Tests run in Playwright with a virtual authenticator with PRF, and without PRF.
- As built so far (#81): the `vault` schema with forced row-level security, column grants and the access matrix; `GET /v1/vault` (status: the current recipient or null, no window needed); `POST /v1/vault` (set-up: the recipient, the recovery envelope and up to 16 passkey envelopes, one per active passkey of the account, inside a `vault_unlock` window; 409 `vault_exists` once a current recipient exists, decided by its unique index so a concurrent set-up loses); `GET /v1/vault/envelopes` (inside the window: the kept recipients, the recovery envelopes and only the active passkeys' envelopes, recorded as `vault_envelopes_fetched`); `POST /v1/vault/envelopes` (inside the window: a passkey's envelope for the current recipient, an existing one kept). Revoking or cancelling a passkey deletes its envelopes as `app_api` once the revocation is allowed, while the passkey rows are locked, so a refused revocation (the last active passkey) keeps them and a failed delete keeps the passkey. `POST /v1/vault/rotate` (a `sensitive_settings` step-up whose target is the recipient being rotated and whose fields carry the new one: marks that recipient rotated, if it is still current, and stores the new one with its envelopes in one transaction, the old envelopes kept; 409 `vault_changed` to a device that missed another rotation, so it never rotates the newer identity away), `PUT /v1/vault/recovery-envelopes` (a `sensitive_settings` step-up whose targets are the recipient IDs in order: replaces every recovery envelope or none, with the account's recipients locked first so a rotation cannot slip a new one in, 409 `vault_changed` unless the list names exactly the recipients that have one) and `DELETE /v1/vault` (a `sensitive_settings` step-up: deletes the recipients, their envelopes and the sharing state, so a vault whose secret was lost before it held anything can be set up again; the documents table must make it refuse while the account owns documents). Audit events `vault_created`, `vault_envelopes_fetched`, `vault_identity_rotated`, `vault_recovery_resealed` and `vault_reset`. Each of these is audited before its transaction commits. A passkey envelope that does not open is replaced by removing that passkey and adding it again; with a single passkey, that means adding a second first, and the recovery secret opens the vault meanwhile. Re-tagging the sharing state at rotation comes with the sharing routes (R4); the `VaultEnvelopes` adapter is in R5, and the screens follow.

### R3. Document storage

Amended by [ADR-0021](../adr/0021-stay-on-vercel-and-neon.md) on 2026-11-04: no AWS account; documents go to Vercel Blob.

- One private Vercel Blob store per environment, created in São Paulo (`gru1`) and connected to the project for that environment only (production, preview), so a preview never reaches production's documents. The preview store holds synthetic data only. The API reaches its store through Vercel's OIDC; no long-lived token is stored, except the read-write token the SDK needs to issue client upload tokens, which stays a Sensitive variable of that environment.
- Blob pathnames are random UUIDs under a fixed prefix; they never contain names or document types. Overwrites stay off (the store's default); a replace writes a new pathname and deletes the old blob.
- Uploads go straight from the device with a client token the API issues for one pathname, with a maximum size of 25 MB and a short expiry. Downloads go through the API, which streams the ciphertext from the store, or through a signed URL valid for 5 minutes; either way only after the checks in R4.
- The owner connects the store in Vercel's dashboard once per environment (one click each); the ticket records the region.
- The data-flow table in ARCHITECTURE.md lists Vercel Blob.

### R4. Documents

- Table `vault.document` (owner account, type key, size, created, object key) and table `vault.document_recipient` (document ID, document owner ID, recipient account ID), one row per share, with a composite foreign key `(document_id, document_owner_id)` to `vault.document (id, owner_id)` `ON DELETE CASCADE`, backed by a `UNIQUE (id, owner_id)` constraint on `vault.document` (the primary key on `id` alone cannot be the target), under row-level security. Owner-side policies on `document_recipient` read its own `document_owner_id` column (no subquery into `vault.document`, so the two tables' policies never recurse): only the owner inserts, changes or deletes recipient rows (`WITH CHECK document_owner_id` = identity); a recipient reads only their own row. The owner and the accounts with a recipient row read the document row. Both registered with the `delete` strategy (the recipient table's owner column is the recipient account).
- **Reading another account's recipient** (to share with them): table `account.link` (inviter account, invitee account), one row per link, both columns foreign keys to the account table `ON DELETE CASCADE`, under row-level security: either party reads it and can delete it, and only the inviter inserts it (`WITH CHECK` inviter = identity), registered with the `delete` strategy on the inviter column (the cascade covers the invitee's erasure). The confirm route (spec 0003 R2) checks on the `app_auth` pool that the invite is accepted, unconfirmed and the session's own, then inserts the row as `app_api` under the inviter's identity (`ON CONFLICT DO NOTHING`, so a retry is safe) and marks the invite confirmed. Row-level security alone does not prove an invite exists, so a compromised API could link an inviter to any account; that exposes only the other account's public recipient, which the sharing state's fingerprint confirmation (ADR-0018) still guards. An account reads the `vault.recipient` row of an account it has a link row for, until the case model adds shared case membership; the target is named by account ID from that link, never looked up by email. `auth` stays unreadable to `app_api`. No other cross-account read exists.
- **Encryption follows the owner's authenticated sharing state** (ADR-0018), never the server's recipient rows: the device verifies the state's tag and version, encrypts only to the recipients it lists, and shows any recipient row it does not list, with its fingerprint, for the owner to confirm or remove.
- Audit events (added to spec 0003 R7's closed list): envelope fetched, download URL issued, document created, shared, share revoked, replaced, deleted, identity rotated, recipient pin changed. Notification channel added and removed are audited too (R7).
- Storage goes through an `ObjectStorage` port in `apps/api` with upload token, download, size-and-hash check and delete (a Vercel Blob adapter and an in-memory adapter that production refuses to select, as spec 0003 does for email); document routes and `eraseAccount` use it, never the Blob SDK directly.
- Limits, checked on the server before any upload token: a per-account quota of 1 GB and 300 documents, create and confirm-upload rate-limited (60 per hour per account, in spec 0003 R10's table), create writes the document row as pending and counts it against the quota, confirm-upload checks the blob's real size and SHA-256 before marking it confirmed (deleting it otherwise), and the daily cleanup deletes pending rows older than 24 hours with their blobs.
- Routes: create (returns a client upload token), confirm upload, list (cursor-paginated, page size capped in the contract), get download URL, replace (a batch, for sharing, revocation and rotation, which happen on the owner's device), delete (a batch). Replace and delete are batch routes (an ordered list of documents, with each new object's SHA-256 for a replace) that need one consumed `vault_write` step-up per batch, whose subject is spec 0003 R5's canonical action (the batch route, the ordered document IDs as targets, a hash of the new objects' SHA-256 values as the body hash, and the action nonce), so a share, revocation, rotation or deletion is one ceremony; confirming a replace checks each new blob's SHA-256 against the approved hash and deletes a blob that differs, so only the approved ciphertext is kept. The Playwright case for R2 also asserts that no document changes or disappears with only a `vault_unlock` window. Each in `packages/api-contract`.
- Resetting the vault (`DELETE /v1/vault`, R2) refuses while the account owns a document, with a test.
- `eraseAccount` (spec 0004 R9) deletes the account's blobs first, then its envelopes, recipient and document rows, so a step that fails in between is retried with the object keys still known; it also deletes the account's own recipient rows on other owners' documents; those documents stay encrypted to the deleted recipient until their owner's next re-encryption, and the deleted recipient's key no longer exists.
- Packages: `@vercel/blob`, in the Versions table with a supply-chain PASS.
- `connect-src` gains the Blob upload origin the client SDK uses, and only it (checked against the SDK when the ticket lands; downloads come from our origin or a signed URL on the store's own host, added the same way); nothing else changes in the CSP.
- Retention of documents, versions and notifications follows [RETENTION.md](../RETENTION.md).
- The plaintext processing path of ADR-0018 is built with the first `DocumentReader` use: one request bound to a `vault.document` row **owned by the requester** (a share recipient is refused, with an access-matrix and an evaluation case), rate-limited and audited; memory only, nothing persisted, logged or traced; the schema-validated result returned to the client, which stores it in the vault; only confirmed, minimized fields enter the case model.

### R5. Platform port and web adapters

- `packages/platform` defines one port per capability in ARCHITECTURE.md (document capture, file picking, key storage, notifications, receiving shared files, sharing, deep links), plus `Passkeys` (spec 0003) and `VaultEnvelopes`. `Capabilities.has()` reports what the running adapter really supports.
- Web adapters: document capture and file picking with `<input type=file>` (with `capture` where useful); key storage with non-extractable WebCrypto keys in IndexedDB, reporting eviction as "not stored"; notifications with the Push API through the service worker; sharing with the Web Share API; receiving shared files with the Web Share Target where supported, otherwise unavailable; deep links as plain URLs; `VaultEnvelopes` (`seal(identity, credentialId)` and `open(envelope)`, typed on our own types, never the library's) with `age-encryption`'s WebAuthn recipient and identity; it is the only producer of passkey envelopes. It pins `fido2prf` vectors generated at adoption (fixed credential, PRF output and nonce) in CI, and the ticket proves one envelope opens with the Go `age-plugin-fido2prf`. Key storage wraps with AES-GCM-256 (`extractable: false`, usages `encrypt` and `decrypt`, a fresh random 96-bit IV per wrap, additional authenticated data of account ID, relying-party ID and format version) and deletes the blob on sign-out, account change and recovery, and whenever the client finds its session revoked; a device that never comes back is covered by the identity rotation offered on revocation (R2). Native adapters follow ADR-0018's native path: the same `age-encryption` code runs in the app's JavaScript runtime with PRF output from the platform passkey API, or, if the library cannot take injected PRF output, the device unlocks with the recovery kit and keeps the identity wrapped in Keystore or Keychain; never a hand-built stanza.
- As built (#81): `createWebVaultEnvelopes(relyingPartyId)` seals and opens with `age-encryption`'s WebAuthn recipient and identity, for the credential the envelope names, and maps every failure to open (another passkey, a changed envelope, a refused ceremony) to `EnvelopeNotOpenedError`. The library builds the `AGE-PLUGIN-FIDO2PRF-1…` identity string only when it creates the credential itself, and Arca's passkeys are registered at sign-up, so the adapter encodes that string (CBOR version 1, credential ID, relying-party ID, no transport hints) and the library decodes it on every use. The pinned vector (synthetic credential and authenticator secret, the nonce inside the envelope) and the identity string are checked in CI with a software authenticator that answers PRF as CTAP2 hmac-secret does. The proof against Go ran on 2026-11-04: `fido2prf.NewIdentity` and `age.Decrypt` from typage v0.2.4 (and its `main` branch's `fido2prf.go`) opened the pinned envelope, with only `go-libfido2` replaced by the same software authenticator; a wrong authenticator secret did not open it. Injected PRF output: the library has no public way to take it. It reads PRF only from `navigator.credentials.get`, so the tests replace that global, and otherwise only through its protected `getCredential`. Native devices therefore take ADR-0018's fallback (recovery kit once, identity wrapped in Keystore or Keychain) unless a later decision accepts a `navigator.credentials` bridge.
- A conformance suite per port, written once (key storage includes: a blob moved to another account or origin fails to open; eviction reports "not stored"), that every adapter (web now, Capacitor and Tauri later) must pass, with fakes for headless runs.
- Lint stays as in spec 0001 R2: no OS checks, no native imports outside `packages/platform`.

### R6. Sensitive fields in the vault

Amended by [ADR-0021](../adr/0021-stay-on-vercel-and-neon.md) on 2026-11-04: no KMS and no server-side field encryption.

- Bank account and identity document numbers are vault items: small age files sealed on the device to the owner's recipient and the recipients of the people they are shared with, exactly like documents (R4), stored as `bytea` in a `vault.item` table under row-level security with the same recipient model, and never decrypted on the server.
- The case model refers to an item by ID; any feature that needs the number (a form draft, a review) decrypts it on the device. The export carries the ciphertext with the person's decryption path, like documents.
- Built with the first slice that adds such a number; until then nothing is built.

### R7. Notifications

- Tables in schema `notification`, under row-level security by account and registered: `notification.channel` (account, kind `web_push` or `email`, push subscription for `web_push`, device description, created, last success), `notification.message` (account, message code, entity ID, created) and `notification.delivery` (account, message ID, channel ID, delivered at; `ON DELETE CASCADE` from both).
- Producing a notification inserts a `message` and starts `deliverNotification(accountId, messageId)` (identifiers only; the step sets the account's identity before reading, per spec 0004 R9). The workflow runs one step per channel of the account, and each records its own delivery in `notification.delivery` (message ID, channel ID, delivered at), so a retry after a partial failure only resends to channels without a delivery row. The step runs as `app_jobs` with the account's identity set, through identity-bound `TO app_jobs` policies: `INSERT` on `notification.delivery`, `UPDATE` of the last-success time on `notification.channel`, and `DELETE` of a channel the push service reports gone; the access-matrix suite covers each, and that identity A cannot write B's rows. Web push uses VAPID with one key pair per environment: the public keys in a repository configuration file, keyed by environment, the private keys Sensitive Vercel variables, generated by an agent after the owner's OK. A subscription that the push service reports gone is deleted.
- **Payloads carry no text:** the push payload is the message code and ID; the service worker turns the code into pt-BR text from the i18n catalog. Email uses spec 0003's sender with the same codes.
- Security notices from spec 0003 R7 go to every channel; this service becomes their only producer, replacing spec 0003's direct email path, except the account-deletion completion notice, which spec 0004 R9 sends by email directly because the account's channels are already erased. Subscribing needs a user gesture; the notifications adapter reports through the `Capabilities` port an unavailability reason such as `needs-install` (derived inside the adapter from the standalone display mode and Push API availability, never from the user agent), and the UI shows the i18n message for that reason, which on iOS explains that push works after adding the app to the home screen ([WebKit: web push for web apps on iOS and iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), checked 2026-11-02).
- Preferences: security notices cannot be turned off; other codes can, per account. Removing a notification channel needs a `sensitive_settings` step-up, so a stolen session cannot silence a channel.
- The web push library is chosen at ticket time with a supply-chain PASS, preferring a maintained one built on WebCrypto with provenance: the common [`web-push`](https://www.npmjs.com/package/web-push) package's last release, 3.6.7, is from 2024-01-16 (npm registry checked 2026-11-02), is MPL-2.0 (needs a license exception), has no provenance and depends on the unmaintained `asn1.js`.

## Threat model for this slice

| Threat | Where | Control |
| --- | --- | --- |
| Information disclosure: server or storage breach reads documents | Blob store, database | Client-side age encryption; recipient set from the owner-tagged sharing state, never from server rows; server holds recipients and envelopes only; residuals: the first share's fingerprint check, and state rollback on a device that never saw the newer state |
| Information disclosure: future quantum attack on stored ciphertext | Documents | Hybrid ML-KEM-768 + X25519 recipients |
| Elevation: a case member reads another's document | Database, Blob store | Per-document recipients; row-level security; upload tokens and downloads issued only after the check |
| Loss of keys | Vault | Recovery envelope from the printed kit; per-passkey envelopes; tested recovery path |
| Tampering: XSS steals the unlocked identity | Web | Strict CSP and Trusted Types; identity in memory only, dropped on idle |
| Information disclosure: personal data in pathnames or push payloads | Blob store, push services | Random UUID pathnames; payloads carry codes only |
| Spoofing: notification phishing | Notifications | Generic text from our own catalog; no links in push |
| Elevation: preview reaching production storage | Vercel Blob | One store per environment, connected to that environment only |

## Definition of done

- Every requirement covered by tests; the C2SP vectors and the platform conformance suite run in CI.
- The access-matrix suite covers every new table: the owner reads and writes; a recipient reads the document row and their own recipient row but cannot change, add or delete one; a non-recipient sees nothing; an envelope is readable only by its account, never by a recipient of a shared document; another account's `vault.recipient` is readable only with an `account.link` row (later, a shared case), and not otherwise; `vault.sharing_state` only by its account; a recipient or `vault.document_recipient` row the server inserts outside the sharing state is never encrypted to (the device shows it for the owner's confirmation), and a validly tagged older state relabelled with a higher version fails verification; erasing the owner of a shared document, or its recipient, succeeds in either order; `app_jobs` under identity A erases nothing of B; erasing either account of an `account.link` removes the row; notification rows only by their account.
- `docs/vault-format.md` written; a document round-trips between two synthetic accounts with sharing and revocation in Playwright; after the recipient rotates on device A, the shared document still opens on their device B before the owner re-encrypts, and after a restored lower sharing-state version the owner's device asks for confirmation instead of using it.
- A preview receives a web push for a synthetic message.
- No personal data anywhere in the diff.
