# Spec 0004: Real-data readiness

- Status: Ready for tickets
- Date: 2026-11-02
- Epic: cross-platform foundations ([ROADMAP.md](../ROADMAP.md#phase-1--family-mvp-web)), after [spec 0001](0001-foundations-scaffold.md)
- Decisions: [ADR-0017](../adr/0017-data-lifecycle-and-backups.md), [ADR-0016](../adr/0016-observability-and-scrubbing.md), [ADR-0012](../adr/0012-automation-first-setup.md), [ADR-0008](../adr/0008-database-security-and-environments.md), [ADR-0009](../adr/0009-background-jobs-guarantees.md); uses [spec 0003](0003-identity-and-access.md) for step-up and the audit log

## Goal

Everything SECURITY.md and ROADMAP.md require before the first real family data enters production: previews provably separate from production, a synthetic seed, error and trace reporting that cannot carry personal data, deletion and export that cover every table, retention enforced, an incident runbook, backups, and the epic's threat model. It ends with a **real-data gate**: a checklist that must be complete before production accepts family data.

## Scope

**In:** the `development` branch and the lineage check; the synthetic seed; `packages/telemetry` and its scrubber; Sentry on server and client through our tunnel; the personal-data registry and its guard; export; account deletion; retention jobs; the incident response runbook and `security.txt`; backups; the threat model for the epic; the real-data gate.

**Out:** Langfuse wiring (with the first model call, R6 records its requirements); the vault and field encryption (spec 0005); the designated-adult recovery factor and case-model registry entries (consultancy core).

**No case data.** Seed and tests are synthetic. Nothing here reads real data.

- As built: `checkLineage` in `tooling/scripts/src/db/deployment-target.ts`, called by the runner inside its transaction after the advisory lock and once `arca_migrations` exists, and again on production after the migrations, so a migration cannot drop the mark; the error is `preview_forked_from_production`. `development` was created on 2026-11-05, before this change merged, so it carries the endpoint mark and no lineage mark.

### R2. Synthetic seed

- `packages/db/seed/` holds synthetic data as typed fixtures with fixed UUIDs, and a seed command in `tooling/scripts` that applies them idempotently after migrations, in preview builds and in CI. The production build never runs it, checked by the database target of spec 0001 R9.
- The seed writes through the runtime roles (`app_auth` for accounts, `app_api` under each synthetic account's identity for case data later), so row-level security applies to the seed as to the app.
- Accounts use addresses at `example.com`. Each slice that adds tables adds seed data for them.
- As built ([#65](https://github.com/fernandolisboa/arca/issues/65)): the fixtures are `packages/db/seed/accounts.json`, read through a typed parser in `tooling/scripts/src/db/seed.ts` that accepts only exact fields, UUIDs and `example.com` addresses; JSON, because tooling may not import a workspace package. `db:seed` runs after `db:migrate` in CI's `e2e` job and in the build command, which now calls one `db:build` script (bootstrap, migrate, seed, runtime settings) because Vercel caps a build command at 256 characters; as `app_auth` in one transaction, inserting with `ON CONFLICT (id) DO NOTHING`. It takes a transaction advisory lock first, since previews building at once share `development`. A production build skips it before it connects, and the seed itself refuses production; a preview checks the endpoint mark and the lineage mark first. A row that exists is left alone, so a fixture change reaches `development` only after its row is deleted there. The seed holds one confirmed owner account with one passkey whose P-256 private key is the SHA-256 of a public label, so the key is public and Deployment Protection is the only control on previews (threat model R-14). It lets `apps/web/e2e/seeded.spec.ts` sign in with a virtual authenticator, in CI rather than against a preview, which would need a protection bypass token. No vault or notification rows are seeded: vault rows are ciphertext only a client can make, and no slice has case data yet.

### R3. One scrubber

- New package `packages/telemetry`, with no workspace dependencies, usable from `apps/api` and `apps/web` (boundary matrix updated). It exports the field allow-lists and the scrub functions that every exporter uses: the existing logger (moved here from `apps/api`, which then imports it), Sentry's hooks on server and client, the tunnel, and later Langfuse's masking function.
- Rules (ADR-0016): allow-listed fields with shape checks; the only identifiers admitted are request ID, trace ID, release and environment (never account, case, document or session IDs); database spans keep operation and table, never statement text; CSP violation reports have their own allow-list; exception messages dropped (class name and error code kept); URLs reduced to route patterns; no bodies, cookies, query strings, local variables, user objects or IP addresses; allow-listed headers only.
- Stack frames keep file, function and line only after shape and length checks (path-like file names, identifier-like function names); CSP report URLs are reduced like other URLs. A URL keeps its host only when it is the app's own or a vendor's, since a host name can carry data; a frame file name that is a URL is reduced too, keeping only a built asset's name; a database span names its table only when the table is in the schema.
- A table-driven suite pushes synthetic personal data (names, emails, CPF-, RG- and passport-shaped values, phone numbers, addresses, free text) through every exporter path and asserts none survives, plus an adversarial envelope whose frames and report fields carry instruction-like text, which must be dropped or truncated.
- The logger gains `traceId` as an allowed field.

Traces sampled at 10% in production and 100% in previews; spans named by route pattern; workflow steps traced under their generic names.
- The DSN and the environment names live in a repository configuration file. The source-map upload token is a Sensitive Vercel variable (`SENTRY_AUTH_TOKEN`, **Production only**, scoped to releases on the one project, scopes recorded in the ticket), added to the lint rule's list of variables only build scripts may read (Vercel also exposes it to functions, ADR-0012); previews skip the upload. Source maps are uploaded with `@sentry/vite-plugin` (bundler telemetry off) and deleted from the output.
- Packages: `@sentry/node`, `@sentry/hono`, `@sentry/react`, `@sentry/vite-plugin`, each in the Versions table with a supply-chain PASS. `@sentry/vite-plugin` pulls `@sentry/bundler-plugin-core` and `@sentry/cli` (license FSL-1.1-Apache-2.0, and an install script that downloads the CLI binary); the ticket checks this against the npm registry, then either records a pinned license exception (used unmodified as build tooling, install script allowed by name) or keeps them out, and proves the deployed function bundle contains neither.
- **Owner, once** (amended by ADR-0016 on 2026-11-04: a project in the owner's existing United States organization, created in Sentry's interface, with no tokens): create the Sentry organization in the German data region on the free Developer plan, with a passkey on the account; give the agent a setup token with the minimum scopes (project write, alert rules write, release token creation) and the shortest expiry Sentry allows, revoked by the owner when the ticket closes. The agent creates the project, alert rules (new issue, regression, email to the owner) and the upload token through Sentry's API, and the Vercel variable after the owner's OK.
- Agent tooling that reads Sentry issues (ADR-0016) uses a read-only token scoped to the one project, wraps issue content as delimited untrusted data, and ships with an evaluation case where injected issue text asks for a containment action and the expected result is a proposal to the owner, not an action.
- A test endpoint that exists only in previews throws a synthetic error carrying synthetic personal data; the ticket shows the resulting Sentry event without it.
- As built (amended by [ADR-0016](../adr/0016-observability-and-scrubbing.md#amendment-2026-11-04-a-smaller-server-setup)): `@sentry/hono/node` is started in `apps/api/src/monitoring.ts` before the app is built, from `sentryProject` in `packages/telemetry` (the DSN of a project in the owner's existing organization, in Sentry's United States region, and each environment's sample rate; the scrubber's environment list comes from the same file). SDK 11 has no `sendDefaultPii`; its `dataCollection` is all off. The integration list is pinned by a test: event filters, linked errors, dedupe, uncaught exceptions, unhandled rejections and HTTP, nothing else. Transactions are sent whole (`traceLifecycle: 'static'`) and the SDK's load-time module rewriting is off. The Hono middleware runs first, names each trace by its route pattern and reports 5xx errors; workflow steps report their failures through `withStepError` with the step's error code, starting Sentry with tracing off if the instance has not loaded the server module. A 5xx flushes Sentry behind the answer and a failing step waits for its report, so a frozen instance loses neither. URLs keep the API's static path segments (from the contract and the internal routes, checked against the app's routes by a test) and the deployment's own host. `/internal/monitoring-check` exists only on previews and throws `SyntheticPersonalDataError`; a test runs it through the SDK with a recording transport and finds the class and frames but none of the values. The owner creates the project in Sentry's interface with its default alert, so there is no setup token; no source maps are uploaded, so there is no upload token, and `@sentry/bundler-plugins` (with the FSL-licensed Sentry CLI) is removed by a pnpm override; agent tooling that reads Sentry issues is not built.

### R5. Sentry in the browser, through our origin

- `@sentry/react`, bundled, errors only; no session replay, no console breadcrumbs; fetch breadcrumbs reduced to route patterns; the same scrub hooks.
- `tunnel: true`; the API serves the tunnel, accepts only our DSN (`allowedDsns`), caps the envelope at 200 KB, rate-limits per IP, and scrubs again before forwarding. The tunnel path is excluded from the SPA fallback in `tooling/security-policy` and answers `Cache-Control: no-store`.
- CSP and Trusted Types violation reports (`report-to` and `Reporting-Endpoints`) go to a second path of the same Hono route, which validates the Reporting API payload against its own allow-list and forwards it to Sentry's security-report endpoint. The tunnel is a Hono route, not a Nitro integration. The CSP keeps `connect-src 'self'`.
- Playwright: an error in the web app reaches the tunnel, and no request leaves the origin.
- As built (amended by [ADR-0016](../adr/0016-observability-and-scrubbing.md#amendment-2026-11-04-our-own-tunnel-in-the-browser-ticket)): the tunnel is our own Hono route at `/internal/monitoring/envelope` (`tunnelPath` in `packages/telemetry`), named by the browser SDK's `tunnel` option, instead of the SDK's managed tunnel, which cannot scrub. It accepts only our DSN, refuses another site's `Origin`, caps the envelope at 200 KB, allows 60 an hour per IP, stamps the server's environment on each event and forwards behind the answer. CSP reports go to `/internal/monitoring/csp` (`cspReportPath` in `tooling/security-policy`, named by `Reporting-Endpoints` and `report-to`), capped at 64 KB and 60 an hour per IP, and are forwarded to the security endpoint. Both paths exist only where the deployment reports; `/internal` already never falls back to the SPA and answers `no-store`. The browser starts Sentry in production builds with a pinned integration list (event filters, linked errors, dedupe, global handlers, fetch and history breadcrumbs), `dataCollection` all off, and the same scrub hooks; route error boundaries and React's uncaught-error handler report too. The web app's page segments are `webPathSegments` in the contract, checked against the router by the web typecheck, so page URLs keep their page through both scrubs.

### R7. Personal-data registry

- `packages/db/src/registry.ts`: for each table in a user schema, an entry (owner, erasing pool, erase strategy `delete` or `retain`, export projection, an i18n label key for the export) or a place on the unowned list with a reason. The owner is a column holding the account ID, or the entry the rows hang off, which removes them through an `ON DELETE CASCADE` foreign key. An unowned table holds no personal data, or holds some, or pseudonyms of it, only for a short time in rows with no owner column (registration contexts, Better Auth's passkey ceremony state, rate-limit counters, the non-production outbox); each of those names its expiry column, and account deletion sweeps their expired rows (R9).
- A guard test reads `pg_catalog` after the migrations and fails on any table in neither list, on any registry entry for a table or column that does not exist, on a child entry without its cascading foreign key, and on the foreign-key and pool rules below. It runs in the `db` CI check (`packages/db/test/postgres/registry.test.ts`); a test of `apps/api` checks that every label key is in the pt-BR catalog.
- Strategies: `delete`, and `retain` (kept after erasure with identifiers only, with a reason and a period; for `audit.event`, 5 years; for `knowledge.decision`, `forever`, as the record of which rules are in use, spec 0007 R7; for `knowledge.admin_grant`, `forever`, since decisions rely on it, ADR-0027). Data shared with others is modelled so each person's part is their own rows (for example one recipient row per share), so `delete` covers it. Purging `retain` rows needs its own ADR before the first period ends, because it changes ADR-0008's insert-only audit log.
- Foreign keys: none from `audit`; none with a cascading delete action (`CASCADE`, `SET NULL`, `SET DEFAULT`) between `auth` and another schema, in either direction, so erasure only happens through the registry, after its audit event.
- Pools: entries in `auth` are erased by `app_auth`, the rest by `app_jobs`. Each `app_jobs` `delete` entry owned by a column needs a permissive `app_jobs` `DELETE` policy and a `SELECT` policy whose qualifier is exactly `owner = nullif(current_setting('app.account_id', true), '')::uuid` on that column, and every permissive policy that lets `app_jobs` delete from the table must have that qualifier (ADR-0017).
- Initial entries: the `auth` tables and `audit.event` (spec 0003).

### R8. Export

- `POST /v1/account/export`, after a `data_export` step-up, returns one JSON document with `Content-Disposition: attachment` and `Cache-Control: no-store`: a schema version, the export time, and every registry entry the account owns, through each entry's projection; field-encrypted values are masked in it (spec 0005 R6), a portability trade-off recorded in ADR-0017. The response schema is in `packages/api-contract`.
- Built per request, never stored, logged or traced beyond the allow-listed fields. An audit event records it.
- As built: the export reads each registry entry through its projection, `auth` entries on the `app_auth` pool in one read-only repeatable-read transaction and every other entry on `app_api` under the account's identity; a child entry is joined to its parent through the foreign key the registry names (`columns` to the parent's `parentColumns`, both checked by the registry guard). Values come out as JSON from the database, so timestamps are ISO 8601; any `bytea` value (ciphertext or key material) becomes the fixed placeholder "Protegido. Veja no Arca.", so a column added to a projection by mistake leaks no byte of it; the registry guard allows only built-in scalar column types, `bytea`, and `jsonb`, `int8` and `numeric`, which the export carries as their text so no reader rounds them (#237), in a projection, so a domain, an array, plain JSON or a float fails CI instead of slipping past the mask or the contract. Labels are the pt-BR names of the tables. The route answers 403 `step_up_required` without a fresh `data_export` step-up for `exportAccountData` with no target, so each export spends its own; the file name carries the date only (the header's name serves direct API clients; the web saves the document under its own pt-BR name). The `data_exported` event is recorded after the document is built. The settings page offers it as "Seus dados" to a signed-in account, with a confirmation before the step-up, and saves the file in the browser.

### R9. Account deletion

- `POST /v1/account/deletion` after an `account_deletion` step-up: revokes every session, marks the account `pending_deletion` with a due time 7 days ahead, writes a `deletion requested` audit event with reason `owner_request`, and sends notices. While pending, sign-in shows only "cancel deletion" (`DELETE /v1/account/deletion`, which needs a fresh `account_deletion` step-up and writes a `deletion cancelled` audit event with reason `owner_cancel`).
- A daily workflow finds due accounts and starts `eraseAccount(accountId)` for each (identifiers only, through the shared start helper). Its steps, in order and each idempotent: remove stored objects first (spec 0005 R4; a missing object counts as deleted); erase every registry entry the account owns (as `app_jobs` under the account's identity); send the completion notice by email only, in a step that reads the address from `auth.user` on the `app_auth` pool and sends it in the same step (no notification row is produced for an account once its registry erase has started); erase the auth rows (as `app_auth`), and delete the expired rows of the unowned `until-expiry` tables (R7), so ceremony state that may name the account outlives it by at most its own lifetime; write an `account_erased` audit event, which is last. Vault cleanup joins with spec 0005.
- `app_jobs` gains exactly the privileges the registry needs, plus those the workflow steps of each slice name (for example spec 0005 R7's delivery writes), each identity-bound, through migrations reviewed by the data-access reviewer. Each entry names its erasing pool: `app_auth` for the `auth` tables (no row-level security; the guard checks the entry names that pool), `app_jobs` for everything else. Every `app_jobs` `delete` entry has a permissive `app_jobs` `DELETE` policy whose qualifier is the request identity on the entry's owner column (`owner = nullif(current_setting('app.account_id', true), '')::uuid`, the form spec 0001 set), plus an `app_jobs` `SELECT` policy with the same qualifier, since Postgres applies `SELECT` policies to a filtered `DELETE`; the registry guard asserts both, because under forced row-level security a missing policy deletes zero rows without an error and a qualifier of `true` would let one step erase every account. The access-matrix suite checks that `app_jobs` with identity A deletes nothing owned by B. The erase test includes a document of A shared with B, erased in both orders (spec 0005 R4). Auth rows are erased on the `app_auth` pool.
- As built: the pending state is `auth.user.deletion_due_at`, set by the request (a second request keeps the first time) and cleared by a cancel only while it is still in the future, so once due the erasure owns the account and a cancel answers 404. The request ends every session in the same transaction (each recorded as `session revoked`, the open challenges bound to them going by their cascades); `GET /v1/session` carries `deletionDueAt`, and while it is set every route but the session, step-up options and verify, signing in and out and the cancel answers 403 `deletion_pending`. With a recovery pending too, the recovery's restriction applies and the cancel stays open, so the owner can stop both. The home page then shows only the due time and the cancel; the settings page offers "Excluir conta" with a confirmation before the step-up. Notices: `deletion requested`, `deletion cancelled`, and `account erased` for completion. The daily cron `/internal/cron/account-erasure` scans `auth.user` and `auth.erased_account` on `app_auth` and starts one `eraseAccount` run per due or noted account; a start that fails does not hold back the others. Its first step checks the account is due or already gone (a retry after its auth step), so a cancelled account is never erased. The app_jobs step deletes every column-owned `app_jobs` entry under the account's identity (none exist yet); the auth step deletes the column-owned `auth` entries in reverse registry order, the account row last, then the expired rows of the `until-expiry` tables; `app_auth` gained `DELETE` on `auth.recovery_lock` for it. In the same transaction it notes the account in `auth.erased_account` (the ID only, unowned), so a run that fails after it is started again the next day; the event step records `account erased` and deletes the note in one transaction, so the event is recorded once per note. A cancel compares with the statement's time and the first step locks the account row, so a cancel in flight at the due time either wins or answers 404. Stored objects and shared documents join with spec 0005.
- **Rule for every `app_jobs` step:** its arguments carry the account ID next to the entity ID (identifiers only), taken from the authenticated session that started the work or from a server-side scan, never from a client-supplied field; the step sets the identity before its first read; with no identity, no rows.
- Exception ([ADR-0027](../adr/0027-admins-and-the-checked-batch-activation.md)): the independent check's step takes a start ID, a route ID and a version number and runs with no identity. It reads only public rule data and inserts into `knowledge.independent_check`, an unowned table with no personal data whose `app_jobs` select and insert policies are `true`; it reads and writes nothing an account owns.
- Tests: a synthetic account with rows in every registry entry's table is fully erased, checked by counting on the test database's superuser connection, which row-level security does not filter; in the unowned `until-expiry` tables only unexpired rows remain (in previews and CI that includes the completion notice in the outbox); the audit trail remains with identifiers only; a cancel inside the window keeps everything; running the workflow twice is harmless, including a retry after the `account erased` event was recorded; the completion notice goes out and no notification row is left behind.

### R10. Retention jobs

- One daily workflow, `enforceRetention(runDate)`, runs every database rule in [RETENTION.md](../RETENTION.md). Rules on `auth` tables run on the `app_auth` pool. Rules on row-level-security tables run per account: a step lists account IDs from `auth.user` on the `app_auth` pool (identifiers only) and, for each, expires that account's rows as `app_jobs` under its identity, so the identity-bound erase policies hold; an access-matrix case checks that the step under identity A leaves B's expired rows. The rules: expired sessions, invites, step-up challenges, recovery links and lockouts, registration contexts, rate-limit rows, notification messages, rotated vault envelopes older than 90 days and pending document uploads older than 24 hours once spec 0005 adds them, the non-production outbox, and the inactivity notice and deletion (3 years plus 60 days), and invited accounts still unconfirmed after 30 days (erased through `eraseAccount`). Every retention erasure is recorded first, so a restore can corroborate it (R12): the inactivity job writes a `deletion requested` event with reason `inactivity` when it sends the notice, and a `deletion cancelled` event with reason `sign_in` if the account signs in before the deletion; an unconfirmed invited account gets one with reason `invite_unconfirmed` before `eraseAccount` starts, and a declined one (spec 0003) with reason `invite_declined`.
- As built: `auth.user.deletion_reason` (`owner_request`, `inactivity`, `invite_declined`, `invite_unconfirmed`) is set exactly while `deletion_due_at` is, by a check constraint. The daily cron `/internal/cron/retention` (06:15 UTC) starts `enforceRetention(runDate)`, whose steps each read their own clock and pass it down, so every cutoff is computed in code: the cleanup deletes, on `app_auth` in one transaction, expired sessions, step-up challenges, recovery links, registration contexts and outbox rows, ended recovery locks whose count is reset, and expired invites never accepted (each with its `invite expired` event); the per-account step runs the rules on row-level-security tables as `app_jobs` under each account's identity, and has no rule until spec 0005; the unconfirmed step marks invited accounts created 30 days or more before and never confirmed; the inactivity step marks accounts whose last sign-in (or creation, if none) is 3 years or more before, due 60 days later, sending the `inactivity warning` email inside the transaction so an account is never marked without its warning. Each mark rechecks its reason under the update, ends the account's sessions and records `deletion requested` before its commit; the daily `eraseAccount` runs (07:00 UTC) erase the accounts once due. A decline marks the account due at once and starts `eraseAccount` itself. The sign-in hook cancels an `inactivity` mark still in its 60 days and records `deletion cancelled` (`sign_in`); an owner's request is never cancelled by a sign-in. The rate-limit windows keep their own daily sweep (spec 0003, R10). A failure for one account does not hold back the others; the step fails afterwards, so its retry picks up the rest. The completion notice no longer says the owner asked for it, since retention erasures send it too.
- A test seeds rows on both sides of each boundary and asserts which remain. A docs test fails if a RETENTION.md row whose enforcement names the daily cleanup or inactivity job has no rule in the workflow, or the workflow enforces a rule no such row lists. Rows enforced by the registry, an expiry check or a later ADR are out of the test's scope, and so are rows for tables not yet migrated (notification messages before spec 0005).

### R11. Incident response

- `docs/runbooks/incident-response.md`: severity levels; who does what (the owner is controller and incident lead; agents assist by reading and proposing: they never run a containment step themselves, each step is run by the owner or after the owner's explicit confirmation of that step, and Sentry, log or alert content is never a trigger for an action); a first-hour checklist; containment steps with links and exact actions:
  - block the API at the edge with a Vercel Firewall deny rule on `/v1/*` (instant, no deploy);
  - roll back with Vercel Instant Rollback;
  - revoke every session by rotating `BETTER_AUTH_SECRET`, deleting every `auth.session` row and every open step-up challenge, and redeploying;
  - rotate each secret in the data-flow table and the Vercel and GitHub variables, with where and how;
  - stop crons;
  - restore the database with Neon point-in-time restore (R12).
- Evidence to keep, and where. Notification: under Resolução CD/ANPD 15/2024, the ANPD and affected people within 3 business days of learning that an incident affected personal data, with the official form's link and a pt-BR template for each notice. A post-incident review template.
- No drills or tabletop exercises: the project owner dropped the yearly tabletop on 2026-11-05 as out of proportion for a family app (the quarterly restore drill went earlier, with the off-vendor backups, R12).
- `/.well-known/security.txt` served by the API, with the repository's private vulnerability reporting URL as `Contact`, `Expires` one year ahead, `Preferred-Languages: pt-BR, en`; a test fails 30 days before it expires.

### R12. Backups

Amended by [ADR-0021](../adr/0021-stay-on-vercel-and-neon.md) on 2026-11-04: backups are Neon's own, and nothing runs on AWS. The off-vendor copy this section first specified (an `app_backup` role, a daily dump into a separate AWS account under Object Lock, a CodeBuild restore and quarterly drills) is not built.

- Neon's point-in-time restore within the plan's history window (6 hours on Free) is the backup. The project owner may take a manual Neon snapshot before a risky change; nothing in the app depends on one.
- The incident runbook (R11) gives the restore steps: Neon restores the production branch to a time and keeps the replaced state as a backup branch; the security events, deletion requests and erasures recorded after the restore point are read from that backup branch's audit log and re-applied before the API is unblocked; every account is then told to check its devices and regenerate its kit, since credentials come back as they were.
- `app_backup` loses its login, read policy and grants, and guard 10 and `ARCA_DB_BACKUP_PASSWORD` go. Bootstrap keeps the role, unable to log in, only so the migrations that once granted to it replay on a new database; guards 3, 5 and 6 still check it. The erasure tombstone step and its port are removed (R9).

## Threat model for this slice

| Threat | Where | Control |
| --- | --- | --- |
| Information disclosure: production data in a preview | Neon branches | `development` default; production lineage mark fails any preview forked from production |
| Information disclosure: personal data in telemetry | Sentry, logs | One allow-list scrubber, applied twice for browser events; no replay; tests with synthetic personal data |
| Tampering: the tunnel used as an open relay | API | Our DSN only, size cap, rate limit, scrub |
| Elevation: deletion or export by someone holding a session | Account | Purpose-bound step-up; 7-day locked window with cancel; notices |
| Repudiation, and incomplete deletion | Registry | Guard fails on unregistered tables; audit events with identifiers only |
| Loss of data | Database | Neon point-in-time restore within the history window; an optional manual snapshot; residual, accepted: losing the Neon or Vercel account loses the data ([ADR-0021](../adr/0021-stay-on-vercel-and-neon.md)) |
| Slow response to an incident | Operations | Runbook with exact steps; ANPD deadline and templates |
