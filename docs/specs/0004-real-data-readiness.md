# Spec 0004: Real-data readiness

- Status: Ready for tickets
- Date: 2026-11-02
- Epic: cross-platform foundations ([ROADMAP.md](../ROADMAP.md#phase-1--family-mvp-web)), after [spec 0001](0001-foundations-scaffold.md)
- Decisions: [ADR-0017](../adr/0017-data-lifecycle-and-backups.md), [ADR-0016](../adr/0016-observability-and-scrubbing.md), [ADR-0012](../adr/0012-automation-first-setup.md), [ADR-0008](../adr/0008-database-security-and-environments.md), [ADR-0009](../adr/0009-background-jobs-guarantees.md); uses [spec 0003](0003-identity-and-access.md) for step-up and the audit log

## Goal

Everything SECURITY.md and ROADMAP.md require before the first real family data enters production: previews provably separate from production, a synthetic seed, error and trace reporting that cannot carry personal data, deletion and export that cover every table, retention enforced, an incident runbook, off-vendor backups, and the epic's threat model. It ends with a **real-data gate**: a checklist that must be complete before production accepts family data.

## Scope

**In:** the `development` branch and the lineage check; the synthetic seed; `packages/telemetry` and its scrubber; Sentry on server and client through our tunnel; the personal-data registry and its guard; export; account deletion; retention jobs; the incident response runbook and `security.txt`; off-vendor backups; the threat model for the epic; the real-data gate.

**Out:** Langfuse wiring (with the first model call, R6 records its requirements); the vault and field encryption (spec 0005); the designated-adult recovery factor and case-model registry entries (consultancy core).

**No case data.** Seed and tests are synthetic. Nothing here reads real data, except the backup job in production, which copies production rows into our own KMS-encrypted bucket in São Paulo.

## Requirements

### R1. Previews fork from `development`, and the build proves it

- **Owner, once, between two bounds:** after the first marked production build (done 2026-11-02, so `development` inherits the endpoint mark of spec 0001 R9) and before the R1 change merges (so it does not inherit the lineage mark), in the Neon console (Vercel › Storage › `arca` › Open in Neon), create branch `development` from `production`, then set it as the default branch. The production branch setting stays `production`. The ticket gives the exact clicks and links in one message.
- A preview build that fails on the lineage mark also alerts the owner through Sentry, and the runbook's first step is deleting that preview branch, which already holds copied rows.
- Recovery if `development` must ever be recreated after R1: before the real-data gate passes (production holds no family data), the owner may re-fork it from production and remove the lineage mark on the new branch in one reviewed step, recorded in the PR, as spec 0001 R9 does for the endpoint mark. After the gate it is never forked from production: it is rebuilt from an empty branch on which the owner writes the production endpoint mark by hand (spec 0001 R9's reviewed `COMMENT ON DATABASE` step) without the lineage mark, so the next preview build migrates and seeds its own fork of it, and `development` itself is migrated and seeded once by a build pointed at it; removing the lineage mark from a fork is forbidden. A runner test covers an empty schema with the endpoint mark and no lineage mark.
- The production build writes a lineage mark, the comment `arca lineage: production` on the runner's `arca_migrations` schema, in the bootstrap transaction. It is separate from the database comment that carries spec 0001 R9's endpoint mark, so the existing endpoint parser is untouched; Neon branches inherit both. A preview build that finds the production lineage mark fails before migrations, with an error code that names the cause. The migration runner re-reads both marks inside its own transaction, so the check does not depend on the order of build steps.
- Tests in `tooling/scripts` cover: a preview database with the lineage mark fails; one with the endpoint mark and without the lineage mark passes; one with no mark at all keeps failing (spec 0001 R9); production writes the lineage mark idempotently.
- After merge, the first preview of any later pull request is the end-to-end proof; the ticket records it.

### R2. Synthetic seed

- `packages/db/seed/` holds synthetic data as typed fixtures with fixed UUIDs, and a seed command in `tooling/scripts` that applies them idempotently after migrations, in preview builds and in CI. The production build never runs it, checked by the database target of spec 0001 R9.
- The seed writes through the runtime roles (`app_auth` for accounts, `app_api` under each synthetic account's identity for case data later), so row-level security applies to the seed as to the app.
- Accounts use addresses at `example.com`. Each slice that adds tables adds seed data for them.

### R3. One scrubber

- New package `packages/telemetry`, with no workspace dependencies, usable from `apps/api` and `apps/web` (boundary matrix updated). It exports the field allow-lists and the scrub functions that every exporter uses: the existing logger (moved here from `apps/api`, which then imports it), Sentry's hooks on server and client, the tunnel, and later Langfuse's masking function.
- Rules (ADR-0016): allow-listed fields with shape checks; the only identifiers admitted are request ID, trace ID, release and environment (never account, case, document or session IDs); database spans keep operation and table, never statement text; CSP violation reports have their own allow-list; exception messages dropped (class name and error code kept); URLs reduced to route patterns; no bodies, cookies, query strings, local variables, user objects or IP addresses; allow-listed headers only.
- Stack frames keep file, function and line only after shape and length checks (path-like file names, identifier-like function names); CSP report URLs are reduced like other URLs.
- A table-driven suite pushes synthetic personal data (names, emails, CPF-, RG- and passport-shaped values, phone numbers, addresses, free text) through every exporter path and asserts none survives, plus an adversarial envelope whose frames and report fields carry instruction-like text, which must be dropped or truncated.
- The logger gains `traceId` as an allowed field.

### R4. Sentry on the server

- `@sentry/node` with the Hono integration (11.x), initialized before the app, with `sendDefaultPii: false`, local variables off, profiling off, `beforeSend`, `beforeSendTransaction` and `beforeBreadcrumb` from `packages/telemetry`. Traces sampled at 10% in production and 100% in previews; spans named by route pattern; workflow steps traced under their generic names.
- The DSN and the environment names live in a repository configuration file. The source-map upload token is a Sensitive Vercel variable (`SENTRY_AUTH_TOKEN`, **Production only**, scoped to releases on the one project, scopes recorded in the ticket), added to the lint rule's list of variables only build scripts may read (Vercel also exposes it to functions, ADR-0012); previews skip the upload. Source maps are uploaded with `@sentry/vite-plugin` (bundler telemetry off) and deleted from the output.
- Packages: `@sentry/node`, `@sentry/hono`, `@sentry/react`, `@sentry/vite-plugin`, each in the Versions table with a supply-chain PASS. `@sentry/vite-plugin` pulls `@sentry/bundler-plugin-core` and `@sentry/cli` (license FSL-1.1-Apache-2.0, and an install script that downloads the CLI binary); the ticket checks this against the npm registry, then either records a pinned license exception (used unmodified as build tooling, install script allowed by name) or keeps them out, and proves the deployed function bundle contains neither.
- **Owner, once:** create the Sentry organization in the German data region on the free Developer plan, with a passkey on the account; give the agent a setup token with the minimum scopes (project write, alert rules write, release token creation) and the shortest expiry Sentry allows, revoked by the owner when the ticket closes. The agent creates the project, alert rules (new issue, regression, email to the owner) and the upload token through Sentry's API, and the Vercel variable after the owner's OK.
- Agent tooling that reads Sentry issues (ADR-0016) uses a read-only token scoped to the one project, wraps issue content as delimited untrusted data, and ships with an evaluation case where injected issue text asks for a containment action and the expected result is a proposal to the owner, not an action.
- A test endpoint that exists only in previews throws a synthetic error carrying synthetic personal data; the ticket shows the resulting Sentry event without it.

### R5. Sentry in the browser, through our origin

- `@sentry/react`, bundled, errors only; no session replay, no console breadcrumbs; fetch breadcrumbs reduced to route patterns; the same scrub hooks.
- `tunnel: true`; the API serves the tunnel, accepts only our DSN (`allowedDsns`), caps the envelope at 200 KB, rate-limits per IP, and scrubs again before forwarding. The tunnel path is excluded from the SPA fallback in `tooling/security-policy` and answers `Cache-Control: no-store`.
- CSP and Trusted Types violation reports (`report-to` and `Reporting-Endpoints`) go to a second path of the same Hono route, which validates the Reporting API payload against its own allow-list and forwards it to Sentry's security-report endpoint. The tunnel is a Hono route, not a Nitro integration. The CSP keeps `connect-src 'self'`.
- Playwright: an error in the web app reaches the tunnel, and no request leaves the origin.

### R6. Langfuse, when the first model call lands

Recorded here so the requirement is not lost; implemented by the consultancy core's first AI adapter.

- Langfuse Cloud, EU region; the masking function from `packages/telemetry` exports no prompt or completion text: prompt version and hash, lengths, token counts, model, latency, scores, error codes and allow-listed fields only; an ID generated per call on a new root trace that inherits no active trace context, never account, case or document IDs, with a scrubber-suite assertion that it differs from the request ID and the active trace ID; the data-flow table and RETENTION.md updated in the same change. The R3 suite gains model-call cases, a `DocumentReader` call included.
- Langfuse trace IDs are generated per call; they are never the request ID, which the audit log stores next to account IDs.
- Before then, R4 keeps Sentry's AI integrations off through an explicit integration list asserted by a test, and allow-lists span attributes.

### R7. Personal-data registry

- `packages/db/src/registry.ts`: for each table in a user schema, an entry (owner column, erase strategy `delete` or `retain`, export projection, an i18n label key for the export) or a place on the "no personal data" list with a reason.
- A guard test reads `pg_catalog` after migrations and fails on any table in neither list, and on any registry entry for a table that does not exist. It runs in the `db` CI check.
- Strategies: `delete`, and `retain` (kept after erasure with identifiers only, with a reason and a period; for `audit.event`, 5 years). Data shared with others is modelled so each person's part is their own rows (for example one recipient row per share), so `delete` covers it. Purging `retain` rows needs its own ADR before the first period ends, because it changes ADR-0008's insert-only audit log.
- Foreign keys: none from `audit`; none that cascade into `auth`, so erasure only happens through the registry, after its audit event.
- Initial entries: the `auth` tables and `audit.event` (spec 0003).

### R8. Export

- `POST /v1/account/export`, after a `data_export` step-up, returns one JSON document with `Content-Disposition: attachment` and `Cache-Control: no-store`: a schema version, the export time, and every registry entry the account owns, through each entry's projection; field-encrypted values are masked in it (spec 0005 R6), a portability trade-off recorded in ADR-0017. The response schema is in `packages/api-contract`.
- Built per request, never stored, logged or traced beyond the allow-listed fields. An audit event records it.

### R9. Account deletion

- `POST /v1/account/deletion` after an `account_deletion` step-up: revokes every session, marks the account `pending_deletion` with a due time 7 days ahead, writes a `deletion requested` audit event, and sends notices. While pending, sign-in shows only "cancel deletion" (`DELETE /v1/account/deletion`, which needs a fresh `account_deletion` step-up and writes a `deletion cancelled` audit event).
- A daily workflow finds due accounts and starts `eraseAccount(accountId)` for each (identifiers only, through the shared start helper). Its steps, each idempotent: remove stored objects first (spec 0005 R4; a missing object counts as deleted); erase every registry entry the account owns (as `app_jobs` under the account's identity); erase the auth rows (as `app_auth`); write an `account_erased` audit event. Vault cleanup joins with spec 0005.
- `app_jobs` gains exactly the privileges the registry needs, through migrations reviewed by the data-access reviewer. Each entry names its erasing pool: `app_auth` for the `auth` tables (no row-level security; the guard checks the entry names that pool), `app_jobs` for everything else. Every `app_jobs` `delete` entry has a permissive `app_jobs` `DELETE` policy whose qualifier is the request identity on the entry's owner column (`owner = nullif(current_setting('app.account_id', true), '')::uuid`, the form spec 0001 set), plus an `app_jobs` `SELECT` policy with the same qualifier, since Postgres applies `SELECT` policies to a filtered `DELETE`; the registry guard asserts both, because under forced row-level security a missing policy deletes zero rows without an error and a qualifier of `true` would let one step erase every account. The access-matrix suite checks that `app_jobs` with identity A deletes nothing owned by B. The erase test includes a document of A shared with B, erased in both orders (spec 0005 R4). Auth rows are erased on the `app_auth` pool.
- **Rule for every `app_jobs` step:** its arguments carry the account ID next to the entity ID (identifiers only), taken from the authenticated session that started the work or from a server-side scan, never from a client-supplied field; the step sets the identity before its first read; with no identity, no rows.
- The last step writes an erasure tombstone (account ID and time) to the backup account's tombstones bucket (R12) through a port: production uses the S3 adapter; previews and CI use a no-op adapter that production refuses to select, like the email outbox.
- Tests: a synthetic account with rows in every registered table is fully erased, checked by counting as `app_backup` (whose read policy is the one honest counter under row-level security) for backed-up tables and as `app_auth` for the `auth` tables it cannot read (sessions, challenges, link tokens, rate-limit rows, outbox); the audit trail remains with identifiers only; a cancel inside the window keeps everything; running the workflow twice is harmless.

### R10. Retention jobs

- One daily workflow, `enforceRetention(runDate)`, runs every database rule in [RETENTION.md](../RETENTION.md). Rules on `auth` tables run on the `app_auth` pool. Rules on row-level-security tables run per account: a step lists account IDs from `auth.user` on the `app_auth` pool (identifiers only) and, for each, expires that account's rows as `app_jobs` under its identity, so the identity-bound erase policies hold; an access-matrix case checks that the step under identity A leaves B's expired rows. The rules: expired sessions, invites, step-up challenges, recovery links and lockouts, registration contexts, rate-limit rows, notification messages and rotated vault envelopes older than 90 days once spec 0005 adds them, the non-production outbox, and the inactivity notice and deletion (3 years plus 60 days).
- A test seeds rows on both sides of each boundary and asserts which remain. A docs test fails if a RETENTION.md row whose enforcement names the daily cleanup or inactivity job has no rule in the workflow, or the workflow enforces a rule no such row lists. Rows enforced by the registry, an expiry check or a later ADR are out of the test's scope, and so are rows for tables not yet migrated (notification messages before spec 0005).

### R11. Incident response

- `docs/runbooks/incident-response.md`: severity levels; who does what (the owner is controller and incident lead; agents assist by reading and proposing: they never run a containment step themselves, each step is run by the owner or after the owner's explicit confirmation of that step, and Sentry, log or alert content is never a trigger for an action); a first-hour checklist; containment steps with links and exact actions:
  - block the API at the edge with a Vercel Firewall deny rule on `/v1/*` (instant, no deploy);
  - roll back with Vercel Instant Rollback;
  - revoke every session by rotating `BETTER_AUTH_SECRET`, deleting every `auth.session` row and every open step-up challenge, and redeploying;
  - rotate each secret in the data-flow table and the Vercel and GitHub variables, with where and how;
  - stop crons;
  - restore the database with Neon point-in-time restore, or from the backup (R12).
- Evidence to keep, and where. Notification: under Resolução CD/ANPD 15/2024, the ANPD and affected people within 3 business days of learning that an incident affected personal data, with the official form's link and a pt-BR template for each notice. A post-incident review template.
- The quarterly restore drill (R12) and a yearly tabletop exercise, each with a results log in `docs/runbooks/drills.md`.
- `/.well-known/security.txt` served by the API, with the repository's private vulnerability reporting URL as `Contact`, `Expires` one year ahead, `Preferred-Languages: pt-BR, en`; a test fails 30 days before it expires.

### R12. Off-vendor backups

- `bootstrap.sql` creates `app_backup` (`NOBYPASSRLS`, `SELECT` only), with its password from `ARCA_DB_BACKUP_PASSWORD` in production; preview builds set a random throwaway password generated in the build and never stored, so a branch never keeps production's verifier and guard 3 holds in every environment. Guard 3 adds it to the login roles; on the tables outside row-level security (`auth`), it gets `SELECT` grants only on the tables worth restoring (users, passkeys, recovery-code hashes, step-up assertions, the `auth.setup` enrollment record), never on sessions, challenges, link tokens, rate-limit counters or the outbox, which are short-lived and would put live tokens in the backup; a new guard 10 checks the catalog: every table in the user schemas is readable by `app_backup` (`has_table_privilege`) unless it is on an explicit not-backed-up list with a reason, and no table on that list is readable by `app_backup` or carries an `app_backup` policy; every row-level-security table has a policy that is permissive, `polcmd = 'r'`, `polroles` exactly `{app_backup}`, qualifier literally `true`, no `WITH CHECK`; and no policy whose roles include `PUBLIC` (`polroles` containing `0`, which is what a policy without `TO` gets) or `app_backup` has any other shape, so every other policy must name its roles with `TO`. The access-matrix suite covers `app_backup` (reads everything backed up, writes nothing, and is denied on each not-backed-up table) and `app_jobs`.
- `infra/aws/backup-account.yaml`, a CloudFormation template the owner launches once in a new AWS account dedicated to backups, in `sa-east-1`: the IAM identity provider for Vercel's OIDC issuer; a writer role trusting only `owner:<team>:project:arca:environment:production`, allowed `s3:PutObject` on the dumps and tombstones buckets and `kms:GenerateDataKey` on the key and nothing else; a restore role for the owner with MFA; a customer-managed KMS key; three buckets, each with versioning, Object Lock (compliance, 35 days), default SSE-KMS, public access blocked and TLS required: **dumps** (current versions expire after 35 days, noncurrent versions 1 day later), **tombstones** (same rules), and **document replica** (below). A quick-create link needs a hosted template, which a new account lacks, so the ticket gives console-upload steps for the repository file at a named commit, with its SHA-256, so the owner can check they launch the reviewed template.
- The **document replica** bucket stays empty until spec 0005 R3 adds the application account and the replication grants. It receives S3 replication from the application account's production document bucket (spec 0005 R3; documents are client-side ciphertext), with delete markers replicated (application deletes are plain `DeleteObject` calls and no application role holds `s3:DeleteObjectVersion`, checked by a template test, because version-specific deletes are not replicated); current versions never expire and noncurrent versions expire after 35 days, so losing the application account does not lose documents and a deleted document leaves the replica 35 days later. The replica is written by S3 replication, not by any Vercel role. Residual, accepted: the field-encryption KMS key cannot leave its account, so losing that account loses the encrypted fields; the account is protected by MFA and few fields use it.
- Packages: the AWS SDK v3 S3 client and the OIDC bridge. The bridge uses `getVercelOidcToken` with the AWS SDK's web-identity provider at the `@vercel/oidc` and `@vercel/functions` versions already accepted in the trust policy, or the owner accepts a newer one again. Every package goes in the Versions table with a supply-chain PASS, and Dependabot groups `@aws-sdk/*`, `@smithy/*` and `@aws-crypto/*` on a monthly schedule.
- A daily production cron starts `backupDatabase(runDate)`. Its step: `REPEATABLE READ, READ ONLY` transaction as `app_backup`; for each table in the catalog minus the not-backed-up list, in dependency order (the step fails if that list differs from what `app_backup` can read), `COPY … TO STDOUT` cut into objects of at most 64 MB, each sent through the `ObjectStorage` port's conditional put (`putIfAbsent`, an `If-None-Match: *` `PutObject` in the S3 adapter; the port lives in `apps/api` with an in-memory adapter production refuses to select, and spec 0005 adds presigning and delete) (multipart would need `kms:Decrypt`, which the writer must not have); then a manifest (migration journal head, tables, row counts, SHA-256 per object). AWS credentials come from Vercel OIDC; no static keys.
- **Restore, drill or real,** never touches a laptop: it runs as an AWS CodeBuild project in the backup account in `sa-east-1`, defined in the same template, started by the owner from the console after an MFA sign-in, assuming the restore role. The owner picks the backup by date; the job reads the manifest and every object by explicit version ID (the runbook tells the owner to pick a backup from before any suspected compromise of the production writer; every key is written once with a conditional `If-None-Match: *` put that the bucket policy enforces with the `s3:if-none-match` condition key; object keys carry the workflow run ID and a random attempt ID drawn at the start of each step attempt, and the manifest, written last, is the only index of the objects that form a backup, so a step retry inside the same run writes fresh keys instead of colliding, and partial attempts simply expire under the 35-day rule; the restore lists every complete manifest for the chosen date and stops if there is more than one until the owner picks one, and refuses any run whose objects' S3 `LastModified` falls outside that date's backup window, so a compromised writer cannot add a run for a past or future date; a key that already exists (only possible if someone else wrote it) fails the step and alerts; the restore refuses a key with more than one version, and the manifest names each object's version ID and SHA-256), so a compromised production writer can add objects but cannot alter a chosen backup. It loads it into a Neon branch of the production project (a throwaway one for the drill): it stops unless the branch's migration journal head equals the manifest's; inside one transaction it truncates every table in the user schemas except the migration runner's journal (which the head check just verified), backed up or not, in a single statement, and copies the dump in dependency order; then it compares the loaded row counts and hashes with the manifest. It refuses the project's default and production branches and any branch not created for that run (name prefix and creation time). It connects as that branch's Neon owner. On the restore branch only, the job grants the branch's Neon owner membership in `app_migrator`, the tables' owner, and loads with `SET ROLE app_migrator`; inside the load transaction it switches forced row-level security off on each table, truncates and copies, and switches it back on before commit, so the load relies on table ownership, not on any role attribute. The membership is revoked before the job reports success, and the job checks the role memberships against spec 0001's guard 5, then runs the migration runner's guards 1 to 10 and the lineage mark check in a verify-only mode (`--verify-only`: one read-only transaction, no bootstrap and no migration, so spec 0001 R9's rule against bootstrapping or migrating outside a Vercel build is untouched; the endpoint mark is not checked, since the branch has a new endpoint); the drill asserts the guards pass. Before a restored branch takes traffic, the owner rewrites the endpoint mark to its endpoint (`COMMENT ON DATABASE` as the owner, the reviewed step spec 0001 R9 already describes), then a production build runs with the full guards. The restore runs from an image that a separate image-build CodeBuild project in the backup account builds from the commit the runbook names (script, Postgres client and dependencies installed from the frozen lockfile and checksum-verified sources) and pushes to the account's registry; that project has internet access but no access to backups, KMS keys or secrets, and records the commit and resulting digest, which the restore project's parameter pins. The restore project runs in a VPC whose security group allows egress only on TCP 5432 (Neon publishes no fixed inbound IP ranges, so the port, not the host, is the limit) and on HTTPS to the account's S3, KMS and Secrets Manager VPC endpoints, so nothing is fetched at run time; the residual, a compromised image sending data to another Postgres host, is bounded by the reviewed image source. Each drill records the image digest and its source commit in `docs/runbooks/drills.md`. Its logs go to an explicit KMS-encrypted CloudWatch log group with 35-day retention (no S3 logs), and the script catches load errors and prints only the table name and SQLSTATE, never an input line. Before the run the owner resets that role's password on the restore branch only (Neon roles are per branch), stores it in AWS Secrets Manager for the CodeBuild run (never a plain environment variable, never logged), and deletes the branch (drill) or resets the password again (real restore) afterwards, as ADR-0017 accepts. Restored data lives only in that production branch. A real restore, before the branch serves any request, copies every audit record newer than the backup from the old production branch when it survives (so the append-only log has no gap; the drill checks for gaps) and re-applies the security events among them (passkeys revoked or cancelled, recovery codes regenerated or cancelled, sessions revoked), erases every account named by an `account_erased` event newer than the backup in the surviving production branch's audit log, and every account named by a tombstone corroborated by a `deletion requested` event at least 7 days older with no later `deletion cancelled` event (so erased accounts are not resurrected even when the live audit log was lost); any other tombstone is listed and the job stops until the owner confirms or discards it, re-applies deletion requests the surviving audit log records after the backup, then switches production to the branch (the runbook gives the Neon and Vercel steps) and sends every account a security notice to check its devices and regenerate its kit, since credentials come back as they were at the backup.
- Failure alerts through Sentry. The ticket proves one run in production and records the first restore drill in `docs/runbooks/drills.md`.

### R13. Threat model and the real-data gate

- `docs/threat-models/foundations.md`: STRIDE plus the LLM and agentic risks for the whole foundations epic (specs 0001, 0003, 0004, 0005), assets, trust boundaries and data flows, each threat mapped to its control and test, and the accepted residuals with the ADR that accepts them.
- **Real-data gate**, kept as a checklist in the epic issue and in `docs/runbooks/real-data-gate.md`. Production accepts family data only when all are true:
  1. Previews fork from `development`, proven by R1.
  2. Spec 0003 is done in production on the production domain, including recovery.
  3. Sentry reports from server and client, scrubbed (R3 to R5).
  4. Registry guard, export and deletion work (R7 to R9).
  5. Retention jobs run (R10).
  6. Runbook written and one tabletop done (R11).
  7. Backups run daily and one restore drill passed (R12).
  8. The threat model is written and reviewed (R13).
  9. The access-matrix suite covers every table with case data.

## Threat model for this slice

| Threat | Where | Control |
| --- | --- | --- |
| Information disclosure: production data in a preview | Neon branches | `development` default; production lineage mark fails any preview forked from production |
| Information disclosure: personal data in telemetry | Sentry, logs | One allow-list scrubber, applied twice for browser events; no replay; tests with synthetic personal data |
| Tampering: the tunnel used as an open relay | API | Our DSN only, size cap, rate limit, scrub |
| Elevation: deletion or export by someone holding a session | Account | Purpose-bound step-up; 7-day locked window with cancel; notices |
| Repudiation, and incomplete deletion | Registry | Guard fails on unregistered tables; audit events with identifiers only |
| Loss of data | Database | Neon point-in-time restore; daily off-vendor copy under Object Lock; quarterly drill |
| Information disclosure: backup read by a compromised API | Backups | Writer role cannot read, decrypt or delete; restore role outside Vercel with MFA |
| Elevation: the restore job's Neon credential misused, or pointed at production | Restore | Branch-scoped owner password reset per run, held in Secrets Manager, never logged; the job refuses default, production and pre-existing branches |
| Elevation: `app_backup` misused | Database | `SELECT` only; Production-only password; policy shape guarded |
| Slow response to an incident | Operations | Runbook with exact steps; ANPD deadline and templates; drills |

## Definition of done

- Every requirement is covered by a test or a recorded proof (R1, R4, R12).
- The real-data gate checklist exists and is tracked in the epic.
- RETENTION.md, ARCHITECTURE.md's data-flow table and SECURITY.md match what was built.
- No personal data anywhere in the diff.
