# Spec 0002: Rules engine and knowledge base

- Status: Ready for tickets
- Date: 2026-11-02
- Epic: consultancy core ([ROADMAP.md](../ROADMAP.md#phase-1--family-mvp-web)), slice 1
- Decisions: [ADR-0014](../adr/0014-knowledge-base-as-reviewed-data.md), [ADR-0002](../adr/0002-rules-as-versioned-data.md), [ADR-0004](../adr/0004-ai-providers-behind-ports.md), [ADR-0010](../adr/0010-stack-revised.md)

## Goal

The deterministic core that every consultancy service reads: a rule schema that can express any route, a pure evaluation engine that applies a route version to a case snapshot, unit computation per route, and a knowledge catalog of versioned, sourced, tested route data. After this slice, adding a route is a data change: a JSON file and its cases.

## Scope

**In:** calendar dates and money in `packages/domain`; the case snapshot and the fact catalog; the rule schema; the evaluation engine, unit computation and the active-version rule; `packages/knowledge` with the country dataset, country sets, official domains, the catalog loader, validation, content hashes and the immutability check; fixture routes and the synthetic families corpus; the staleness report.

**Out:** real route data (slice 2); storing cases, intake, any AI, and the activation screen with its passkey verification (slice 3); ranking and routes chained to citizenship (slice 4); documents, steps and action points (slice 5); retrieval (slice 6); FX rate feeds and the simulator (slice 7); any API route or UI.

**No case data.** Every snapshot in this slice is synthetic, and the snapshot schema has no names, document numbers or free text.

## Requirements

### R1. Packages and boundaries

- New package `@arca/knowledge`. This slice updates the boundary matrix in spec 0001 R2 and `tooling/scripts/src/check-boundaries.ts`: `packages/knowledge` may depend on `domain`; `apps/api` may also depend on `knowledge`. Nothing else changes.
- `@arca/domain` gains `zod` (already in the catalog) as its only runtime dependency. It stays pure: the domain lint rules of spec 0001 R2 apply unchanged, so no clock, no I/O, no hashing.
- In `packages/knowledge`, `src` is the runtime entry and does no I/O: it exports the catalog the build produced. File reading, validation and hashing live in `scripts`, which run at build and in CI. The build writes the catalog as a generated module, `src/generated/catalog.ts`, which is not checked in. A Turborepo task, `knowledge#catalog`, produces it, and the `typecheck`, `lint`, `test` and `build` tasks of `knowledge` and `api` depend on it, so `pnpm check` works on a fresh checkout.
- `fast-check` joins the catalog for property tests in `domain` and `knowledge` (see [Versions](#versions)); this spec adds it to ADR-0010's testing row.

### R2. Calendar dates and money

- **Dates.** `CalendarDate` is an ISO 8601 calendar date (`YYYY-MM-DD`) with no time or time zone. Operations: parse and validate, compare, add a `Duration`, whole years and months between two dates, and age at a date.
  - `Duration` is ISO 8601 `PnYnMnD`. Adding one applies years, then months, clamps to the month's last day, then adds days (as `Temporal.PlainDate.add` does).
  - Durations are compared only anchored to a date: "at least P2Y since D" means `D + P2Y <= reference date`. A duration range uses a single unit, so its bounds always order.
  - Age at a date counts whole years. Jurisdictions differ on when a 29 February birthday turns a year older in common years, so a route version that reads an age (in a requirement, a condition, a cost or an assessment's evidence) must set `leapDayBirthday` to `"feb-28"` or `"march-1"`, citing its source; validation rejects one that reads an age without it. Every age goes through `person.ageYears` (R3), which applies that setting: validation rejects `since` over a birth-date fact, so no requirement can reach an age by plain duration arithmetic, and a property test shows `ageYears` and the `leapDayBirthday` setting agree on 29 February birthdays.
  - `PartialDate` (a year, or a year and month) exists for ancestors, whose records are often incomplete. A comparison with a partial date is true or false only when every date it could be gives the same answer; otherwise unknown.
  - When `Temporal.PlainDate` is available on the runtime and in TypeScript's library, it can replace the implementation behind the same interface.
- **Money.** `{ amount, currency }`: `amount` is an integer in minor units (a safe integer), `currency` an ISO 4217 code with its minor-unit exponent from a table in the package. The table is written by hand, because `domain` takes no data dependency and the list is small and rarely changes; it cites the ISO 4217 list published by the maintenance agency (SIX) and its verification date. No floating point anywhere in money or rates.
- **Decimals.** Multipliers, shares and FX rates are decimal strings (up to 12 fractional digits), computed with `bigint` scaled arithmetic.
- **Rounding.** Comparisons use exact values: a converted or multiplied amount is compared with a threshold before any rounding. Only reported amounts (costs and totals) are rounded half-even to minor units, once, after an exact sum.
- **FX.** Conversion uses an `FxTable` the caller supplies: rates with their date and source. Pairs are directional (from one currency to another), with no inversion and no cross rates. The rate for a pair is the latest dated on or before `factsAsOf` and at most 7 days older; a table with two rates for the same pair and date is rejected. The engine never fetches a rate. A missing rate makes the comparison unknown and is reported under `missingRates`, never as a question for the family.
- Property tests cover date arithmetic and month-end clamping, ages around birthdays and leap days, partial-date comparisons, money addition and comparison, and conversion rounding.

### R3. Case snapshot and fact catalog

- **`CaseSnapshot`** is the engine's only view of a case, a Zod schema in `packages/domain/src/case`. People carry opaque IDs and structured facts only: birth date, citizenships (country, acquired and lost dates, basis), country of residence, education (ISCED 2011 level), languages (BCP 47 language, CEFR level), income (active or passive, monthly amount, source country), immigration history (country, event kind such as a visa refusal, date), job offers (country, ISIC Rev. 4 section, temporary or not), financial dependence on another person, and whether the person is studying. Assets sit beside people: kind, owners with shares that add up to at most 1, a non-negative value with its valuation date, liquidity and an optional sale.
- **Opaque IDs.** The API assigns IDs per snapshot: one letter and up to four digits, such as `p1` or `a3`. They are too short to carry a name, a document number or an instruction, and they mean nothing outside the snapshot.
- **Relationships** are typed edges: `spouse` and `partner` (with start and end dates) and `parent` (with kind, such as biological or adoptive, custody, and an optional start date for an adoption). Other relationships are derived: an ex-spouse is a `spouse` edge that ended, an in-law is a path such as `spouse.parent`, a sibling shares a parent. The graph may hold people who are not case members, such as grandparents. Validation rejects references to unknown people, self edges, the same edge twice (a couple that remarries is two edges with different starts), more than four parents per person and parent cycles.
- **Recorded on.** A snapshot carries `recordedOn`, the date it describes, and is stored with every evaluation of it. `"none"`, complete lists and completeness markers hold as of that date, so facts are read only at dates on or before it: the engine refuses a `factsAsOf` or a named reference date after `recordedOn`. Projections to later dates are out of scope for this slice.
- **Edge validity at a date.** A couple edge holds from its start until its end; an unknown start or end makes it unknown at a date. A parent edge has no end and is never valid before the child's birth. With a start, it holds from the start. Without one, a biological link holds from the child's birth; any other link, and a biological one whose birth date is unknown, began on an unknown date no later than `recordedOn`, so it is certain at `recordedOn` and unknown before it. The engine follows only edges that are, or may be, valid at the evaluation date (R5).
- **Unknown versus none.** An absent field is unknown, never false. Fields whose usual answer is that something has not happened take an explicit value for it: an end date of a `spouse` or `partner` edge, a lost date of a citizenship and a sale of an asset are a date, `"none"`, or absent (unknown). A present list is complete, so `[]` means none.
- **Completeness markers.** Each person carries markers for what is recorded in full: `spouses`, `partners`, `children` and `parents` (directional, for relationships) and `assets` (every asset the person has a share in is listed, with the person among its owners). Without the marker, people or assets that are not recorded may exist: a collection or a sum over them has no upper bound, and the missing marker is itself a decisive missing fact (R5). Table cases cover absent, `"none"`, empty and complete for each.
- The schema has no free-text fields, names or document numbers, so a snapshot cannot carry instructions. Objects are strict: unknown keys fail validation.
- **Fact catalog.** Rules read facts by key (for example `person.ageYears`, `person.citizenships`, `unit.liquidAssets`). The catalog in `packages/domain` maps each key to its value type, its scope and the pure function that derives it from the snapshot and the context. Scopes are `person` (any person the rule is bound to), `unit` (the unit being computed), `edge` (the edge a dependent rule reached a candidate by, such as `edge.parentKind` or `edge.dependsOnLinkedPerson`) and `lineage` (a person in a line of ancestors). Rule paths bind keys by prefix: `person.*` to the current person, `principal.*` to the principal, `unit.*` to the unit, `edge.*` to the edge, `lineage.*` to the current link and `lineage.ancestor.*` to the ancestor. Reading a key outside its scope fails validation (R4) and throws in the engine.
  - Derived facts such as age, elapsed time or the unit's liquid assets are computed here, in code. Money facts sum per currency and convert each total once, at `factsAsOf`, into the route version's currency per R2; a missing rate leaves the upper bound open, keeps what did convert as the lower bound, and is reported under `missingRates`, every missing pair listed. An owner's share of an asset counts as certain only when the asset is certainly liquid and unsold and the owner is certainly in the unit; otherwise it raises only the upper bound.
  - Facts in a line of ancestors can read the next person toward the principal (for example `lineage.childBirthDate`, and `lineage.edgeKind` for a biological or adoptive link), so "the ancestor was a citizen when the next person in the line was born" is expressible. `lineage.links` is the collection of people strictly between an ancestor and the principal (empty for a parent, where `every` is true), so an unbroken line (each link a citizen at the next birth) is expressible with `every`. Inside a nested collection, `person.*` and `lineage.*` bind to the current link, and the ancestor stays readable as `lineage.ancestor.*`.
  - A fact can be read at a named reference date from the context (for example the filing date, for age protections) instead of `factsAsOf`. A missing named date makes the fact unknown and is reported under `missingDates`.
- A rule that names a key outside the catalog, or compares it with a value of the wrong type, fails validation. Adding a fact is a reviewed code change in `domain`; adding a route never is.

### R4. Rule schema

Zod schemas in `packages/domain/src/rules`, exported as JSON Schema for editors (`z.toJSONSchema`), with `schemaVersion: 1` on every file. Objects are strict. The schema evolves additively; a breaking change adds a schema version that the engine supports alongside the old one, so old versions still evaluate.

- **Route.** `id` (`<country code in lowercase>-<slug>`, for example `pt-d7`), country, tags (free strings such as `work`, `investment`, `descent`, `seasonal-work`; never an enumeration in code) and its versions. There is no separate route file: country and tags are fields of every version file, so they are hashed and activated with it.
- **Route version.** Route ID; number (contiguous from 1); `effectiveFrom` (a `CalendarDate`); optional `corrects` (R6); `status` (`open` or `closed`); `currency`; optional `leapDayBirthday`; `sources`; `closureSources` (on a `closed` version only); `countrySets`, `officialDomains`, `countries` and `formerCountries` (references pinned to an exact ID and number); `requirements`; `assessments`; `dependents`; `costs`; `durations`. A `closed` version (for example, an abolished golden visa) has no requirements, assessments, dependents or costs, and its `closureSources` cite at least one `official` source.
- **Sources.** Each has an ID, an `https` URL, a title, a kind (`official` or `secondary`) and `verifiedAt`. Every requirement, assessment, dependent rule, cost and duration cites at least one `official` source by ID. A source is `official` only if its host is on one of the official-domain lists that the route version, or the country set citing it, pins (R6). Matching uses the parsed URL (the knowledge package parses it and hands `domain` the host, since `domain` has no URL parser; `domain` does the matching): `https` only, no user information or port, the host lowercased and in ASCII (punycode), equal to a listed host or a subdomain of it on a label boundary (`www.uscis.gov` matches `uscis.gov`; `evil-uscis.gov` does not). Secondary sources may be added beside an official one, never instead.
- **Free text.** Titles, names and tags are plain strings capped at 200 characters and rendered escaped. They are data: when knowledge text reaches a model (retrieval, slice 6), it goes inside a delimited data block. Slice 6, which builds retrieval, adds injection cases for knowledge text to the evaluation suite under `eval/`, with its own reviewed decision on how the reviewers treat them. Reviewers of knowledge pull requests flag instruction-like text.
- **Expressions.** A JSON tree with a closed set of operators, evaluated without `eval`, regular expressions or user code:
  - Values: boolean, integer, decimal, money, date, duration, country code, string enum from the fact catalog, pinned country set.
  - Comparisons: `eq`, `ne`, `lt`, `lte`, `gt`, `gte`, `in`, `intersects`.
  - Logic: `all`, `any`, `not`.
  - Arithmetic: `add`, `sub`, `mul` (by a literal decimal), `min`, `max`, so a threshold can depend on the unit (Portugal D7 shape: a base amount, plus a share per adult dependent and per child).
  - Money operands must share a currency; mixing currencies fails validation unless an operand is wrapped in `convert(expression, currency)`.
  - Dates: `since(date, duration)`, true when the date plus the duration is on or before `factsAsOf`, or a named reference date when the expression names one. A version declares the names of the reference dates it reads (`referenceDates`, such as `filingDate`); validation rejects any other name.
  - Collections: `count`, `sum`, `some` and `every` over people (`unit.members`, which includes the principal; `unit.dependents`; `principal.ancestors`, every line from the principal up through `parent` edges to a generation depth given in the expression, at most 4, whether its people are case members or not; `lineage.links` inside it), each with a condition per person. An ancestor reached through two lines (pedigree collapse) is one item per line, since line facts such as citizenship at the next birth depend on the line.
  - Literals: `bool`, `int`, `decimal`, `money` (minor units and a currency), `date`, `token`, `tokens` (a literal list used as a set) and `set` (a pinned country set). `in` takes a token and a set; `intersects` takes a list fact, such as citizenships, and a set.
  - Limits checked by validation: depth at most 16 and at most 500 nodes per version. Collections do not nest, except `lineage.links` inside `principal.ancestors`, so evaluation stays linear in expressions times people. The knowledge loader checks JSON depth without recursion after `JSON.parse` and before the schema parse.
- **Logic is three-valued** (Kleene): true, false or unknown. `all` is false if any operand is false, `any` is true if any operand is true. Collections carry bounds: `count` and `sum` over members whose condition or membership is unknown yield a known minimum and maximum. When a completeness marker is absent, a `count` is unbounded above, and a `sum` is unbounded above only when validation proves its summand non-negative (no `sub`, no negative multiplier, only facts the fact catalog marks non-negative) and unbounded on both sides otherwise. Bounded values carry through arithmetic as intervals: `add` gives [a.min + b.min, a.max + b.max], `sub` gives [a.min − b.max, a.max − b.min], `mul` by a negative decimal swaps the bounds and by zero gives exactly zero, and `min` and `max` apply to each bound. A known value is an interval of one point and a wholly unknown number is unbounded on both sides; an unknown date, enum, country or set ranges over its whole domain. A comparison is decided when every value its operands can take gives the same answer, and unknown otherwise. Intervals ignore links between operands (assets and a threshold that depend on the same possible dependent), so they over-approximate: an answer they decide is never wrong, but some answers stay unknown and the decisive missing facts may then include a fact that a joint analysis would show does not matter. Property tests check the interval rules, and the D7-like fixture has a case decided because its bounds agree.
- **Requirements** are named expressions on the principal and the unit, each with sources. **Assessments** model judgment calls (for example, national importance in an EB-2 NIW petition) as named factors with the evidence facts that support them, never as pass or fail (ADR-0002).
- **Dependents.** Rules of the form _relationship path from the principal_ (`spouse`, `partner`, `child`, `parent`, or a composition of up to three steps such as `spouse.parent`) _plus a condition on the candidate_ (for example, unmarried and under 21; or financially dependent on the principal). Each step crosses only edges valid at `factsAsOf`, or at the rule's named reference date (start on or before it, and end `"none"` or after it); an unknown start or end makes the candidate possible. A `parent` edge is valid as R3 describes: from its start date when it has one, otherwise from the child's birth for a biological link, and certainly at `recordedOn` for any link; an adoption without a known date is therefore valid when `factsAsOf` is `recordedOn`, and a rule that needs the date (adoption before a given age) reads it as an `edge` fact, which is then unknown. So `spouse` means a current spouse, and an ex-spouse is never reached. Conditions read `candidate`, `principal` and `edge` facts (kind, custody, start and end of the path's last edge), never `unit` facts, so a unit cannot depend on itself. Paths never return the principal and return each person once, with every last edge they were reached by; the condition holds for the person when it holds through any of those edges. This expresses U.S. EB-5's spouse and unmarried children under 21 and Portuguese family reunification's dependent parents of the resident or spouse, without a fixed family partition.
- **Costs.** Kind (a free string tag such as `fee`, `capital`, `proof_of_means`, `bond` or `health_insurance`; never an enumeration in code, so a new kind is a data change), an amount expression in the version's currency, who it applies to (`principal`, `each_dependent`, `unit`), an optional condition, and sources.
- **Durations.** Named stages (for example, to a decision, to residence) as a single-unit `Duration` range with sources.
- **Country sets** (for example, E-2 treaty countries, Mercosur members) are versioned files that cite an official source and pin their own official-domain, countries and former-countries versions. A route version pins each set it uses by ID and number, so a new set version reaches a route only through a new route version. The same holds for official-domain lists.

### R5. Evaluation engine and unit computation

Pure functions in `packages/domain/src/rules`, with no I/O and no model calls. The catalog hands the engine `CatalogEntry` values: a validated version, its identity (with the content hash over every file it pins, R6) and the pinned files the engine reads, which in this slice are its country sets. The engine reads sets only from the entry, never from the caller, and refuses an entry whose identity disagrees with its version or that lacks a pinned set.

- **Context:** `rulesAsOf` (the date that selects the version: today, or a filing date when a route keeps old rules for pending applications), `factsAsOf` (the date ages and elapsed times are computed at; defaults to `rulesAsOf`), named reference dates (`factsAsOf` and these are on or before the snapshot's `recordedOn`, R3; the API builds the snapshot when it evaluates, so `recordedOn` is today and the default holds), `today` (for staleness only), the `FxTable`, `states`, and the engine's commit (for reproducibility, ADR-0014). `states` maps each version identity (route ID, number and content hash, so an activation covers one exact content) to its decision state: `active`, `rejected` or `proposed` (which also covers a version whose rejection is still pending, ADR-0014). In slice 3 the API computes it from verified decisions (ADR-0014); in this slice tests supply it. The engine never reads decisions.
- `selectVersion(identities, rulesAsOf, states)` picks, among **all** versions, the one in effect. `states` comes from the context. The initial candidates are the versions that are not rejected and have `effectiveFrom` on or before `rulesAsOf`. Each initial candidate removes the version its `corrects` names and, transitively, every version that one corrects in turn, whether or not those are rejected. All removals happen at once. So in a chain where v2 corrects v1 and v3 corrects v2, both v1 and v2 go, even when v2 was rejected. Among what remains, the greatest `effectiveFrom` wins, and on a tie the highest number. Only then is activation checked: if the selected version is not active, the result is `pending_activation`. The engine never falls back to an older version on its own, so a proposed closure or a proposed correction is never silently ignored; the only way back to the older version is an approver's rejection of the newer one (ADR-0014). Selection reads only the identity of proposed versions (number, `effectiveFrom`, `corrects`, `status`, hash, state); their content is never evaluated for a case.
- **Route catalog interface.** `packages/domain/src/rules` defines `RouteCatalog`, with `identities(routeId)` and `activeEntry(identity, states)`, which returns nothing for a version that is not active. `evaluateRoute` takes a `RouteCatalog`; `packages/knowledge` implements it, and the reproduction lookup below, over the generated catalog (R6). `domain` imports nothing from `knowledge`.
- **Identity only for selection.** `VersionIdentity` (route ID, number, `effectiveFrom`, `corrects`, `status`, hash), `CatalogEntry` and `DecisionState` are types defined in `packages/domain`; `knowledge` only produces values of them, so the boundary matrix holds. The catalog exposes the identity of every version, and the full entry only through `activeEntry`. `selectVersion` takes identities only, and `evaluateRoute` obtains the full entry from `activeEntry` after selection, so CLAUDE.md rule 5 is a compile-time property.
- `computeUnit(snapshot, entry, principalId, context)` returns the dependents the version covers (included), the ones it might cover pending unknown facts (possible, with those facts), and everyone else with the reason they are out: no rule's path reaches them, no condition holds, or, while any dependent rule reads a reference date the context lacks, nobody can be ruled out. That last case leaves the unit open, like a missing completeness marker. Each dependent keeps every last edge it was reached by with whether a rule covers it through that edge, so an `each_dependent` cost applies only through an edge that covers the dependent. Units are computed, never stored. Possible dependents count as unknown members, so collection bounds (R4) and `each_dependent` costs reflect them: costs give a known total plus the possible extra.
- `evaluateVersion(snapshot, entry, principalId, context)` evaluates one given version, with no selection and no activation check. It returns an `Evaluation`: route ID, version number, content hash, the dates of the context, principal, unit, status, each requirement's result with its sources and a trace, each assessment with evidence present and missing, the decisive missing facts, `missingRates`, `missingDates`, costs per item with totals per currency (each item rounded on its own and each total from the exact sum, so shown items may differ from the total by rounding), durations, the FX rates it used, and its stale sources (R9). Table-driven cases (R8) and the reproduction of an old evaluation use it, with entries from a reproduction lookup keyed by route ID, number and content hash that ignores `states`, so an evaluation of a version later rejected stays reproducible. That lookup is a separate entry point of `@arca/knowledge`, and a lint rule allows importing it only in the cases runner and the reproduction path, never where `evaluateRoute` runs.
- `evaluateRoute(snapshot, catalog, routeId, principalId, context)` is selection, then the activation check, then `evaluateVersion`. It adds `newerProposedVersion`, with the date it would apply from, when a version that is not active would be selected at `rulesAsOf` or a later date in place of the selected one (a later rule change, or a correction of the selected version), and sets `stale` (R9). It refuses context dates after `recordedOn` before selecting, and an entry from `activeEntry` that is not the identity it selected. `evaluateVersion` and `computeUnit` take the context without `states`, since they select nothing. Slice 3 adds the activation the evaluation relied on to the record.
- **Status**, first match wins: `unavailable` (no version in effect), `pending_activation` (the version in effect is not active; `evaluateRoute` only), `unavailable` (the version is `closed`), `not_eligible` (a requirement is false), `missing_information` (a requirement is unknown), `needs_assessment` (all requirements hold and the version has assessments), `eligible`. A proposed closure therefore shows as `pending_activation`, never as `unavailable`.
- **Decisive missing facts**, defined deterministically: empty when a requirement is false; otherwise, for each unknown requirement, the facts at its unknown leaves that are not cut off by a known operand (a false inside `all`, a true inside `any`), plus, for each collection there that is not decided, the facts that make its possible dependents possible (as `computeUnit` reports them) and the completeness markers whose absence leaves it unbounded. Facts that matter only together are both listed. Missing FX rates and context dates are reported apart, since the family cannot answer them. Slice 3 turns them into "only the questions that change the answer". A missing fact is one of three kinds, each about a person or an edge in the snapshot: a catalog fact read on a person (`unit.*` facts name the principal and bring in the facts behind possible dependents), a relationship whose validity at the date is unknown, or a completeness marker. Paths and lines of ancestors carry the edges whose validity is unknown, so a possible dependent or ancestor names the relationship to ask about.
- **Evaluations are personal data.** A snapshot, an evaluation and its trace hold birth dates, assets, income and immigration history of several adults. They are never logged, never sent to error reports or workflow payloads, and slices 3 and 4 show each viewer only what that viewer may see (SECURITY.md principle 3). A lint rule forbids `console` anywhere in `packages/domain`.
- Performance: linear in the size of the expressions times the number of people; a test bounds a 12-person snapshot against the full fixture catalog.

### R6. Knowledge catalog

- **Build.** `scripts/build.ts` reads every file in `data`, validates it against R4, checks references (sources, pinned country sets, official domains, route ID prefix against the country) and writes the catalog, with hashes, into the generated module (R1); `@arca/api` imports it. Nothing reads the data directory at runtime.
- **Content hash:** SHA-256 over the RFC 8785 canonical JSON of one container object, `{ "version": <the route version>, "pinned": { "<kind>/<id>/<number>": <file>, … } }`, where `pinned` holds every file the version pins, transitively: country sets, official-domain lists, countries and former countries, and the files those sets pin in turn. One canonical document means no framing between files is needed. The same container, with `version` holding the file, hashes country sets. Computed by the build with Node `crypto`. An activation therefore covers all of them, and the activation screen's diff shows the same files.
  - The accepted JSON subset: integers only, within ±(2^53 − 1) (no floating point; decimals and money are strings), strings in NFC that the build checks and never normalizes, no control, format or invisible characters (Unicode `Cc`, `Cf`, `Zl`, `Zp` and `Default_Ignorable_Code_Point`, line breaks included, since knowledge strings are single-line), so a reviewer sees the text that is hashed (this also refuses the zero-width joiners some scripts, such as Persian, need; titles are in Portuguese and English), no duplicate keys. Keys are ordered by UTF-16 code units and strings escaped as RFC 8785 section 3.2.2.2 sets out.
  - The canonicalizer passes the RFC 8785 appendix test vectors as fixed tests. A committed `packages/knowledge/data/hashes.json`, append-only like the cases files and covered by the same check, records each version's hash and the RFC 8785 vectors' expected hashes, and a test fails when the build computes a different one, so a canonicalizer change shows up in review, not as activations lost in production.
- **Corrections.** A rule change is a new version with an `effectiveFrom` later than every lower-numbered version's, corrections included; a rule change dated earlier is written as a correction of the version selected from the latest `effectiveFrom` onward, carrying the merged content. A correction of a data error is a new version with `corrects: <n>`, where `n` is a lower version number, and an `effectiveFrom` in one of three places: the date of the version it fixes (it wins the tie, R5), an earlier date when the original started too late, or a later date inside the original's period for a change found late. Selection (R5) drops a corrected version once its correction is in effect, so each of the three gives the right version on every date; R8 has a fixture case for each. Old evaluations keep pointing at the version they used and are reproduced with `evaluateVersion`.
- **Official domains.** `data/official-domains/<issuer>/<n>.json` lists the hosts that count as official for a country or an international body (for example `uscis.gov` for `us`; `eur-lex.europa.eu` for `eu`; `mercosur.int` for `mercosur`), each with a source showing the host belongs to that government or body. A route version or country set may pin several lists. Versioned and immutable like everything in `data`; each route version is validated against the list version it pins, so a later list never breaks an old version.
- **Immutability check:** fails when a file under `data` or `vendor` that exists on the base branch is modified, renamed or deleted. Cases files and `hashes.json` are the exceptions: entries may be added, but an existing entry (matched by its `id`, or by version for hashes) may not change or disappear. A case whose expected result must change after an engine fix gets a new entry with `supersedes: <id>`, and a reason; the superseded entry stops running and no longer counts toward coverage. The check accepts it only when the same pull request changes code under `packages/domain/src` (rules, calendar, money or the fact catalog can each change a result) and the two entries differ only in their expected results, and the check itself is tested on a synthetic pair of entries. A cases file is `{ "schemaVersion": 1, "cases": [ … ] }` and an entry's expected results are its `expected` member, so a superseding entry may differ from the one it supersedes only in `id`, `supersedes`, `reason` and `expected`; a case is superseded at most once.
  - It runs as the required check `knowledge-immutable` in `policy.yml` on `pull_request_target`, like `lockfile-policy`: the definition and script come from `main`, and it compares the pull request head's `packages/knowledge/data` and `packages/knowledge/vendor` trees and `.github/policy/vendored.json` with the base, as data fetched from git: paths are read with `git ls-tree -z` and never interpolated into a shell, anything it installs comes from `main`'s lockfile, and nothing from the pull request runs. Spec 0001 R8's table and the `main` ruleset list it. `pnpm check:knowledge-immutable` runs the same script locally.
  - It also fails a pull request that changes `data/official-domains` together with any other knowledge data (appending to `hashes.json` excepted), so a change to a trust root is always its own pull request (ADR-0014). A host added to an existing issuer's list must cite proof (its `source.url`, read as `hostOf` reads it) on a host of any issuer's list version on `main`, matched as official sources are. The first list for an issuer cites a registry such as the country's domain authority, which its reviewer checks since registries are not listed as data, and goes in a pull request with no other list change. The check compares the pull request head with `main`'s tip; the `main` ruleset requires branches to be up to date, so the difference is the pull request's own. Slice 2 extends the rule to country guides, and slice 3 to the approver list.
- **Validation in `pnpm check`:** every file validates; version numbers are contiguous; a version without `corrects` has an `effectiveFrom` strictly after every lower-numbered version's, corrections included, so a new rule or closure is never shadowed by an earlier correction; a `corrects` version names a lower number and is judged by its outcome: added to the versions numbered below it, all treated as active, it must make `selectVersion` pick it, from its `effectiveFrom` on, on every date where selection picked the version it fixes, a correction of that version (directly or through a chain) or a version its own chain removes; a correction that starts before those dates also takes the run just before them, but starts after that run's start unless that run's version is in its chain (any date when no run precedes, so a correction of the first version may predate it); and every other date keeps its version. A correction therefore never shadows a version it does not fix, and a newer correction of a version is never shadowed by an older one, which a property test over random histories checks; every requirement, assessment, dependent rule, cost and duration cites an official source, and a `closed` version's `closureSources` do; `verifiedAt` is not after the build date; every version has a cases file that meets R8's coverage.
- **Review.** The core reviewers check knowledge data's structure and CLAUDE.md's domain rules like any other change. They cannot open the sources. Checking a rule's content against its official source is an approver's job on the activation screen (ADR-0014), which shows the rule, its source hosts and its cases side by side, helped by the independent check's advisory report in its own panel.

### R7. Countries

- `data/countries/<n>.json` is generated by `scripts/generate-countries.ts` from a pinned Unicode CLDR release (Unicode License v3). The source is CLDR JSON's English territory names file (`cldr-localenames-full/main/en/territories.json`, read for its codes only) from the `unicode-org/cldr-json` GitHub release tag, vendored with the Unicode license notice under `vendor/cldr/<release>/`, beside a `manifest.json`. `.github/policy/licenses.json` covers npm packages only and is not changed.
  - **Approval first.** A policy pull request of its own, which needs a supply-chain PASS, adds a self-contained entry to `.github/policy/vendored.json`: upstream repository, tag, the tag's 40-hex commit SHA, path, SHA-256 of the data file, path and SHA-256 of the upstream license file, and the license. `vendored.json` is append-only: an existing entry never changes or disappears. `knowledge-immutable`, the required check, enforces both and verifies every new entry from the entry alone, with no write permission (the job reads `contents` only, which on this public repository grants nothing an anonymous reader lacks), no secrets, no persisted credentials and a timeout. A change to `vendored.json` carries no knowledge data or vendored file, so the vendor pull request reads its approval from `main`. It first validates every field against a strict grammar: the repository exactly as listed in `.github/policy/vendored-sources.json` on `main` (today `unicode-org/cldr-json`), the commit `^[0-9a-f]{40}$`, the tag `^[A-Za-z0-9][A-Za-z0-9._-]*$` with no `..` (so no glob or ref syntax), and each path relative segments of `[A-Za-z0-9._-]+` with no `.` or `..` segment and no `%`, `?`, `#` or `\`. It then builds each URL itself as `https://raw.githubusercontent.com/<repository>/<commit>/<path>` and fails unless the parsed URL's pathname equals the expected string, so a branch name, any other ref or another repository is impossible; adversarial cases cover a `..` path, a `%2e` path, a traversing tag, the tags `head` and `*`, a branch named like the tag and a commit from a fork's pull request ref. Because GitHub serves commits from a repository's whole fork network under the upstream path, it also resolves the tag with `git ls-remote --tags -- https://github.com/<repository> refs/tags/<tag> refs/tags/<tag>^{}`, its arguments passed as an array, with `-c http.followRedirects=false -c protocol.allow=never -c protocol.https.allow=always`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0`, from an empty temporary directory with `GIT_CEILING_DIRECTORIES` set and an allow-listed environment without `GIT_CONFIG_*` variables, a timeout and an output cap. It accepts only lines whose ref name is exactly `refs/tags/<tag>` or `refs/tags/<tag>^{}`, uses the peeled commit when present, fails on no match or any other ref, and fails unless the result equals the entry's commit. It follows no redirect, refuses any other host, caps the size, and fails unless both SHA-256 values match. It requires the license file's SHA-256 to match a license text pinned in `vendored-sources.json`, rather than trusting a field the pull request wrote. `vendored-sources.json` is a trust root like `licenses.json`: a change to it is a policy pull request of its own and needs a supply-chain PASS.
  - **Then the vendor pull request.** `knowledge-immutable`, reading `vendored.json` from `main`, accepts a new data file under `vendor` only when its SHA-256 is in an approved entry, and requires the `manifest.json` beside it to equal that entry field for field; the approved entry wins, so a manifest that disagrees fails the check. The license notice is the upstream license file at the same commit, so its SHA-256 is listed in the same entry and checked the same way.
  - **Generator.** It pins the tag and the file's SHA-256 and fails on a mismatch; it runs only by hand when a maintainer regenerates, never in `pnpm check` or the build, and no npm package is added. The output records the CLDR release, the SHA-256, the license and the license file's SHA-256; the notice itself stays beside the vendored file, since knowledge strings are single-line. The countries file holds the following.
  - every current ISO 3166-1 alpha-2 code CLDR lists as a region. The generator excludes numeric macro-regions, grouping codes (`EU`, `EZ`, `UN`), the pseudo-regions `XA` and `XB`, `QO`, `ZZ` and, by an explicit list, the exceptionally reserved codes CLDR also lists (`AC`, `CP`, `CQ`, `DG`, `EA`, `IC`, `TA`).
  - `XK` (Kosovo) is included: CLDR lists it and it issues passports.
  - The generator classifies every region code in the file as included or excluded by the lists above, and fails on any code that is in neither the previous countries file, those lists nor the generator's reviewed admissions, and on any code of the previous file that a new release drops unless the generator lists it as withdrawn, so each code a new CLDR release adds or removes is classified by a reviewed change. The first file has no predecessor, so its full included list is the baseline its own pull request reviews.
- `data/former-countries/<n>.json` is a reviewed, sourced list of former states with ISO 3166-3 four-letter codes (for example `CSHH` Czechoslovakia, `SUHH` Soviet Union, `YUCS` Yugoslavia, `DDDE` East Germany), allowed only in citizenship and ancestry facts (the fact catalog marks them; a former code in a rule's literal, or a pinned country set with a member outside the countries file, compared with any other country fact is invalid), since many ancestors were citizens of states that no longer exist. Route versions pin it with the countries file.
- A regeneration is a new numbered file, like any other data, and the generator's test, offline, hashes the vendored bytes itself and compares the result with the hash approved in `.github/policy/vendored.json`, the countries file and the manifest. The vendored file is covered by the immutability check like `data`. Each route version and country set validates against the countries version it pins.
- Current country names come from `Intl.DisplayNames` in the reader's locale, so pt-BR names are natural Brazilian Portuguese and none is written by hand. `Intl.DisplayNames` has no names for ISO 3166-3 codes, so former countries' names live in the i18n catalogs.
- The real catalog accepts only codes in this dataset. User-assigned codes `QM` to `QZ` (except `QO`, which CLDR uses, and `QU`) are reserved for fixtures: only a fixture build (the tests' option) accepts them, and the real build rejects them.

### R8. Table-driven cases, fixtures and families

- **Cases files.** Each `<n>.cases.json` lists entries for that version, run through `evaluateVersion`, with an `id`, a snapshot (inline, or a family from `eval/families` named by ID, number and the SHA-256 of its file; family files are numbered and immutable, which `knowledge-immutable` enforces, so extending a family is a new number and old cases keep theirs), the principal, the context dates, FX rates when needed, and the expected status, unit and decisive missing facts. CI runs them all. Expected results live only here.
- **Coverage**, measured from the engine's trace across a version's cases file: every requirement evaluates to true, false and unknown at least once; every dependent rule includes and excludes someone at least once; the statuses `eligible` (or `needs_assessment` when the version has assessments), `not_eligible` and `missing_information` each appear. A `closed` version needs one case, `unavailable`. Selection, rejection, `pending_activation` and `newerProposedVersion` are covered by the engine's own tests on the fixture routes, with fixture `states`.
- **Fixture routes** prove the schema before real data exists. They use user-assigned country codes, are labeled as fixtures, and cover these shapes:
  - a threshold computed from the unit's composition (D7-like);
  - dependents limited to a spouse and unmarried children under 21, with an investment threshold in another currency than the assets (EB-5-like);
  - dependent parents of the principal or of the spouse (family-reunification-like);
  - citizenship by descent through a parent or grandparent, conditioned on the ancestor's citizenship when the next person in the line was born, with a partial date and a former country (Italian-descent-like);
  - eligibility through a pinned country set of the principal's citizenships (E-2-like);
  - a judgment factor with evidence (EB-2 NIW-like);
  - a seasonal work route tied to a job offer (H-2A-like);
  - a closed route, and a closure left proposed; a version replaced at a date, evaluated with a pending-applications `rulesAsOf`; corrections dated the same as, before and after the version they fix, one of them on an earlier version, not the latest; a proposed correction dated before the active version it fixes; a chain of corrections (v3 corrects v2, which corrects v1); a newer version left proposed, and one rejected;
  - an adoptive parent edge with and without a start date;
  - a correction of a later version dated before the route's first version, which validation rejects;
  - a correction of v2 dated the same as v1, which validation rejects;
  - a correction of an earlier correction when a later version without `corrects` exists (v1 in January, v2 in June, v3 correcting v1 in March, v4 correcting v3 in April), which validation accepts, and v4 dated in July, which it rejects;
  - a requirement using `since` over a birth date, which validation rejects;
  - two corrections of the same version, the newer one dated earlier, which validation rejects;
  - a version without `corrects` dated before an existing correction (v1 in January, v2 correcting v1 in March, v3 in February), which validation rejects, and its accepted form, v3 correcting v2 in February;
  - a correction of a rejected correction, which still removes the original.
- **Synthetic families** in `eval/families/`: a single person; a couple with young children; divorced parents with shared custody; dependent elderly parents; a previous visa refusal; assets held by an ex-spouse; and a large three-generation family of six adults. All values are invented and mirror no real person's ages, dates or holdings.

### R9. Staleness

- A source is stale when its `verifiedAt` is more than 90 days before the context's `today`. `evaluateVersion` lists the stale sources it cited. `evaluateRoute` sets `stale: true` when there are any and `selectVersion(identities, today, states)`, with the context's `states`, returns the version evaluated, so the interface can say the rule needs re-checking. A superseded version reached through a past `rulesAsOf` (pending applications) is never stale: its sources record the rule as it was, and its page may no longer show it. Re-verifying a source is a new version (ADR-0014), so every verification date a user sees has been activated. The staleness report has no states, so it treats every version as active and checks the version each route selects at the report's date.
- `scripts/staleness-report.ts` lists stale sources by route, as identifiers only (route ID, version number, source ID, host, `verifiedAt`, days stale), never titles or other free text. A weekly workflow (schedule and manual dispatch only) runs it and keeps one open issue up to date, found by the label `knowledge-staleness` alone, never by title. It has `permissions: {}` at the top and two jobs: one with `contents: read` that installs and runs the report and passes it on as an artifact, and one with `issues: write`, no checkout and no install, that posts it. Actions are pinned by SHA and each job has a timeout. The only secret is `GITHUB_TOKEN`, used only in the `issues: write` job, and the workflow's entry in the workflow-secrets policy lists exactly that. The issue is locked to collaborators.
- Agents re-verify by running the report locally and proposing new versions; they never take instructions from the issue's text or comments.

## Definition of done

- Every requirement above is met and covered by a test or a CI check.
- The fixture catalog passes validation and coverage; every case, including those on synthetic families, passes.
- `pnpm check` runs in CI, and `knowledge-immutable` is a required check from `policy.yml`.
- No user-facing string added; no personal data anywhere.
